## Current Phase — Phase 4 / P4

The API audit found that the existing reliability submit callback is already the
smallest suitable integration boundary:

```text
Reliability
    |
    | enp_reliability_submit_fn
    v
Routing DATA path
    |
    +-- current route lookup
    +-- current next-hop selection
    +-- logical -> transport resolution
    +-- transport send
```

No new reliability API is required. Reliability owns the transaction and packet
identity; routing determines the current path for each transmission attempt.

The E3 self-test also deliberately changes the active route between the initial
submission and a retransmission. This proves that a retry re-enters routing and
can select a new next hop without changing the reliability transaction identity.

## Route-failure/resilience boundary

E3 does not implement route failure detection, RERR, route rediscovery or route
repair. Those behaviours must be implemented later in routing/resilience. The
E3 integration is deliberately designed so that reliability does not cache or
own a routing next-hop decision.

Future example:

```text
Attempt 1: A -> B -> C

B/C path becomes unavailable and routing repairs the route

Attempt 2: A -> E -> C

Same reliability transaction; different current route.
```

## Next steps

1. Consolidate the validated E3 components into reusable ENP infrastructure and reduce the E3 test applications to thin integration tests.
2. Keep routing resilience (stale/lost next hops, RERR, route rediscovery/repair) as a separate subsequent phase.
3. Preserve the frozen E3A/E3B/E3C contracts while integrating the proven behavior into production services.

## Phase 4 / E1 — Reusable Data Plane

**Status:** PASS / FROZEN.

P4.1 introduces `core/data/enp_data_plane.*` and moves reusable receive-time
DATA/ACK duplicate-domain ownership and non-local DATA/ACK forwarding into
ENP core infrastructure. The existing routing data path remains the owner of
route lookup, next-hop resolution, TTL decrement and transport transmission.

The existing dispatcher API remains compatible. `enp_dispatcher_dispatch_local()`
was added for the future data-plane receive path so that DATA/ACK packets are not duplicate-filtered twice.

### Phase 4 / E3 — E3C Consolidation

**Status:** PASS / FROZEN.

P4/E3 consolidates the reusable DATA/ACK receive-time behavior proven by the
Phase 3 E3C three-node test into `core/data/enp_data_plane.*`. The E3C
integration test no longer owns the production DATA/ACK duplicate caches,
DATA forwarding, ACK forwarding, or cached-ACK recovery logic.

The validated hardware path is:

```text
A -> B -> C DATA
C -> B -> A ACK

First ACK is intentionally dropped at A before A data-plane processing.
A retransmits the same DATA transaction.
B suppresses the duplicate DATA and recovers the cached ACK.
B forwards the recovered ACK to A.
A completes the same reliability transaction as DELIVERED.
```

The three-node hardware validation was performed with the controlled startup order `C -> B -> A`, so that C and B are ready before A submits the initial reliable DATA. This startup order is a property of the current hardware test harness and is not an ENP protocol requirement.

B validation counters were observed as:

```text
DATA received              2
DATA forwarded             1
ACK received               1
ACK forwarded              2
duplicate DATA suppressed  1
cached ACK recovered       1
```

C delivered application DATA exactly once and generated exactly one ACK. A observed exactly one retransmission, received the recovered ACK, and reached `DELIVERED`.
Non-DATA/ACK traffic, including periodic Discovery packets, is excluded from the reusable data plane; the data plane remains responsible for DATA and ACK traffic rather than discovery/routing-control packet processing.
