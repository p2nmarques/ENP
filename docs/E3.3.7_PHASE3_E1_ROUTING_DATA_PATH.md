# E3.3.7 Phase 3 / E1 — Routing Data-Path Integration

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** HARDWARE VALIDATED  

## Purpose

Phase 3 begins the routing integration boundary required by E3.3.7.
The project routing integration specification defines logical operations for
`routing_tx_data`, `routing_lookup_next_hop`, and transport submission. The
existing route table is deliberately transport-independent, while the E3
hardware tests previously implemented route lookup, neighbor-to-transport
resolution, and `enp_transport_send()` locally inside test applications.

This phase extracts the DATA transmission boundary into a reusable component
without changing the route-table API or the ENP wire format.

## Implemented boundary

```text
Reliability
    |
    | enp_reliability_send()
    v
Routing DATA path
    |
    +-- active route lookup
    +-- logical next-hop selection
    +-- next-hop -> transport-address resolution callback
    +-- enp_transport_send()
    |
    v
Transport / ESP-NOW
```

## Important source-derived constraint

The current `enp_route_table` is intentionally a routing-core data structure
and does not own forwarding or transport dependencies. The current routing
integration specification explicitly places transport submission in the
integration layer. Therefore this phase does not add transport dependencies
to `enp_route_table`.

## Origin submission

`enp_routing_data_path_submit()`:

1. validates the packet;
2. obtains the active route for the packet's logical destination;
3. obtains the transport address for the selected next hop through a callback;
4. submits the original packet unchanged through the ENP transport.

This is the path that E3.3.7 reliability will use for the initial DATA and
for retransmissions. Preserving the packet unchanged is required so that
DATA transaction identity remains stable across retries.

## Forwarding

`enp_routing_data_path_forward()`:

1. validates the received packet;
2. obtains the active route;
3. rejects forwarding when TTL is already 1 or less;
4. copies the packet;
5. decrements TTL in the copy;
6. reseals the packet CRC;
7. transmits the copy to the selected next hop.

The caller's received packet is not modified.

## Deliberate non-goals

This phase does not yet implement:

- route discovery orchestration;
- RREQ/RREP/RERR integration;
- ESP-NOW-specific routing code;
- changes to duplicate suppression;
- changes to E3.3.6;
- automatic route discovery when a route is missing.

Those belong to the broader routing integration work and must use the
existing R4 processor interfaces.

## E1 acceptance tests

The self-test verifies:

- active route lookup;
- next-hop selection;
- transport-address resolution;
- origin DATA submission;
- preservation of DATA sequence, flags and TTL;
- forwarding through the selected route;
- TTL decrement on the forwarded copy;
- preservation of the caller's original packet.

## Validated result

E1 passed on ESP32 hardware under ESP-IDF 6.0.2. The self-test validated active-route lookup, next-hop selection, transport-address resolution, origin DATA submission, DATA identity/TTL preservation, forwarding TTL decrement, and preservation of the caller packet.

## Next step

After E1 passes on ESP-IDF 6.0.2, the next integration step is to connect the
real ENP context/neighbor table and transport to this boundary, then connect
`enp_reliability_send()` to it. Only after that should the three-node E3.3.7
hardware test be attempted.
