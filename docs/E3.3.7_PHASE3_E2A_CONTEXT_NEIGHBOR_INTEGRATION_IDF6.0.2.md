# E3.3.7 Phase 3 / E2-A — Real ENP Context + Neighbor Integration

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** HARDWARE VALIDATED

## Purpose

E2-A connects the E1 routing data-path boundary to the existing ENP runtime context and neighbor table without introducing a new routing or transport abstraction.

The test uses the real `enp_context_t` and `enp_neighbor_table_t`, but a controlled transport adapter. ESP-NOW is intentionally not exercised in E2-A; that is the separate E2-B stage.

## Production API extension

The only production API added by E2-A is:

```c
esp_err_t enp_neighbor_get_transport_address(
        enp_neighbor_table_t *table,
        const enp_address_t *address,
        enp_transport_address_t *transport_address);
```

The API copies the transport address while the neighbor table is locked. It does not expose a pointer to internal neighbor-table storage.

The routing data path remains independent of the neighbor table and receives the mapping through its existing resolver callback.

## Acceptance tests

The self-test verifies:

- real ENP context initialization;
- supplied transport initialization;
- local logical identity initialization;
- real neighbor-table update;
- logical neighbor -> transport-address resolution;
- active route lookup;
- routing data-path initialization with a context resolver;
- origin DATA submission through the real context/neighbor mapping;
- controlled transport send;
- correct transport destination selection;
- unchanged DATA bytes;
- unchanged DATA sequence, flags and TTL;
- context and transport deinitialization.

## Deliberate non-goals

E2-A does not implement or change route discovery, RREQ/RREP/RERR processing, the route-table API, forwarding architecture, duplicate suppression, reliability, or ESP-NOW-specific routing.

## Validated result

```text
E3.3.7 Phase 3 / E2-A self-test PASS
No main-task stack overflow
```

The first E2-A hardware run passed functionally but exposed a main-task stack
overflow after `app_main()` returned. The test-only large ENP objects were moved
to static storage. The corrected run passed with no stack-overflow report. This
change is consistent with the project-wide static-allocation policy.

## Next step

After E2-A passes on hardware, E2-B will replace the controlled transport adapter with the existing ESP-NOW transport implementation and validate the same context -> neighbor -> routing-data-path boundary against a real peer.
