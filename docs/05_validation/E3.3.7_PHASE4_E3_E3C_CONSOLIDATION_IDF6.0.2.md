# E3.3.7 Phase 4 / E3 — E3C Integration Consolidation

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** Hardware validation PASS; P4/E3 frozen

## Purpose

P4/E3 consolidates the already hardware-validated Phase 3 E3C receive-path behavior into the
reusable ENP data plane.

The E3C hardware test remains the acceptance reference:

```text
A -> B -> C DATA
C -> B -> A ACK

first ACK is lost
    |
A retransmits the same DATA transaction
    |
B suppresses duplicate DATA
    |
B forwards the cached ACK
    |
A -> DELIVERED
```

P4/E3 does not introduce route discovery or route repair.

## Production consolidation

`core/data/enp_data_plane.c` now owns:

- DATA duplicate suppression;
- ACK duplicate suppression;
- local/remote destination classification;
- non-local DATA forwarding;
- non-local ACK forwarding;
- bounded static cached-ACK storage;
- cached-ACK lookup by original DATA source + DATA packet sequence;
- cached-ACK recovery when a duplicate ACK-required DATA packet is received.

The cached ACK is associated with the original DATA identity:

```text
DATA identity = source logical address + DATA sequence
```

The ACK payload supplies the acknowledged DATA packet sequence and the ACK
destination supplies the original DATA origin.

The cache is:

- statically allocated;
- bounded to `ENP_DATA_PLANE_ACK_CACHE_SIZE`;
- time-limited;
- independent of the reliability transaction table;
- transport-independent.

This is important because a relay such as B does not own the originating
reliability transaction. Cached ACK recovery therefore belongs in the data
plane rather than in `enp_reliability`.

## Reliability boundary

The reliability layer continues to submit every transmission attempt through:

```c
enp_reliability_submit_fn
        |
        v
enp_routing_data_path_submit()
```

P4/E3 does not change the reliability transaction API.

Periodic retries are driven by the already frozen P4/E2 maintenance integration.

## Test application

The new integration test is:

```text
main/tests/2-E/E3.3.7_p4_E3_test_enp_three_node_reliability_main.c
```

The application no longer owns:

- DATA duplicate caches;
- ACK duplicate caches;
- DATA forwarding;
- ACK forwarding;
- cached ACK storage;
- cached ACK recovery;
- manual reliability ticking.

The application remains responsible for:

- test topology setup;
- route installation;
- transport receive queue;
- application-level DATA validation at C;
- application-level ACK construction at C;
- reliability result observation at A;
- controlled fault injection for the acceptance test.

## Fault injection

The consolidated P4/E3 hardware test deliberately drops the first ACK at A
before the packet enters the data plane. This provides a controlled ACK-loss
condition while allowing B's reusable data plane to cache and recover the ACK.

The earlier Phase 3 E3C test remains the reference validation for the stronger
condition where B itself deliberately drops the first ACK after receiving it.

Thus P4/E3 validates consolidation without changing the already validated E3C
acceptance behavior.

## Acceptance criteria

A successful P4/E3 hardware run must demonstrate:

1. A submits reliable DATA through routing.
2. B forwards DATA through the reusable data plane.
3. C delivers DATA exactly once.
4. C generates and routes one ACK.
5. The first ACK is intentionally lost before A's data-plane processing.
6. A retransmits the same reliability transaction.
7. B suppresses the duplicate DATA.
8. B recovers and forwards its cached ACK.
9. A receives the recovered ACK through the data plane and dispatcher.
10. Reliability reaches `DELIVERED`.
11. C still reports exactly one application delivery.
12. A reports exactly one retransmission.

## Explicit non-goals

P4/E3 does not implement:

- RERR;
- stale/lost next-hop recovery;
- route rediscovery;
- route repair;
- alternate-path selection;
- multi-path routing;
- larger-topology optimization.

Those remain routing-resilience work after Phase 4.
