# E3.3.7 Phase 3 / E3 — Reliability-to-Routing Integration Design Audit

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** Design audit complete; implementation not started

## 1. Purpose

This document records the API audit performed before implementing E3.3.7 Phase 3 / E3.
The purpose is to connect the already validated reliability layer to the already
validated routing DATA path without introducing a second submission abstraction or
coupling reliability to ESP-NOW.

## 2. Audited components

The current implementation was inspected for:

- `enp_reliability.h/.c` — Phase 1 reliability transaction manager;
- `enp_reliability_service.h/.c` — Phase 2 dispatcher ACK service;
- `enp_dispatcher.h/.c` — ACK dispatch and duplicate suppression boundary;
- `enp_routing_data_path.h/.c` — E1 routing DATA submission boundary;
- existing context, neighbor and ESP-NOW transport integration validated by E2-A/E2-B.

## 3. Existing reliability submission boundary

The reliability API already provides:

```c
typedef esp_err_t (*enp_reliability_submit_fn)(
        const enp_packet_t *packet,
        void *user_context);
```

and:

```c
bool enp_reliability_set_submit_callback(
        enp_reliability_submit_fn submit,
        void *user_context);
```

`enp_reliability_send()` uses this callback for the initial DATA transmission.
`enp_reliability_tick()` uses the same callback for retransmissions.

The reliability layer retains a static copy of the packet in its transaction table.

## 4. Existing routing submission boundary

The validated routing API is:

```c
esp_err_t enp_routing_data_path_submit(
        enp_routing_data_path_t *path,
        const enp_packet_t *packet);
```

It validates the packet, looks up the current ACTIVE route for the packet destination,
selects the current logical next hop, resolves that next hop to a transport address,
and submits the packet through `enp_transport_send()`.

The packet is not modified by origin submission.

## 5. Smallest integration extension

**No new reliability API is required.**

The existing reliability submit callback is already exactly the required
transport-independent integration boundary.

The initial E3 implementation should add only an integration adapter/callback that
maps:

```text
reliability submit callback
        |
        v
enp_routing_data_path_submit()
```

The adapter's `user_context` should contain the existing
`enp_routing_data_path_t` instance.

Conceptually:

```c
static esp_err_t reliability_submit_to_routing(
        const enp_packet_t *packet,
        void *user_context)
{
    enp_routing_data_path_t *path = user_context;
    return enp_routing_data_path_submit(path, packet);
}
```

The exact ownership and placement of this adapter will be determined by the E3 test
and integration layer; it must not be placed inside `enp_reliability.c`.

## 6. Why this is sufficient

The reliability layer already:

- owns the transaction;
- owns the static retransmission packet copy;
- preserves DATA transaction identity;
- calls the submit boundary for the initial attempt;
- calls the same submit boundary for retries.

The routing DATA path already:

- performs current route lookup for every submission;
- selects the current next hop;
- resolves logical next hop to transport address;
- submits through the transport abstraction.

Therefore a retransmission does not permanently bind the transaction to its original
next hop.

For example:

```text
Attempt 1:
    A -> B -> C

Route later changes:
    A -> E -> C

Attempt 2:
    reliability -> routing submit
                    -> current route
                    -> E
```

The transaction identity remains unchanged while routing may select a different path.

## 7. Route-failure boundary

The initial E3 integration does not implement automatic route repair.

If `enp_routing_data_path_submit()` returns `ESP_ERR_NOT_FOUND`, reliability must not
perform route-table manipulation itself.

Route invalidation, RERR processing, route discovery and route repair remain routing
responsibilities and will be addressed in the subsequent routing-resilience work.

This preserves:

```text
Reliability = transaction
Routing     = path
Transport   = physical transmission
```

## 8. Phase 2 dispatcher relationship

The Phase 2 dispatcher integration remains unchanged.

ACKs continue to enter through:

```text
Transport RX
    |
    v
ENP dispatcher
    |
    +--> duplicate suppression
    |
    v
reliability ACK service
    |
    v
enp_reliability_process_ack()
```

E3 only adds the DATA transmit direction:

```text
Application
    |
    v
enp_reliability_send()
    |
    v
reliability submit callback
    |
    v
enp_routing_data_path_submit()
    |
    v
enp_transport_send()
```

## 9. Hardware-independent E3 self-test scope

Before ESP-NOW integration, the self-test should prove:

1. reliability initializes;
2. routing data path initializes;
3. the reliability submit callback is connected to the routing path;
4. a reliable DATA transaction is submitted exactly once initially;
5. the routing path receives the original DATA unchanged;
6. a timeout causes a retry through the same callback;
7. the retry reaches routing again with the same DATA transaction identity;
8. an ACK can complete the transaction through the existing Phase 2 path;
9. no transport-specific code is required by reliability.

## 10. Deliberate non-goals

This E3 step does not implement:

- route discovery orchestration;
- RREQ/RREP changes;
- RERR changes;
- automatic route repair;
- neighbor failure detection changes;
- ESP-NOW-specific code in reliability;
- a new reliability submission API;
- a second routing abstraction;
- three-node failure testing.

## 11. Next implementation step

Create the smallest hardware-independent E3 integration test and adapter using the
existing reliability submit callback and `enp_routing_data_path_submit()`.

Only after that self-test passes should the same integration be exercised over the
already validated two-node ESP-NOW transport.
