# E3.3.7 Phase 3 / E3 — Reliability-to-Routing Integration

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** Hardware-independent self-test PASS; E3A frozen

## Purpose

E3 connects the existing E3.3.7 reliability transaction manager to the validated
routing DATA-path boundary.

The API audit confirmed that the existing reliability submit callback is already
the smallest suitable integration interface:

```c
bool enp_reliability_set_submit_callback(
        enp_reliability_submit_fn submit,
        void *user_context);
```

The callback is used by both `enp_reliability_send()` for the initial DATA
submission and `enp_reliability_tick()` for retransmissions.

No new reliability API is required for E3.

## Integration boundary

```text
Application
    |
    v
Reliability
    |
    | enp_reliability_submit_fn
    v
Routing DATA path
    |
    +-- current active route lookup
    +-- current next-hop selection
    +-- logical -> transport resolution
    +-- enp_transport_send()
    |
    v
Transport
```

The E3 test supplies a small adapter that calls:

```c
enp_routing_data_path_submit(path, packet);
```

Reliability remains transport-independent and does not inspect route entries,
neighbor entries or transport addresses.

## Retransmission and route changes

A reliability transaction owns its DATA packet and transaction identity. Routing
owns the path used for each transmission attempt.

Therefore an active transaction may observe different next hops between attempts:

```text
Attempt 1:
    A -> B -> C

route changes / is repaired

Attempt 2:
    A -> E -> C
```

The reliability transaction remains the same. The retransmission re-enters the
same routing submission interface, which performs a fresh route lookup.

This phase does not implement route failure detection, RERR generation, route
rediscovery or route repair. Those remain part of the later routing-resilience
work. E3 only proves that the integration boundary does not prevent those future
behaviours.

## Phase 2 ACK path

The existing dispatcher integration remains unchanged:

```text
ACK
 |
 v
Dispatcher
 |
 v
Reliability ACK service
 |
 v
enp_reliability_process_ack()
 |
 v
Transaction -> DELIVERED
```

E3 exercises this existing path in the self-test rather than creating another
ACK integration mechanism.

## Self-test scope

The hardware-independent self-test uses:

- the real reliability implementation;
- the real ENP context;
- the real neighbor table and logical-to-transport mapping;
- the real route table;
- the real routing DATA path;
- the existing dispatcher and reliability ACK service;
- a controlled transport adapter.

The test verifies:

1. reliability initialization and callback registration;
2. initial DATA submission through reliability -> routing -> transport;
3. current route selection to next hop B;
4. preservation of the original DATA transaction identity;
5. route update while the transaction is still waiting for an ACK;
6. retransmission through the same reliability callback;
7. fresh routing lookup selecting next hop E after the route update;
8. preservation of the DATA transaction identity across the retry;
9. ACK delivery through the existing dispatcher/reliability service;
10. exactly one reliability completion for the transaction;
11. safe handling of a duplicate ACK;
12. static lifetime of large ENP test objects.

## Deliberate non-goals

E3 does not add:

- ESP-NOW-specific code to reliability;
- route discovery orchestration;
- RREQ/RREP/RERR integration;
- route failure detection;
- automatic route repair;
- changes to the route-table API;
- changes to the routing DATA-path API;
- changes to the Phase 2 dispatcher ACK service;
- changes to duplicate suppression;
- dynamic allocation.

## First E3 self-test observation

The first hardware run of the prepared E3 self-test reached and passed all reliability-to-routing functional checks, including initial routing, route change, retransmission through the same reliability submit callback, ACK completion, and duplicate ACK handling.

The run nevertheless reported one test failure because the test initially assumed that `enp_context_init()` automatically registers the transport receive callback. The current `enp_context_init()` implementation validates that the transport provides `set_receive_callback`, but transport callback registration is performed explicitly through `enp_transport_set_receive_callback()`.

This is a test-harness issue, not a production routing or reliability failure. The E3 test has therefore been corrected to register its controlled transport receive callback explicitly through the existing transport API. No production ENP API was changed.

The corrected test was re-run and passed all checks. E3A is frozen.

## Next step

E3A is frozen. E3B validates the same integration over two real ESP32 nodes using the existing ESP-NOW transport. E3C then validates the three-node reliability path. The later

rediscovery using the already-established separation between reliability and
routing.
