## 3. Cleanup finding — pending-resource bound

The adapter originally repeated the E5D pending bound as a second literal:

```c
#define ENP_ROUTE_REPAIR_ADAPTER_MAX_PENDING 8U
```

The authoritative E5D coordinator already defines:

```c
ENP_ROUTE_REPAIR_MAX_PENDING
```

The adapter has therefore been cleaned up to derive its bounded pending capacity from the existing E5D contract:

```c
#define ENP_ROUTE_REPAIR_ADAPTER_MAX_PENDING ENP_ROUTE_REPAIR_MAX_PENDING
```

### Reason

This prevents the adapter from silently diverging from the frozen E5D resource bound if the coordinator configuration changes later.

This is a cleanup-only change. It does not alter current behaviour or capacity.

### R4-C

### Route table

The adapter does not introduce a new persistent route state.

## 5. Failed-next-hop audit

The failed-next-hop rule remains local to the active repair:

```text
active repair destination = D
failed next-hop = H

candidate RREP route:
    destination D + next-hop H  -> reject
    destination D + next-hop != H -> allow
```

The candidate is rejected before an ACTIVE route is installed.

The rule is not encoded in the RREQ/RREP wire payload.

---

## 6. Sequence-number audit

The adapter retains the existing STALE route sequence when starting repair.

A candidate RREP sequence must satisfy the active discovery's retained sequence requirement before the candidate route is installed.

This duplicate-looking check is intentional: R4-A performs final discovery correlation, but R4-C invokes the route-update callback before discovery completion. Therefore candidate route installation must not occur for an insufficient sequence.

No independent E5D sequence-number algorithm is introduced.

---

## 7. Discovery ownership audit

No parallel R4-A discovery is created.

## 8. Transport boundary audit

```text
enp_packet_init()
    -> populate route header
    -> copy routing payload
    -> enp_packet_seal()
    -> enp_transport_send()
```

No new routing-specific transport API is introduced.

The logical-next-hop-to-transport resolution remains callback-based and transport-independent.
