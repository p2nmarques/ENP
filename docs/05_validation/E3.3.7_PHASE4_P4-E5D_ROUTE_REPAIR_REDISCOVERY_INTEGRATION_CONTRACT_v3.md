# E3.3.7 PHASE 4 / P4-E5D
# ROUTE REPAIR / REDISCOVERY INTEGRATION CONTRACT

**Project:** ENP v0.2-r5  
**Protocol:** E3.3.7  
**Phase:** Phase 4  
**Item:** P4-E5D  
**Target:** ESP-IDF 6.0.2  
**Status:** **FROZEN — APPROVED CONTRACT / HARDWARE VALIDATED**  
**Scope:** Production route repair / rediscovery following transport-induced route invalidation

---

## 1. Purpose

P4-E5D defines the interface and architecture boundary for route repair and
rediscovery after a transport failure has caused an affected route to become
`STALE`.

P4-E5D builds directly on the frozen P4-E5C behaviour:

```text
ESP-NOW / transport TX result
          |
          v
   transport failure
          |
          v
 affected next-hop identified
          |
          v
 affected routes invalidated
          |
          v
        STALE
          |
          v
       P4-E5D
 route repair / rediscovery
```

The purpose of E5D is to restore a usable route when an alternative path can be
discovered, while preserving the existing routing, discovery and reliability
contracts.

The existing routing architecture remains authoritative for route discovery,
RREQ/RREP processing, route state management, route installation and bounded
discovery behaviour. P4-E5D therefore integrates those mechanisms rather than
creating a second routing protocol.

The routing data path remains the single production DATA-submission boundary.

## 3. Architectural position

The intended production path is:

```text
                     ENP Reliability
                           |
                           | DATA / retransmission
                           v
                  Routing Data Path
                           |
                           v
                      Route Lookup
                           |
                  +--------+--------+
                  |                 |
                ACTIVE             STALE
                  |                 |
                  v                 v
             normal TX         P4-E5D repair
                                    |
                                    v
                              R4 discovery
                                    |
                               RREQ / RREP
                                    |
                           +--------+--------+
                           |                 |
                        success           failure
                           |                 |
                           v                 v
                         ACTIVE       existing routing/
                                      discovery failure
                                      semantics
                           |
                           v
                    normal routing
```

The architectural progression is:

```text
E5B = observe real transport result
E5C = invalidate affected route
E5D = initiate / coordinate repair
R4  = perform route discovery
Route table = own route state
Routing data path = select and submit using the current route
Reliability = own the transaction and retransmission policy
```

P4-E5D does not create a second DATA-transmission path.

## 4. Ownership model

The following ownership boundaries are normative.

| Responsibility | Owner |
|---|---|
| ESP-NOW TX-result observation | Transport / E5B boundary |
| Transport-result normalization | Existing ENP transport boundary |
| Identification of affected next-hop from TX failure | E5C routing integration |
| Route invalidation | E5C / existing route-table integration |
| Persistent route state | Route table |
| Detection that a stale route requires repair | E5D |
| Repair request generation | E5D |
| Repair-operation coordination | E5D |
| RREQ/RREP generation and processing | R4 route discovery |
| Discovery timers / retry limits | Existing R4 discovery |
| Route installation | Existing route-table / routing architecture |
| Current next-hop selection | Routing data path |
| DATA submission | Routing data path |
| Reliability transaction identity | Reliability |
| Reliability retry accounting | Reliability |
| ACK correlation | Reliability |
| Transaction timeout | Reliability |
| Final delivery/failure result | Reliability |
| ESP-NOW API usage | Transport adapter only |

E5D must not assume ownership of responsibilities assigned to another
subsystem merely because repair requires coordination with that subsystem.

---

## 5. Scope

P4-E5D shall implement or integrate:

1. detection that a `STALE` route requires repair;
2. generation of a routing-level repair request;
3. coordination of a repair operation;
4. interaction with the existing R4 route-discovery mechanism;
5. failed-next-hop avoidance during repair;
6. duplicate repair suppression;
7. successful route restoration;
8. bounded repair-failure handling;
9. preservation of route metadata and sequence semantics;
10. compatibility with reliability retransmission;
11. preservation of ENP DATA transaction identity;
12. bounded/static resource usage;
13. safe interaction with the existing routing task/context model.

The scope is deliberately limited to the integration required to make an
already-invalidated route usable again.

---

## 6. Non-goals

P4-E5D shall not:

- modify the ENP wire format;
- redesign RREQ;
- redesign RREP;
- redesign RERR;
- replace the existing route table;
- replace the existing R4 discovery architecture;
- modify the ESP-NOW transport;
- modify the P4-E5B TX-result observation boundary;
- redefine the P4-E5C transport-failure interpretation;
- create a second reliability mechanism;
- create a second retransmission mechanism;
- change reliability transaction identity;
- change DATA sequence semantics;
- change duplicate suppression semantics;
- introduce transport-specific routing logic;
- create a second route-selection mechanism;
- silently introduce new route-table states;
- silently change existing discovery timers, retry limits, TTL rules or
  other routing-protocol parameters.

Any implementation issue requiring one of these changes shall stop implementation
at the affected boundary and trigger explicit architecture review.

## 7. E5C → E5D boundary

P4-E5C remains responsible for the transport-failure-to-route-invalidation
boundary:

```text
TX result
    |
    +-- SUCCESS
    |      |
    |      +--> no E5D repair trigger from this result
    |
    +-- FAILURE
           |
           v
      identify failed next-hop
           |
           v
      invalidate affected routes
           |
           v
         STALE
```

E5D consumes the resulting routing condition.

E5D shall not independently interpret ESP-NOW send results.

The intended separation is:

```text
E5B = observe
E5C = invalidate
E5D = repair
```

E5D therefore begins at the routing-level condition that a required route is
`STALE`, not at the ESP-NOW callback.

---

## 8. Repair trigger

The primary E5D trigger is:

> An existing route required for routing has entered `STALE` as a consequence
> of the established E5C failure-invalidation path.

Conceptually:

```text
ACTIVE route
     |
     | transport failure
     v
   STALE
     |
     | repair required
     v
 repair request
```

A route that is already `STALE` shall not cause an unlimited sequence of
independent repair operations.

A successful transport result shall not by itself trigger E5D repair.

A `STALE` route makes repair eligible; E5D initiates repair when the routing
system determines that a usable route is needed and the current route is
unavailable according to the existing route-state semantics.

---

## 9. Repair request semantics

A **repair request** is a routing-level event that indicates that a logical
destination currently lacks a usable route and requires route repair.

The conceptual information carried by a repair request is:

```text
Repair Request
--------------
destination
failed_next_hop (when known)
reason = route_stale
```

This is a **logical contract**, not a declaration that a particular C structure
or function already exists.

The repair request shall:

1. identify the logical destination requiring repair;
2. identify the failed next-hop when the failure path provides that information;
3. preserve sufficient information for R4 to avoid the failed next-hop;
4. be bounded and safe to queue or coalesce;
5. not contain ESP-NOW-specific types;
6. not create a new wire-format packet merely to represent the local repair
   request.

The exact C interface shall be determined only after the implementation audit
defined in Section 29.

Until that audit is complete, notation such as:

```text
repair(destination, failed_next_hop)
```

shall be treated as conceptual semantics rather than a pre-approved API.

---

## 10. Repair ownership

E5D owns the decision and coordination that a stale route requires repair.

A repair operation shall be associated with the **logical destination**, not merely
with one individual DATA packet.

Example:

```text
Destination = Node 12
Failed next-hop = Node 2
```

If several reliability retransmissions require Node 12 while repair is already
underway:

```text
DATA retry 1 ----+
DATA retry 2 ----+----> one logical repair operation
DATA retry 3 ----+
```

They must not produce uncontrolled parallel discovery operations such as:

```text
RREQ #1
RREQ #2
RREQ #3
```

for the same destination and applicable repair condition.

The existing R4 discovery mechanism remains the owner of outstanding discovery
state.

E5D must not duplicate R4's discovery-state machine merely to coordinate
multiple repair requests.

---

## 11. Failed-next-hop exclusion

When the failed next-hop is known, a repair shall exclude that next-hop from
the repaired path. When it is not known, repair shall follow the existing R4
discovery semantics.

Example:

```text
Before failure:

A ----> B ----> C
        ^
        |
      failed
```

A successful repair should seek an alternative such as:

```text
A ----> D ----> C
```

rather than:

```text
A ----> B ----> C
        ^
        |
      failed
```

The failed next-hop therefore becomes a repair constraint when it is known.

The precise representation of this exclusion must use the existing routing/R4
interfaces wherever possible.

The implementation audit must explicitly determine:

1. how the failed next-hop is represented;
2. how that information reaches R4;
3. whether R4 already supports next-hop exclusion;
4. whether a minimal interface extension is required;
5. whether such an extension preserves the frozen routing/discovery contract.

E5D must not invent a parallel route-identity or discovery mechanism merely to
implement next-hop exclusion.

---

## 12. R4 discovery integration

E5D shall use the existing R4 route-discovery architecture.

It shall not create an independent RREQ/RREP state machine.

The intended logical relationship is:

```text
P4-E5D
   |
   | repair request
   v
Existing R4 discovery
   |
   +-- RREQ
   |
   +-- forwarding
   |
   +-- RREP
   |
   v
Existing route-table integration
```

Therefore:

> E5D decides **when repair is needed**.

> R4 decides **how route discovery is performed**.

> The route table remains authoritative for persistent route state.

> The routing data path remains authoritative for current next-hop selection
> and DATA submission.

The exact interface between E5D and R4 is an implementation audit gate and must
not be assumed from conceptual diagrams.

---

## 13. Route-state semantics

E5D shall preserve the existing route-state model.

The contract shall not introduce a new persistent route-table state merely to
represent a repair operation.

The conceptual repair sequence is:

```text
ACTIVE
   |
   | transport failure / E5C invalidation
   v
 STALE
   |
   | repair / discovery
   v
 ACTIVE
```

If repair cannot produce a usable route, E5D shall use the **existing routing and
route-discovery failure semantics**.

E5D shall not introduce or depend upon an `INVALID` route state. If the
implementation audit discovers that the existing authoritative route-table
contract already defines such a state, its meaning shall be documented and
explicitly reviewed before E5D implementation proceeds.

Repair-operation state shall remain separate from persistent route state.

In particular, E5D shall not introduce a permanent `REPAIRING` state without
explicit architecture approval.

---

## 14. Successful repair

A repair is successful only when the routing system has obtained a valid route
to the requested destination through a usable next-hop according to the existing
route-table contract.

On successful repair:

```text
STALE
  |
  v
new valid route
  |
  v
ACTIVE
```

The repaired route shall use the normal route-table representation and normal
routing metadata.

E5D shall not create an E5D-specific route representation.

Route installation remains owned by the existing routing architecture.

---

## 15. Repair failure

If R4 cannot produce a usable route within the existing bounded
discovery/repair policy:

```text
STALE
  |
  v
repair attempts exhausted / unsuccessful
  |
  v
existing routing/discovery failure handling
```

E5D shall not introduce an unbounded repair loop.

The existing R4 discovery limits, retry policy, timers, TTL behaviour and route
failure semantics remain authoritative.

E5D shall not silently redefine those values.

The exact terminal behaviour shall be inherited from the existing routing
architecture and verified during the implementation audit.

---

## 16. RERR interaction

P4-E5D shall integrate with the existing routing architecture's RERR boundary.

It shall not invent a new RERR packet or wire format.

The conceptual relationship is:

```text
repair unsuccessful
       |
       v
existing routing failure handling
       |
       v
existing RERR behaviour where applicable
```

If the existing RERR implementation is not yet part of the production path,
E5D shall not create a parallel RERR subsystem merely for this phase.

The precise RERR propagation behaviour remains governed by the existing routing
protocol contract.

---

## 17. Multiple destinations

E5C can invalidate multiple routes sharing the same failed next-hop.

Example:

```text
Route A: D10 -> next-hop 2
Route B: D11 -> next-hop 2
Route C: D12 -> next-hop 3
```

After failure of next-hop 2:

```text
D10 -> STALE
D11 -> STALE
D12 -> ACTIVE
```

E5D shall preserve this isolation.

Repair is logically destination-specific:

```text
D10 -> repair(D10)
D11 -> repair(D11)
```

Implementation may reuse an existing R4 discovery operation where the routing
architecture permits this.

However, the critical invariant is:

> All and only the destinations affected by the failure receive appropriate
> repair handling.

E5D shall not assume that all affected destinations must use the same repaired
route.

---

## 18. Duplicate repair suppression

Multiple reliability transmissions may discover that the same destination
currently has no usable route.

Example:

```text
DATA retry 1 ----+
DATA retry 2 ----+----> one logical repair operation
DATA retry 3 ----+
```

They must not create uncontrolled parallel discovery operations for the same
destination and repair condition.

The ownership boundary is:

```text
E5D
  |
  | coordinates repair requests
  v
R4
  |
  | owns outstanding discovery state
  v
RREQ / RREP
```

If R4 already provides discovery suppression, E5D shall reuse it rather than
creating a second suppression mechanism.

If R4 does not provide the required suppression semantics, that gap must be
identified during the Section 29 audit before implementation.

---

## 19. Repeated failures

Repeated failure reports for an already-stale route shall be idempotent with
respect to route state.

For example:

```text
ACTIVE
   |
 failure #1
   v
 STALE
   |
 failure #2
   v
 STALE
```

A repeated failure shall not:

- corrupt the route;
- reset route metadata;
- arbitrarily change route sequence information;
- create an uncontrolled second repair;
- create duplicate reliability transactions.

E5D builds on the E5C stale-route behaviour and shall not replace it.

---

## 20. Unrelated routes

A repair triggered by one failed next-hop shall not invalidate or otherwise
corrupt unrelated active routes.

Example:

```text
failed next-hop = 2

D10 -> next-hop 2 -> STALE
D11 -> next-hop 2 -> STALE
D12 -> next-hop 3 -> ACTIVE
```

Repair of D10/D11 must not change D12 unless a normal routing-protocol event
independently changes D12.

This preserves the route-isolation property established at the E5C boundary.

---

## 21. Reliability integration

Reliability remains responsible for the end-to-end transaction.

Consider:

```text
A -> B -> C
```

with a reliability transaction:

```text
T = ENP DATA transaction
```

If B fails and E5C makes the route stale:

```text
A -> B -> C
       |
       v
    failure
       |
       v
     STALE
```

E5D repairs the route:

```text
A -> D -> C
```

The reliability transaction remains the same logical transaction.

E5D therefore integrates with reliability rather than replacing reliability's
transaction machinery.

Reliability retains ownership of:

- transaction identity;
- retransmission count;
- ACK correlation;
- transaction timeout;
- final delivery/failure result.

The routing layer retains ownership of route selection.

---

## 22. Transaction identity

Route repair shall not change reliability transaction identity.

Conceptually:

```text
transaction identity before repair
             ==
transaction identity after repair
```

E5D shall not:

- create a new reliability transaction;
- reset reliability transaction identity;
- silently restart the transaction;
- terminate the transaction solely because repair started.

The original reliability transaction remains alive according to the existing
reliability contract.

---

## 23. Retransmission after repair

After successful repair, reliability retransmission shall re-enter the normal
routing data path.

The intended path is:

```text
Reliability
    |
    | retransmission
    v
Routing Data Path
    |
    | current route lookup
    v
repaired next-hop
    |
    v
Transport
```

E5D shall not create a special DATA transmission path.

The reliability transaction continues to own retry timing and retry accounting.

The routing data path selects the current usable route.

---

## 24. DATA identity preservation

E5D shall not modify the existing ENP DATA transaction merely because a route is
being repaired.

The important invariant is:

```text
same ENP DATA transaction identity
new usable route
```

The term **ENP DATA transaction identity** is deliberate. It does not require
the physical ESP-NOW transmission frame to be byte-for-byte identical between
attempts.

The reliability layer remains the owner of the original DATA transaction and
its retransmission semantics.

Route repair does not reset the reliability retransmission timer unless the
existing reliability contract explicitly defines such behaviour.

This preserves the existing reliability and duplicate-suppression architecture.

---

## 25. Concurrency

The implementation must safely handle concurrent:

- reliability transmission requests;
- route invalidation;
- repair requests;
- RREQ/RREP processing;
- repeated transport failures;
- route-table lookups;
- route installation;
- completion of an existing repair operation.

E5D shall not modify route state concurrently without the synchronization
required by the existing routing implementation.

E5D shall not introduce a second synchronization model for route state.

Where multiple execution contexts can request repair for the same destination,
the implementation must provide bounded and deterministic coordination.

---

## 26. Callback/task context

E5D must respect the existing transport and routing callback/task boundaries.

Route repair and RREQ/RREP processing must not be performed as lengthy or
blocking work directly inside an ESP-NOW transport callback.

The preferred architecture is:

```text
transport callback
       |
       v
bounded routing event
       |
       v
routing / repair task context
       |
       v
route repair / R4 discovery
```

This preserves the asynchronous transport boundary established by E5B/E5C.

The actual task/queue interface shall reuse the existing project context model
where possible.

---

## 27. Resource policy

E5D shall follow the existing ENP bounded/static resource policy.

E5D shall not introduce unbounded:

- dynamic repair lists;
- dynamically growing discovery queues;
- retry arrays;
- per-packet heap-owned repair contexts;
- asynchronous heap-owned repair transactions;
- dynamically growing route-repair state.

Any additional E5D state must have an explicitly bounded capacity.

The exact capacity shall be derived from the existing routing architecture and
implementation constraints rather than invented independently by the test.

---

## 28. Transport independence

E5D shall not depend directly on ESP-NOW APIs.

The routing implementation shall operate using ENP-level transport and routing
interfaces.

The following remain confined to the transport adapter:

```text
esp_now_send()
esp_now_send_status_t
ESP-NOW peer management
ESP-NOW-specific callbacks
```

The routing repair mechanism shall not include ESP-NOW-specific types merely to
perform route repair.

The transport implementation remains replaceable without redesigning E5D's
repair semantics.

---

## 29. Implementation audit gates

**No E5D implementation should begin until the following audit questions have
been answered against the actual production source tree.**

### E5D-A01 — Route-state audit

Verify the authoritative route-table states actually implemented by the
production routing code.

Confirm specifically that E5D does not assume an `INVALID` or `REPAIRING`
state unless such a state is already part of the authoritative contract.

**Required result:** exact route-state model documented.

### E5D-A02 — R4 API audit

Identify the actual production R4 discovery interfaces used to initiate and
complete route discovery.

Determine whether the existing interface already provides the semantics needed
for:

```text
repair(destination, failed_next_hop)
```

This notation is conceptual until the audit identifies the real interface.

**Required result:** actual API/function/context identified.

### E5D-A03 — Failed-next-hop exclusion audit

Determine exactly how a failed next-hop can be supplied to R4 and how R4 can
exclude it from the repair path.

**Required result:** existing interface reused, or an explicitly reviewed
minimal extension identified.

### E5D-A04 — Duplicate-discovery audit

Determine whether R4 already suppresses duplicate discovery operations for the
same destination.

**Required result:** existing suppression reused, or a bounded integration
mechanism explicitly defined.

### E5D-A05 — Route-installation audit

Determine which production component installs a successful RREP-derived route
and which component changes the route to its active/usable state.

**Required result:** E5D does not duplicate route installation.

### E5D-A06 — Repair-failure audit

Determine the actual production behaviour when discovery exhausts its bounded
attempts or cannot produce a usable route.

**Required result:** E5D uses the existing failure semantics and does not invent
a new terminal route state.

### E5D-A07 — Sequence/metadata audit

Determine which existing routing component owns sequence-number comparison and
route metadata selection during RREP processing.

**Required result:** E5D does not introduce a second ordering algorithm.

### E5D-A08 — Reliability integration audit

Confirm that a reliability retransmission after successful repair naturally
re-enters the existing routing data path.

**Required result:** no E5D-specific DATA transmission path.

### E5D-A09 — Context/concurrency audit

Identify the existing tasks, queues, callbacks and synchronization protecting
route state and discovery state.

**Required result:** E5D extends the existing execution model rather than
creating a parallel concurrency model.

### E5D-A10 — Resource audit

Identify the existing bounded/static resource limits relevant to route
discovery and repair.

**Required result:** any E5D state has an explicitly bounded capacity.

### Implementation gate

If any audit reveals that the contract requires a change to a frozen interface,
a second discovery implementation, a new persistent route state, a transport
dependency, or a new reliability mechanism, implementation shall stop and the
E5D contract shall be revised before coding continues.

## 30. Controlled validation

Before hardware validation, the controlled self-test shall demonstrate at
minimum:

### E5D-T1 — Repair trigger

```text
ACTIVE
   |
   v
STALE
   |
   v
repair requested
```

### E5D-T2 — Successful repair

```text
STALE
   |
   v
controlled R4 discovery success
   |
   v
new route installed
   |
   v
ACTIVE
```

### E5D-T3 — Failed-next-hop exclusion

Verify that the repaired route does not select the failed next-hop.

### E5D-T4 — Unrelated route preservation

Verify:

```text
affected route   -> repaired
unaffected route -> unchanged
```

### E5D-T5 — Duplicate repair suppression

Multiple repair requests for the same destination and condition result in one
bounded repair operation.

### E5D-T6 — Repeated failure safety

Repeated failure events do not corrupt route or repair state.

### E5D-T7 — Repair failure

Discovery exhaustion produces the existing defined routing/discovery failure
semantics without introducing a new route-table state.

### E5D-T8 — Reliability identity

A reliability transaction retains the same ENP DATA transaction identity before
and after route repair.

### E5D-T9 — Normal retransmission path

Retransmission after repair enters the normal routing data path rather than an
E5D-specific transmission path.

### E5D-T10 — Sequence/metadata integrity

Successful repair obeys the existing routing sequence-number and route-metadata
rules.

Controlled validation is complete only when all mandatory controlled criteria
pass.

## 31. Hardware validation

Hardware validation is a separate evidence level from controlled validation.

P4-E5D becomes **HARDWARE VALIDATED** only after real ESP32 hardware
demonstrates the complete production behaviour.

The hardware validation shall use, as applicable:

```text
real ESP32 hardware
+
real ESP-NOW
+
production transport
+
production routing data path
+
production route table
+
production R4 discovery
+
production repair integration
+
production reliability path
```

The behavioural requirement is an initial usable route followed by a real
failure of the original next-hop and successful repair through a distinct
usable path.

Conceptually:

```text
Initial path:

A -> B -> C

B becomes unavailable

Repair:

A -> D -> C
```

The exact number of ESP32 nodes, physical topology, failure mechanism and
instrumentation shall be defined in the separate E5D hardware-validation test
document after the implementation audit.

This contract deliberately does **not** freeze a 3-node or 4-node equipment
requirement.

The hardware validation shall demonstrate, at minimum:

1. the initial route is usable;
2. real DATA uses the initial route;
3. the original next-hop becomes unavailable;
4. real transport failure is observed;
5. E5C changes the affected route to `STALE`;
6. E5D initiates repair;
7. R4 discovery establishes an alternate route;
8. the repaired route becomes usable/`ACTIVE` according to the existing
   route-state contract;
9. the failed next-hop is not selected;
10. unrelated routes remain unaffected;
11. the original ENP DATA transaction identity is preserved;
12. reliability retransmission uses the repaired route;
13. the destination receives DATA according to the existing reliability
    contract;
14. the ACK returns through the repaired routing topology where applicable;
15. repair does not create duplicate application delivery.

Hardware validation must use the production implementation rather than a
test-specific replacement for routing or discovery.

| E5D-HV08 | Repaired route becomes usable/`ACTIVE` according to the existing contract |
| E5D-HV09 | Failed next-hop is not selected |
| E5D-HV10 | Unrelated routes remain unaffected |
| E5D-HV11 | ENP DATA transaction identity is preserved |
| E5D-HV12 | Reliability retransmission uses the repaired route |
| E5D-HV13 | Destination receives DATA according to the existing reliability contract |
| E5D-HV14 | ACK recovery succeeds where required by the test |
| E5D-HV15 | No duplicate application delivery is produced |

Hardware-validation evidence shall be recorded separately from the controlled
self-test evidence.

## 33. Freeze criteria

P4-E5D may be marked **FROZEN** only when:

1. the contract has been approved;
2. all implementation audit gates are resolved;
3. the approved contract has been implemented;
4. the existing R4 discovery architecture is used as defined;
5. the controlled self-test passes;
6. no forbidden ownership coupling has been introduced;
7. no frozen E5A/E5B/E5C interface has been silently changed;
8. the implementation is reproducible on ESP-IDF 6.0.2;
9. full-clean build validation passes;
10. the required hardware-validation acceptance criteria pass;
11. the documentation reflects the accepted implementation.

The E5D validation progression is:

```text
CONTROLLED VALIDATED
        |
        v
HARDWARE VALIDATED
        |
        v
FROZEN
```

The project must retain the distinction:

```text
VALIDATED
    !=
HARDWARE VALIDATED
```

and:

```text
FROZEN
    !=
HARDWARE VALIDATED
```

The final E5D status shall be determined from the actual evidence, not inferred
from code completion.

## 35. Final architecture

The intended E5D architecture is:

```text
                    +------------------+
                    |   Reliability    |
                    +--------+---------+
                             |
                         DATA / retry
                             |
                             v
                    +------------------+
                    | Routing Data     |
                    | Path             |
                    +--------+---------+
                             |
                         route lookup
                             |
                    +--------+--------+
                    |                 |
                  ACTIVE             STALE
                    |                 |
                    v                 v
                normal TX       P4-E5D repair
                                      |
                                      | repair request
                                      v
                               +-------------+
                               | R4 Discovery|
                               +------+------+
                                      |
                                   RREQ/RREP
                                      |
                              +-------+-------+
                              |               |
                           success          failure
                              |               |
                              v               v
                           Route          existing routing/
                         installation     discovery failure
                              |
                              v
                           ACTIVE
                              |
                              v
                       normal routing
```

The ownership model remains:

```text
Transport       -> reports transport result
E5C             -> invalidates affected route
E5D             -> initiates / coordinates repair
R4 Discovery    -> performs route discovery
Route table     -> owns persistent route state
Routing path    -> selects current next-hop and submits DATA
Reliability     -> owns transaction and retransmission
```

The routing data path remains the single production DATA submission boundary.

No second routing protocol, second route-selection mechanism, transport-specific
repair mechanism or E5D-specific DATA transmission path is permitted.

## 36. Contract decision

The P4-E5D contract establishes:

> **A transport failure may make a route stale; E5D initiates and coordinates
> repair; R4 performs route discovery; the route table remains authoritative
> for route state; and reliability transaction identity remains unchanged
> throughout repair and retransmission.**

The existing transport, routing, route-table, R4 discovery and reliability
interfaces remain authoritative.

The following are deliberately **not** assumed by this contract until the
implementation audit proves them:

- a particular C API such as `repair(destination, failed_next_hop)`;
- a persistent `INVALID` route state;
- a persistent `REPAIRING` route state;
- a specific repair timer or retry count;
- a specific hardware topology or number of ESP32 nodes.

The implementation audit in Section 29 is therefore a mandatory architecture
gate before implementation.

**P4-E5D contract status: FROZEN — APPROVED CONTRACT.**
