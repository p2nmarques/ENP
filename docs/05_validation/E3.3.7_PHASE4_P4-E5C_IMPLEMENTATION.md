## 1. Scope

P4-E5C consumes the frozen P4-E5B ENP transport send-result callback and
applies a non-`ESP_OK` asynchronous transmission result at the routing
data-path boundary.

For a failed transport destination, the routing data path:

1. receives the failed transport address;
2. examines ACTIVE routes;
3. resolves each route's logical `next_hop` through the existing
   `enp_routing_resolve_transport_fn` boundary;
4. compares the resolved transport address with the failed address;
5. transitions every matching route from `ACTIVE` to `STALE`.

Successful (`ESP_OK`) results do not invalidate routes.

## 2. Frozen ownership boundary

```text
ESP-NOW / transport
        ↓
P4-E5B send-result callback
        ↓
P4-E5C routing data path
        ↓
existing route-table invalidation
        ↓
ACTIVE → STALE
```

The transport layer remains protocol-agnostic.

The routing layer remains responsible for interpreting a failed transport
destination in terms of logical ENP next hops.

The route table remains the sole owner of route state.

## 3. Implementation

P4-E5C uses the existing:

```c
enp_transport_send_result_callback_t
enp_transport_set_send_result_callback()
enp_routing_resolve_transport_fn
enp_route_table_invalidate()
```

No new transport-to-routing API, reverse MAC-to-node API, second route table,
or new route state was introduced.

The implementation invalidates **all ACTIVE routes** whose logical next hop
resolves to the failed transport destination.

An already `STALE` or `INVALID` route is not modified by a repeated failure.

The route sequence is preserved by the `ACTIVE → STALE` transition.

## 5. What is deliberately not validated by this record

This controlled validation does **not** claim real ESP-NOW hardware validation.

It does not validate:

- real ESP-NOW TX failure observation;
- RERR generation or processing;
- RREQ/RREP;
- route discovery;
- route repair;
- alternate-path selection;
- reliability retransmission or recovery.

Those remain separate architectural boundaries.
