## Purpose

Expand the Step-3 controlled self-test beyond the already validated happy path and exercise the principal failure and lifecycle boundaries before hardware validation.

## Additional controlled cases

### 1. Old / insufficient RREP sequence

A candidate RREP with a destination sequence lower than the retained discovery sequence is rejected.

Expected behaviour:

- no ACTIVE route is installed;
- discovery remains active;
- a later acceptable RREP may still complete the discovery.

### 2. Duplicate repair while active

A second repair request for the currently active destination is submitted while the first discovery is active.

Expected behaviour:

- the E5D request reaches the Step-3 consume boundary;
- the adapter does not create a second active discovery;
- no duplicate pending repair is retained.

### 3. Multiple affected destinations

A second affected destination is submitted while the first repair is active.

Expected behaviour:

- the second destination is retained in the bounded adapter pending set;
- it does not interrupt the active discovery;
- it becomes active only after the first repair completes or fails.

### 4. Discovery timeout and retransmission

The active discovery deadline is advanced directly through the controlled clock and `enp_route_repair_adapter_tick()`.

Expected behaviour:

- each permitted retry retransmits the existing RREQ;
- no new RREQ identity is invented for a retry;
- after `ENP_MAX_RETRIES`, the discovery enters FAILED;
- the failed destination does not become ACTIVE.

### 5. Queued destination activation

After the first discovery fails, the queued second destination is started automatically.

Expected behaviour:

- exactly one initial RREQ is transmitted for the queued destination;
- its destination and retained sequence are preserved;
- the second repair has an independent active lifecycle.

### 6. Unrelated route isolation

An unrelated active route remains unchanged through all failure, retry and repair operations.

## Combined controlled flow

```text
E5D repair A
    |
    v
R4 discovery A ACTIVE
    |
    +-- duplicate A -> suppressed
    |
    +-- repair B -> queued
    |

    |

    |
    v
A FAILED / remains STALE
    |
    v
B starts automatically
    |
    v
valid RREP B
    |
    v
B ACTIVE
```

## Acceptance

The expanded controlled test passes only when all cases above pass and the existing Step-3 happy-path checks remain passing.

Hardware validation remains a separate evidence level and is not part of this test.


## Final controlled-validation result

The expanded Step-3 controlled test passed all defined lifecycle cases:

- stale route sequence 7 was carried into R4-A;
- initial RREQ was transmitted exactly once;
- failed-next-hop RREP candidate was rejected;
- allowed alternative next-hop RREP candidate completed discovery;
- repaired route became ACTIVE using next-hop 3;
- destination sequence was preserved;
- duplicate repair while active was suppressed;
- a second affected destination was queued;
- old/insufficient RREP sequence was rejected without completing discovery;
- route A exhausted the configured maximum retries and failed without an ACTIVE route;
- queued route B became active after route A failure;
- route B independently completed through next-hop 3;
- unrelated routes remained unchanged.
