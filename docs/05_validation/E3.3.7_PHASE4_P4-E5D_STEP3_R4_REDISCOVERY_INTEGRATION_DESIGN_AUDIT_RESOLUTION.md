# E3.3.7 PHASE 4 / P4-E5D

# STEP 3 --- R4 ROUTE REDISCOVERY INTEGRATION DESIGN / AUDIT RESOLUTION

**Status:** PROPOSED --- READY FOR REVIEW\
**Baseline:** `ENP-0.2-r5(20260821-175726)`\
**Contract:**
`E3.3.7_PHASE4_P4-E5D_ROUTE_REPAIR_REDISCOVERY_INTEGRATION_CONTRACT_v3.md`\
**Target:** ESP-IDF 6.0.2

------------------------------------------------------------------------

## 1. Purpose

This document resolves the implementation boundary between the already
validated P4-E5D repair coordinator and the existing R4 route-discovery
infrastructure.

It is an implementation-design and audit-resolution document. It does
not freeze implementation and does not change the frozen E5D
architecture contract.

The objective is to define how an E5D repair request shall initiate and
complete an existing R4 discovery transaction while preserving:

-   existing R4 ownership;
-   existing RREQ/RREP processing;
-   existing route-table semantics;
-   failed-next-hop exclusion;
-   bounded resources;
-   transport independence;
-   E5C/E5D ownership boundaries.

------------------------------------------------------------------------

## 2. Baseline evidence

The actual baseline contains:

-   `enp_route_repair.*` --- E5D Step 1/2 coordinator;
-   `enp_route_discovery.*` --- R4-A discovery state machine;
-   `enp_rreq_processor.*` --- R4-B RREQ processing;
-   `enp_rrep_processor.*` --- R4-C RREP processing;
-   `enp_route_table.*` --- route state and route metadata;
-   `enp_routing_data_path.*` --- E5C transport-failure integration.

E3.2.2, E3.2.3 and E3.2.4 have already been regression-tested
successfully before this design step.

------------------------------------------------------------------------

## 3. Actual R4 interface

The existing R4-A entry point is:

``` c
bool enp_route_discovery_start(
    enp_route_discovery_t *discovery,
    enp_discovery_destination_t destination,
    uint32_t route_request_id,
    uint32_t destination_sequence,
    uint8_t ttl,
    uint32_t now_ms);
```

R4-A also exposes:

``` c
enp_route_discovery_on_rrep(...)
enp_route_discovery_on_timeout(...)
enp_route_discovery_is_active(...)
enp_route_discovery_state(...)
```

R4-A deliberately does not:

-   transmit RREQ/RREP packets;
-   access the transport;
-   modify the route table;
-   implement RREQ/RREP processing;
-   allocate dynamically;
-   depend on FreeRTOS.

Therefore E5D shall **not** bypass these ownership rules.

------------------------------------------------------------------------

## 4. Architectural decision

E5D shall integrate with R4 through an **orchestration
adapter/context**, not by adding a new conceptual public API such as:

``` c
repair(destination, failed_next_hop)
```

to R4-A.

The adapter owns the integration context required to connect:

``` text
E5D repair request
        |
        v
R4 discovery transaction
        |
        +--> RREQ generation/processing
        |
        +--> RREP processing
        |
        v
route-table integration
        |
        v
E5D completion/failure
```

The adapter may call the existing `enp_route_discovery_start()` and the
existing R4 processing interfaces.

No RREQ/RREP wire-format change is required by this design.

------------------------------------------------------------------------

## 5. Ownership

  -----------------------------------------------------------------------
  Responsibility                      Owner
  ----------------------------------- -----------------------------------
  Detect transport failure            E5B / transport

  Mark affected route `STALE`         E5C

  Generate repair request             E5C → E5D

  Suppress duplicate repair requests  E5D

  Queue/execute repair work           E5D

  Maintain repair context             E5D orchestration

  Own active R4 discovery transaction R4-A through integration context

  Generate/process RREQ               R4-B / surrounding routing
                                      integration

  Generate/process RREP               R4-C / surrounding routing
                                      integration

  Install/refresh route               Existing route-table integration

  Select route freshness              Existing route-table contract

  Transport access                    Transport adapter only

  Reliability transaction identity    Reliability layer
  -----------------------------------------------------------------------

E5D must not absorb R4-A, R4-B, R4-C or route-table ownership.

------------------------------------------------------------------------

## 6. Repair-context representation

The E5D repair request remains:

``` c
typedef struct {
    enp_route_destination_t destination;
    enp_route_destination_t failed_next_hop;
} enp_route_repair_request_t;
```

The `failed_next_hop` is **repair context**, not an RREQ/RREP wire
field.

The context must remain available throughout the repair transaction:

``` text
repair request
    destination = D
    failed hop  = H
          |
          v
R4 discovery context
          |
          v
candidate route evaluation
```

The exact C representation of the adapter context is an implementation
detail and is not added to R4-A's public discovery object unless
required by implementation.

------------------------------------------------------------------------

## 7. Failed-next-hop exclusion

The current R4 APIs do not provide a forbidden-next-hop parameter.

Therefore failed-next-hop exclusion cannot be achieved by simply
calling:

``` c
enp_route_discovery_start(...)
```

with an additional argument.

The exclusion shall be enforced at the **route-candidate integration
boundary** where the actual next-hop is known.

The required rule is:

> During repair of destination D caused by failed next-hop H, a
> candidate route whose next-hop is H shall not be accepted as the
> repaired route.

This is a routing integration constraint, not a protocol-wire change.

If the existing route-processing callbacks cannot express this
constraint without ambiguity, an explicit adapter-level route-candidate
policy interface shall be added. It must remain outside the RREQ/RREP
payload definitions.

------------------------------------------------------------------------

## 8. Discovery transaction ownership

R4-A currently supports one active discovery transaction per discovery
object.

E5D shall therefore serialize actual R4 discovery execution.

The E5D queue may contain multiple pending destinations:

``` text
D1
D2
D3
```

but the R4-A transaction is executed as:

``` text
D1 -> COMPLETE/FAILED
             |
             v
D2 -> COMPLETE/FAILED
             |
             v
D3 -> COMPLETE/FAILED
```

E5D shall not create parallel R4-A transactions merely by creating
multiple discovery objects.

The implementation may maintain bounded repair entries, but only one
repair shall be designated as the active R4 discovery operation unless a
later approved architecture explicitly changes this rule.

------------------------------------------------------------------------

## 9. Discovery start

When an E5D request reaches the repair execution context:

1.  confirm the destination is still a repair candidate;
2.  confirm no identical repair is already active;
3.  obtain the current destination sequence according to the existing
    route-table contract;
4.  allocate a new local `route_request_id`;
5.  call `enp_route_discovery_start()`;
6.  preserve the failed-next-hop in the adapter repair context.

E5D shall not invent a new discovery timeout. R4-A continues to own its
existing discovery timeout/retry semantics.

------------------------------------------------------------------------

## 10. RREQ/RREP integration

The adapter shall use the existing R4-B and R4-C interfaces.

R4-B continues to learn reverse routes using the actual immediate
sender.

R4-C continues to:

1.  update/refresh the forward route through its existing callback;
2.  determine whether the RREP reached the discovery originator;
3.  complete the R4 discovery through its existing discovery-complete
    callback.

E5D shall not duplicate these mechanisms.

------------------------------------------------------------------------

## 11. Successful repair

A repair is successful only when both conditions are satisfied:

1.  the R4 discovery transaction reaches `COMPLETE`;
2.  the resulting route-table state contains a usable `ACTIVE` route for
    the requested destination whose next-hop is not the failed next-hop.

The second condition is essential because R4-A completion alone only
proves that an acceptable RREP was correlated with the discovery
transaction.

E5D shall then:

-   clear the active repair context;
-   release the destination from E5D pending state;
-   expose completion to the next integration layer;
-   allow the next queued repair to execute.

------------------------------------------------------------------------

## 12. Repair failure

If R4 exhausts its existing bounded retry mechanism and enters `FAILED`:

-   the repaired route shall not be manufactured;
-   the route shall remain `STALE` unless an existing route-table rule
    independently changes it;
-   E5D shall mark the repair operation failed;
-   the failed-next-hop context shall not be converted into a new route;
-   unrelated routes shall remain unaffected.

No new route state is introduced.

------------------------------------------------------------------------

## 13. Repeated failures

If the same destination becomes a repair candidate again while its
previous repair is active, E5D shall suppress the duplicate according to
the existing Step-1/Step-2 pending-destination rule.

If a repair has completed or failed and a later transport failure
generates a new repair request, that is a new repair transaction.

The implementation must not indefinitely suppress a destination after
completion/failure.

------------------------------------------------------------------------

## 14. Multiple destinations sharing a failed next-hop

E5C may produce:

``` text
D1 -> H
D2 -> H
D3 -> H
```

as independent repair events.

E5D shall retain each destination as an independent repair request.

The failed-next-hop may be identical across requests, but each
destination has its own repair outcome.

A successful repair of D1 must not automatically mark D2 or D3 repaired.

------------------------------------------------------------------------

## 15. Duplicate discovery protection

E5D duplicate suppression and R4 discovery-state protection are
complementary.

E5D prevents duplicate repair requests for the same destination.

R4-A prevents concurrent starts on the same discovery object.

Neither layer should be removed in favour of the other.

------------------------------------------------------------------------

## 16. Completion/failure callback boundary

The R4 integration adapter shall provide an explicit completion/failure
boundary back to E5D.

Conceptually:

``` c
repair_discovery_complete(context, destination, sequence);
repair_discovery_failed(context, destination);
```

These are adapter-level semantics, not additions to the R4 wire
protocol.

The callback must execute in the controlled routing/repair task context
rather than inside an ESP-NOW callback.

------------------------------------------------------------------------

## 17. Concurrency and callback context

The existing E5C notification is generated from the transport
send-result callback context.

E5C therefore only submits the bounded E5D repair request.

E5D performs the actual repair work in its dedicated task context.

The R4 processing path must not be invoked directly from the transport
callback.

The resulting execution model is:

``` text
ESP-NOW callback
      |
      v
E5C
      |
      v
E5D queue
      |
      v
E5D task
      |
      v
R4 orchestration
```

This preserves the callback/task boundary established by E5A/E5B/E5C.

------------------------------------------------------------------------

## 18. Resource policy

All Step-3 state shall be bounded.

At minimum:

-   one bounded E5D repair queue;
-   one bounded E5D pending registry;
-   one active R4 discovery context;
-   bounded R4 retry count;
-   no dynamic allocation.

The implementation shall document the maximum number of simultaneously
retained repair requests.

------------------------------------------------------------------------

## 19. Reliability boundary

Step 3 shall not modify reliability.

The only permitted interaction at this stage is notification that a
route is being repaired or has become available again, if required by
the existing reliability architecture.

Reliability retransmission, transaction identity and DATA identity
remain owned by the reliability layer.

A repaired route must not create a new ENP DATA transaction identity.

------------------------------------------------------------------------

## 20. Implementation audit gates

Before coding, the following gates must be satisfied:

### E5D-S3-A01 --- R4 start adapter

Identify the exact production context that owns the
`enp_route_discovery_t` instance.

### E5D-S3-A02 --- RREQ transmission integration

Identify the existing production/test integration point that turns R4
discovery state into an RREQ transmission.

### E5D-S3-A03 --- RREP completion integration

Identify the existing callback/context that calls
`enp_route_discovery_on_rrep()` and completes R4.

### E5D-S3-A04 --- Failed-next-hop exclusion

Identify the exact point at which a candidate next-hop is available and
define the minimal adapter-level exclusion mechanism.

### E5D-S3-A05 --- Route installation

Identify the existing route-table callback used by R4-C and prove that
E5D can verify the resulting next-hop.

### E5D-S3-A06 --- Timeout ownership

Confirm that R4-A continues to use the resolved
`ENP_DISCOVERY_TIMEOUT_MS` configuration and that E5D does not introduce
another discovery timeout.

### E5D-S3-A07 --- Active discovery ownership

Identify the single active R4 discovery context and its lifecycle.

### E5D-S3-A08 --- Execution context

Prove that R4 discovery initiation and completion execute outside the
ESP-NOW callback context.

### E5D-S3-A09 --- Resource bound

Define the exact bounded repair capacity.

### E5D-S3-A10 --- No frozen-interface regression

Confirm that E5A, E5B, E5C, R4 and reliability public contracts remain
unchanged unless a separately approved interface extension is required.

**Implementation gate:** all ten gates must be resolved before Step-3
implementation is frozen.

------------------------------------------------------------------------

## 21. Controlled validation plan

The first Step-3 controlled test shall validate only the R4
orchestration boundary.

### S3-T1 --- Start

E5D repair request causes exactly one R4 discovery transaction to start.

### S3-T2 --- Active ownership

A second repair request for the same destination does not create a
second R4 transaction.

### S3-T3 --- Successful discovery

A controlled RREP completes the active discovery.

### S3-T4 --- Route verification

The resulting route is `ACTIVE` and uses an allowed next-hop.

### S3-T5 --- Failed-next-hop exclusion

A candidate using the failed next-hop is rejected and an alternative
candidate is accepted.

### S3-T6 --- Discovery failure

R4 failure leaves the destination route `STALE` and completes the E5D
repair with failure.

### S3-T7 --- Multiple destinations

Multiple pending repair destinations are serviced serially.

### S3-T8 --- Unrelated route

An unrelated route remains unchanged.

### S3-T9 --- Repeated failure

Repeated failure does not create duplicate active repairs.

### S3-T10 --- Context

All R4 repair operations occur in the E5D/routing task context.

------------------------------------------------------------------------

## 23. Freeze criteria

Step 3 may be frozen only when:

1.  all implementation audit gates pass;
2.  the exact R4 orchestration boundary is documented;
3.  failed-next-hop exclusion is implemented without changing the
    RREQ/RREP wire format;
4.  controlled validation passes;
5.  no E5A/E5B/E5C regression is introduced;
6.  E3.2 regression remains valid;
7.  resource bounds are documented;
8.  callback/task context is verified;
9.  documentation is synchronized.

Hardware validation is required before declaring the overall P4-E5D
feature `HARDWARE VALIDATED`.

## 24. Final Step-3 architecture

``` text
                    TRANSPORT
                        |
                        v
                  E5B TX result
                        |
                        v
                 E5C route failure
                        |
                        v
                E5D repair queue
                        |
                        v
                E5D repair task
                        |
                        v
             E5D/R4 orchestration
                        |
                        v
                 R4-A discovery
                        |
              +---------+---------+
              |                   |
              v                   v
         R4-B / RREQ         R4-C / RREP
              |                   |
              +---------+---------+
                        |
                        v
                  Route table
                        |
              +---------+---------+
              |                   |
              v                   v
        allowed route       failed-next-hop
              |                   |
              v                   X
          ACTIVE             rejected
              |
              v
       E5D repair complete
```

Ownership remains separated:

-   **E5C detects and invalidates.**
-   **E5D coordinates repair.**
-   **R4 performs discovery.**
-   **RREQ/RREP processors process routing messages.**
-   **Route table owns route state and metadata.**
-   **Transport remains below routing.**
-   **Reliability remains above/alongside the routing data path.**

------------------------------------------------------------------------

## 25. Decision

**Step-3 design decision: APPROVED ARCHITECTURAL DIRECTION ---
IMPLEMENTATION NOT YET FROZEN.**

The actual R4 source tree does not require a new
`repair(destination, failed_next_hop)` public R4 API.

The implementation shall introduce only the minimum
orchestration/adaptation needed to connect the already validated E5D
repair coordinator to the existing R4 discovery primitives and to
enforce failed-next-hop exclusion at the actual route-candidate
boundary.

No implementation shall begin until the ten Step-3 audit gates above are
resolved against the actual source tree.
