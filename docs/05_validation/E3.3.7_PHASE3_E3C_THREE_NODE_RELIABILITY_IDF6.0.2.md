# E3.3.7 Phase 3 / E3C — Three-Node End-to-End Reliability

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** Hardware validation PASS; E3C frozen

## Purpose

E3C combines the validated reliability-to-routing integration with the existing
three-node ENP topology:

```text
A (Node 1)          B (Node 2)          C (Node 3)
Gateway             Relay               Sensor
    |                   |                   |
    +------ DATA ------>+------ DATA ------>+
    |                   |                   |
    |                   +<------ ACK -------+
    |<------ ACK -------+
```

The test deliberately drops the first ACK at B. The originating reliability
transaction at A must time out and retransmit the same DATA packet. B must
recognize the retransmission as a duplicate, suppress another DATA forwarding
operation, and forward the cached ACK. C must deliver the application DATA
exactly once and generate one ACK. A must complete the original reliability
transaction as `DELIVERED`.

## Scope

E3C isolates the multi-hop reliability integration. Route discovery is not part
of this test. The route table is populated with the already validated topology:

```text
A: C -> B       metric = 2
B: C -> C       metric = 1
B: A -> A       metric = 1
C: A -> B       metric = 2
```

This deliberately avoids combining route discovery failures with reliability
failures in the same test. Route discovery and route repair remain separate
validation stages.

## Reliability ownership

The originating node A owns the end-to-end reliability transaction. B does not
create or own a reliability transaction for the forwarded DATA.

```text
A
|
+-- reliability transaction
|       |
|       +-- initial submission
|       +-- timeout
|       +-- retransmission
|       +-- ACK correlation
|       +-- DELIVERED
|
+-- routing determines current path
```

This preserves the E3 architectural rule that reliability owns delivery state
while routing owns the current path. The reliability layer retains the DATA
identity across the retry.

## DATA retry / ACK recovery sequence

```text
1. A submits reliable DATA to C.
2. Routing selects B.
3. B receives DATA and forwards it to C.
4. C delivers the application DATA once.
5. C generates an ACK addressed to A.
6. Routing sends the ACK C -> B.
7. B deliberately drops the first ACK but caches the exact packet.
8. A's reliability timeout expires.
9. A retransmits the same DATA identity.
10. B recognizes source + sequence as duplicate.
11. B does not forward the DATA again.
12. B forwards the cached ACK toward A.
13. A dispatcher delivers the ACK to the reliability service.
14. The original reliability transaction becomes DELIVERED.
```

The expected application delivery count at C is exactly one.

## Duplicate domains

The test maintains separate duplicate caches for DATA and ACK at B:

```text
DATA duplicate cache:
    source + DATA packet sequence

ACK duplicate cache:
    source + ACK packet sequence
```

This preserves the existing ENP duplicate-domain separation. The first ACK is
not classified as a duplicate; it is deliberately dropped by the test after it
has been cached. The retransmitted DATA is the duplicate that triggers ACK
recovery.

## Reuse of current routing integration

No new routing or transport API is introduced for E3C.

The existing routing data-path implementation performs route lookup,
logical-to-transport resolution and transmission. Its current implementation
is packet-validation/route based and therefore can forward the ACK packet as
well as the DATA packet. E3C uses that existing behavior rather than adding a
second transport-facing ACK path solely for the test.

This is intentionally a minimal integration step. A future API cleanup may
rename/generalize the current `enp_routing_data_path_*` naming if packet-type-
agnostic forwarding becomes a permanent public abstraction, but that is not a
requirement for E3C.

## Concurrency

The transport receive callback only copies the received frame into a statically
allocated FreeRTOS queue. Protocol processing occurs in the application task:

```text
ESP-NOW transport callback
        |
        v
StaticQueue
        |
        v
Application task
        +-- DATA duplicate processing
        +-- routing forwarding
        +-- ACK generation/forwarding
        +-- dispatcher ACK processing
        +-- reliability tick
```

This prevents reliability state from being modified concurrently by the
transport callback during the test.

## Acceptance criteria

### A — Gateway / originator

- [ ] reliable DATA transaction created
- [ ] initial DATA submitted through routing
- [ ] route A -> C selects B
- [ ] ACK is not received from the first attempt
- [ ] reliability performs exactly one retransmission
- [ ] retransmission enters the same routing submit interface
- [ ] recovered ACK reaches A
- [x] ACK passes through dispatcher and reliability service
- [ ] transaction completes as `DELIVERED`

### B — Relay

- [ ] DATA A -> B is received
- [ ] first DATA is forwarded B -> C
- [ ] first ACK C -> B is received
- [ ] first ACK is deliberately dropped and cached
- [ ] retransmitted DATA is recognized as a duplicate
- [ ] duplicate DATA is not forwarded to C
- [ ] cached ACK is forwarded B -> A exactly once
- [ ] DATA and ACK duplicate caches remain separate

### C — Sensor / destination

- [ ] DATA B -> C is received
- [ ] DATA packet identity is valid
- [ ] application sequence is valid
- [ ] application payload is valid
- [ ] application delivery count is exactly one
- [ ] one ACK is generated and submitted toward A

## Deliberate non-goals

E3C does not implement or validate:

- route discovery orchestration;
- stale-neighbor detection;
- next-hop failure detection;
- RERR propagation;
- route repair;
- alternate-path selection;
- larger than three-node topologies;
- changes to reliability transaction semantics;
- changes to the transport abstraction.

Those belong to the subsequent routing-resilience work.

## Validated result

E3C was hardware validated on three ESP32 nodes using ESP-IDF 6.0.2. The test demonstrated A -> B -> C DATA, C -> B -> A ACK, deliberate first-ACK loss at B, one reliability retransmission from A, duplicate DATA suppression at B, cached ACK recovery at B, exactly-once application delivery at C, and final `DELIVERED` completion at A. E3C is frozen. Route failure/repair remains outside this phase.
