## 1. Purpose

This document records the final results of the Step-3 implementation audit before implementation is frozen.

The objective was to resolve the remaining integration questions around:

- RREQ forwarding and next-hop selection;
- RREQ packet transmission;
- failed-next-hop exclusion during route repair;
- stale-route sequence-number handling;
- R4-A/B/C integration boundaries;
- task-context requirements;
- route verification after discovery.

The guiding rule is to preserve the existing ENP routing/discovery architecture and avoid unnecessary public API or wire-format changes.

---

# 2. Architectural principles confirmed

The following principles are retained:

```text
E5A = observe
E5B = prove real transport observation
E5C = invalidate
E5D = repair
```

E5C remains responsible for interpreting transport failure and invalidating affected routes. E5D consumes the resulting routing condition and starts repair. E5D does not independently interpret ESP-NOW send results.

The existing route-discovery subsystem remains the owner of:

- RREQ generation;
- RREQ forwarding;
- RREP processing;
- discovery state;
- discovery completion;
- sequence-number semantics.

E5D decides **when repair is required** and supplies the repair constraint.

The route table remains the authoritative source of persistent route state and metadata.

The Step-3 routing-control context must contain the existing routing/discovery objects and integration dependencies required to connect E5D to R4-A/B/C.

# 4. S3-I02 — R4-B / RREQ forwarding and next-hop selection

## Result: PASS / RESOLVED

### 4.1 Existing transport boundary

RREQ transmission shall use the existing ENP packet and transport path:

```text
R4-A / R4-B
     |
     v
routing-control
     |
     v
enp_packet_init()
     |
     v
populate ENP header
     |
     v
copy RREQ payload
     |
     v
enp_packet_seal()
     |
     v
enp_packet_data_const()
     |
     v
enp_packet_length()
     |
     v
enp_transport_send()
```

No routing-specific transport API is introduced.

### 4.2 Initial RREQ

For an E5D repair, the destination does not have an active route. Therefore the initial RREQ cannot obtain its next-hop from the destination route-table lookup.

The routing-control integration selects a usable neighbour and then resolves that logical neighbour to its transport address.

Conceptually:

```text
candidate neighbours
        |
        +-- local node? -------- reject
        |
        +-- failed next-hop? --- reject during repair
        |
        +-- unusable transport? reject
        |
        +-- usable ------------ candidate
```

The neighbour table remains outside `enp_route_table`.

### 4.3 RREQ forwarding

For an intermediate node:

```text
RREQ RX
   |
   v
R4-B
   |
   v
forwarding decision
   |
   v
logical next-hop
   |
   v
resolve_transport()
   |
   v
enp_transport_send()
```

The received packet is processed according to the existing R4-B semantics. The routing-control adapter supplies the transport integration required to actually transmit the RREQ.

### 4.4 Important scope rule

The E5D failed-next-hop constraint is local to the active repair originator.

It must NOT become a global rule applied to every node processing the RREQ.

# 9. S3-I07 — Failed-next-hop exclusion

## Result: PASS / RESOLVED

This is implemented at the R4-C route-update boundary.

The active repair context contains:

```text
destination = D
failed_next_hop = H
```

When R4-C proposes:

```text
candidate_next_hop = H
```

the candidate is rejected.

When:

```text
candidate_next_hop != H
```

normal route installation is permitted.

Conceptually:

```text
R4-C route update
       |
       v
active E5D repair?
       |
   +---+---+
   |       |
  no      yes
   |       |
normal   destination == D?
update      |
          +-- no --> normal update
          |
         yes
          |
          v
candidate_next_hop == H?
          |
      +---+---+
      |       |
     yes      no
      |        |
   REJECT    ACCEPT
```

### Critical rule

The failed-hop exclusion is:

- local;
- destination-specific;
- active-repair-specific;
- not encoded in the RREQ;
- not encoded in the RREP;
- not a global routing rule.

This prevents an unrelated route or discovery from being affected.

# 10. Stale-route sequence semantics

## Result: PASS / RESOLVED

E5C changes an affected route from:

```text
ACTIVE
   |
   v
STALE
```

The existing route entry retains its routing metadata, including its existing sequence information.

E5D must not:

- reset the sequence;
- invent a new sequence;
- arbitrarily increment the sequence;
- introduce a second sequence-ordering algorithm.

For repair, the existing route metadata is retrieved from the route-table entry associated with the destination.

Conceptually:

```text
STALE route
     |
     v
retrieve existing route metadata
     |
     v
existing sequence S
     |
     v
R4-A discovery
```

If no existing route entry exists, E5D must not manufacture a sequence number. The repair must follow the existing discovery failure semantics.

The existing routing protocol remains responsible for determining the legitimacy and ordering of newer routing information.

# 11. S3-I08 — Route verification

## Result: PASS / RESOLVED

R4-A reaching COMPLETE is necessary but insufficient.

A repair succeeds only if, after completion:

```text
route exists
AND
route.state == ACTIVE
AND
route.next_hop != failed_next_hop
```

Therefore:

```text
R4-A COMPLETE
      |
      v
route verification
      |
   +--+----------------+
   |                   |
acceptable          unacceptable
   |                   |
   v                   v
SUCCESS              FAILURE
   |                   |
   v                   v
ACTIVE route        route remains STALE
```

No new persistent `REPAIRING` route state is introduced.

# 15. Multiple routes sharing a failed next-hop

The existing E5C behaviour may invalidate several destinations sharing the same transport next-hop.

Example:

```text
D10 -> H2
D11 -> H2
D12 -> H3
```

After H2 failure:

```text
D10 -> STALE
D11 -> STALE
D12 -> ACTIVE
```

E5D therefore creates destination-specific repair requests:

```text
repair(D10, H2)
repair(D11, H2)
```

while D12 remains unaffected.

The E5D bounded pending set already provides duplicate suppression.

---

# 16. Repair serialization

There remains only one active R4-A discovery.

Multiple pending E5D destinations may exist:

```text
D10 -> repair
D11 -> pending
D12 -> pending
```

They are processed serially:

```text
D10
 ↓
R4 discovery
 ↓
complete/fail
 ↓
D11
 ↓
R4 discovery
 ↓
complete/fail
 ↓
D12
```

This prevents uncontrolled parallel RREQ discovery state.

---

# 17. Reliability interaction

No reliability changes are required.

If:

```text
A -> B -> C
```

fails and repair produces:

```text
A -> D -> C
```

the end-to-end reliability transaction remains the same transaction.

Repair must not:

- create a new application DATA transaction;
- reset transaction identity;
- reset reliability sequence;
- reset retry accounting;
- terminate the transaction solely because repair started.

After successful repair, retransmission re-enters the normal routing DATA path.

# 18. Controlled validation requirements

Before Step 3 is frozen, the controlled test must demonstrate:

1. E5D repair request starts exactly one R4 discovery.
2. R4-A becomes active.
3. RREQ is constructed using the existing ENP packet path.
4. RREQ transmission uses the existing transport boundary.
5. Controlled RREP reaches R4-C.
6. R4-C invokes the completion callback.
7. Completion reaches `enp_route_discovery_on_rrep()`.
8. R4-A reaches COMPLETE.
9. An acceptable route becomes ACTIVE.
10. A candidate using the failed next-hop is rejected.
11. A valid alternative next-hop is accepted.
12. An old/insufficient-sequence RREP does not complete the discovery.
13. Discovery failure leaves the route STALE.
14. Multiple destinations are serviced serially.
15. Unrelated routes remain unchanged.
16. R4 processing occurs in routing-control task context.
