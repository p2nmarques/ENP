# E3.3.7 Phase 4 / P4-E5A — Next-Hop Failure Detection and Propagation
## Interface / Architecture Contract

**Status:** VALIDATED / FROZEN (controlled self-test, 2026-08-17)  
**Target:** ESP-IDF 6.0.2  
**Phase:** E3.3.7 Phase 4 consolidation  
**Predecessors:** P4-E1, P4-E2, P4-E3, P4-E4A, P4-E4B, P4-E4C, P4-E4D  
**Scope:** Transport delivery-failure observation and propagation to the routing boundary

---

## 1. Purpose

P4-E5A defines the smallest architectural boundary required for ENP to
observe a transport-level transmission failure and propagate that failure to
the routing layer.

P4-E5A does **not** implement route invalidation, RERR generation,
route rediscovery, route repair, or reliability recovery. Those responsibilities
remain subsequent P4-E5 consolidation boundaries.

The purpose of this contract is therefore limited to establishing:

```text
transport transmission result
        ↓
ENP transport abstraction
        ↓
logical next-hop failure observation
        ↓
routing boundary
```

The contract must preserve the existing ownership boundaries established by
the Phase 4 architecture.

---

## 2. Architectural decision

The P4-E5A boundary is based on the following rule:

> **Transport reports what happened; routing decides what it means.**

The transport layer reports a transmission result. It must not decide that a
route is invalid, initiate route discovery, generate RERR, or manipulate the
route table.

The routing layer receives the failure observation and is responsible for
interpreting it as a routing event in a later consolidation step.

Reliability remains outside this boundary.

---

## 3. Existing interfaces that remain authoritative

P4-E5A must use the existing ENP ownership model.

### 3.1 Reliability

Reliability owns:

- reliability transaction identity;
- retry count;
- retry timing;
- transaction completion;
- delivery result.

Reliability does **not** own:

- transport delivery-result interpretation;
- route invalidation;
- next-hop failure detection;
- RERR;
- route discovery.

A reliability retry must continue to re-enter the routing data path so that a
current route and current next hop can be selected.

No reliability API extension is required by this contract.

---

### 3.2 Routing data path

The routing data path owns:

- logical destination handling;
- route lookup;
- current next-hop selection;
- logical-to-transport address resolution;
- transport submission.

P4-E5A must not introduce a second route-selection mechanism.

A transport failure must not cause the routing data path to cache or retain a
failed next hop as a new routing state.

---

### 3.3 Route table

The route table remains the owner of:

- route records;
- route state;
- active-route lookup;
- route invalidation.

The existing route states remain authoritative:

```text
ENP_ROUTE_STATE_ACTIVE
ENP_ROUTE_STATE_STALE
```

P4-E5A does not add a new route state.

The existing route-table invalidation interface remains the intended mechanism
for a later P4-E5B integration.

---

### 3.4 RERR

The RERR processor remains responsible for:

- RERR validation;
- RERR applicability;
- destination sequence handling;
- route invalidation based on an accepted RERR.

P4-E5A does not generate or process RERR.

---

### 3.5 Route discovery

RREQ/RREP and route-discovery remain responsible for route establishment.

P4-E5A does not initiate route discovery.

---

## 4. Required transport observation

The current architectural gap is that the ESP-NOW transport invokes
`esp_now_send()` and its asynchronous send callback currently does not expose
the delivery result to ENP routing.

P4-E5A must establish an ENP-level observation point for that result.

The transport result must distinguish at least:

```text
SUCCESS
FAILURE
```

The exact ESP-NOW status value must remain an implementation detail of the
ESP-NOW transport adapter.

The routing layer must not depend on `esp_now_send_status_t`.

---

## 5. Proposed transport-level callback contract

If inspection of the existing transport interface confirms that no equivalent
callback already exists, the smallest clean extension is conceptually:

```c
typedef void (*enp_transport_send_result_callback_t)(
    const enp_transport_address_t *destination,
    esp_err_t result,
    void *context);
```

with a corresponding registration operation:

```c
esp_err_t enp_transport_set_send_result_callback(
    enp_transport_t *transport,
    enp_transport_send_result_callback_t callback,
    void *context);
```

### Important

These declarations are **contract-level proposals**, not yet approved API
changes.

Before implementation, the current `enp_transport_t` interface must be
re-inspected and the smallest compatible extension selected.

If an existing interface can express the same contract without duplication,
that interface must be reused instead.

---

## 6. Result semantics

The callback reports the result of a transport transmission attempt.

### SUCCESS

```text
transport accepted and reported successful delivery
```

The event must not alter routing state.

### FAILURE

```text
transport reported unsuccessful delivery
```

The event must be observable at the ENP routing boundary.

P4-E5A does not define what routing subsequently does with that observation.

That interpretation belongs to P4-E5B and later.

---

## 7. Logical identity boundary

The transport adapter may internally use a transport-specific address such as
an ESP-NOW MAC address.

That address must not become part of the routing protocol contract.

The architectural boundary is:

```text
ESP-NOW MAC / transport address
              ↓
       transport adapter
              ↓
       ENP transport event
              ↓
      routing integration
              ↓
logical ENP next-hop identity
```

The exact mechanism used to associate the transport transmission with the
logical ENP next hop must be determined during implementation from the existing
routing-data-path interfaces.

P4-E5A must not duplicate route-table ownership merely to perform this mapping.

---

## 8. Callback execution context

The ESP-NOW send callback executes in the ESP-NOW/Wi-Fi callback context.

Therefore the production implementation must not perform lengthy routing,
route-table, route-discovery, or reliability processing directly from the
ESP-NOW callback.

The transport adapter must follow the existing project rule for callback
handling:

```text
ESP-NOW callback
       ↓
bounded event handoff
       ↓
ENP task / safe processing context
```

The implementation must not block the ESP-NOW callback.

The existing static-task/static-queue architecture remains preferred where
applicable.

---

## 9. Failure event ownership

P4-E5A establishes observation only.

The resulting event has the following ownership:

```text
Transport
    owns:
        - transport result
        - transport-specific status translation

Routing integration
    owns:
        - logical next-hop association
        - interpretation of failure

Route table
    owns:
        - route state

RERR processor
    owns:
        - RERR semantics

Route discovery
    owns:
        - route establishment

Reliability
    owns:
        - transaction/retry state
```

No component may silently assume another component's responsibility.

---

## 10. Error propagation rules

P4-E5A distinguishes two paths.

### 10.1 Immediate/synchronous transport error

If the existing transport send operation returns an immediate `esp_err_t`
failure:

```text
routing data path
        ↓
transport send
        ↓
immediate error
```

the existing synchronous error return remains valid.

P4-E5A does not replace that mechanism.

### 10.2 Asynchronous delivery failure

If the transport reports failure asynchronously:

```text
transport send
        ↓
ESP-NOW send callback
        ↓
failure event
        ↓
ENP routing boundary
```

the event must be propagated without blocking the transport callback.

Both mechanisms may coexist.

---

## 11. No route repair in P4-E5A

The following are explicitly outside the P4-E5A acceptance boundary:

```text
route invalidation
RERR generation
RERR forwarding
RREQ generation
RREP generation
route rediscovery
route replacement
reliability retransmission
transaction completion
```

Those operations may consume the P4-E5A failure observation in later
consolidation steps.

This prevents P4-E5A from coupling transport failure observation to the full
route-repair mechanism.

---

## 12. Acceptance criteria

P4-E5A is accepted only when all of the following are demonstrated.

### E5A-1 — successful transmission observation

A controlled transport can report a successful transmission result through the
new or existing transport result interface.

Expected:

```text
SUCCESS
```

is observable at the defined boundary.

### E5A-2 — failed transmission observation

A controlled transport can report a failed transmission result.

Expected:

```text
FAILURE
```

is observable at the defined boundary.

### E5A-3 — no transport-specific routing API leakage

The routing-facing interface does not expose ESP-NOW-specific status types.

### E5A-4 — no route-state mutation

A P4-E5A failure observation alone does not invalidate a route.

Route mutation remains a later P4-E5B responsibility.

### E5A-5 — no RERR

P4-E5A does not generate, process, or forward RERR.

### E5A-6 — no route discovery

P4-E5A does not start RREQ/RREP processing or route discovery.

### E5A-7 — reliability isolation

The reliability API and transaction ownership remain unchanged.

### E5A-8 — callback safety

The transport callback does not perform blocking or lengthy routing processing.

### E5A-9 — production transport mapping

The ESP-NOW adapter translates its native send result into the ENP-level
transport result without exposing `esp_now_send_status_t` above the transport
adapter.

### E5A-10 — reproducible test

The complete controlled-transport validation is reproducible on ESP-IDF 6.0.2.

---

## 13. Controlled-test boundary

The first P4-E5A self-test must use a controlled transport.

The controlled transport must be able to produce at least:

```text
send → SUCCESS
send → FAILURE
```

The test must verify the observation at the defined ENP boundary.

The test must not require a real route failure.

This isolates the P4-E5A contract from later route-repair behavior.

---

## 14. Hardware-validation boundary

P4-E5A becomes **HARDWARE VALIDATED** only after a separate hardware test
demonstrates that the real ESP-NOW transport can produce the corresponding
ENP-level failure observation on real ESP32 hardware.

A successful controlled test alone establishes:

```text
VALIDATED
```

not:

```text
HARDWARE VALIDATED
```

The hardware test must use:

```text
real ESP32
+
real ESP-NOW
+
production transport adapter
+
production failure-observation path
```

The exact hardware failure scenario must be defined when the implementation
test is prepared.

---

## 15. Freeze criteria

P4-E5A may be marked **FROZEN** only when:

1. the transport-result contract is implemented;
2. the smallest required API extension has been approved;
3. controlled SUCCESS and FAILURE observations pass;
4. no forbidden ownership coupling has been introduced;
5. ESP-NOW-specific result types remain confined to the transport adapter;
6. the implementation is reproducible on ESP-IDF 6.0.2;
7. documentation reflects the accepted interface.

P4-E5A may be marked **HARDWARE VALIDATED** only after the separate real-hardware
acceptance criteria pass.

---

## 16. Relationship to subsequent P4-E5 stages

The intended dependency chain is:

```text
P4-E5A
Next-Hop Failure Detection and Propagation
        ↓
P4-E5B
Route Invalidation / RERR Integration
        ↓
P4-E5C
Route Rediscovery / Repair
        ↓
P4-E5D
Reliability + Route Repair Integration
```

The boundaries must remain separate unless a later architecture review
explicitly approves their consolidation.

---

## 17. Contract decision

The P4-E5A architecture contract establishes:

> **Transport reports what happened; routing decides what it means.**

The existing reliability, route-table, RERR and route-discovery interfaces remain
authoritative.

The only expected architectural extension is at the transport-result
observation boundary, and only if the existing `enp_transport_t` interface
cannot express this contract without duplication.

**P4-E5A contract status: VALIDATED / FROZEN (2026-08-17).**

The controlled self-test demonstrated the approved transport send-result
boundary for both SUCCESS and FAILURE. P4-E5A is not yet HARDWARE VALIDATED;
real ESP-NOW failure observation remains a subsequent validation step.
