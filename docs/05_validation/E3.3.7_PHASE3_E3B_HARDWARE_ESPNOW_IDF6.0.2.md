# E3.3.7 Phase 3 / E3 — Reliability-to-Routing Real ESP-NOW Hardware Integration

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Status:** Hardware validation PASS; E3B frozen

## Purpose

This stage combines the already validated Phase 3 boundaries:

```text
Reliability
    |
    | enp_reliability_submit_fn
    v
Routing DATA path
    |
    +-- active route lookup
    +-- current next-hop selection
    +-- logical -> transport resolution
    +-- enp_transport_send()
    |
    v
Real ESP-NOW
    |
    v
Remote ESP32
    |
    | ACK
    v
Dispatcher
    |
    v
Reliability ACK service
    |
    v
Transaction -> DELIVERED
```

E1, E2-A, E2-B and the hardware-independent E3 self-test have already been
validated. This stage validates their combined operation on two real ESP32
nodes.


## E3B r1 correction

The first hardware run exposed a test-application error in DATA packet construction.
The test had constructed an `ENP_PACKET_APPLICATION` packet with only the raw
application payload. The existing reliability validation correctly requires the
ENP DATA payload sub-header (`enp_data_header_t`) to be present.

The r1 test now uses the existing `enp_data_header_init()` API and seals the
packet with:

```text
ENP_DATA_HEADER_SIZE + application_payload_length
```

The receiver correspondingly validates the DATA sub-header, application sequence,
and application payload separately. No production ENP API or implementation was
changed.

The failed first run is therefore recorded as a **test implementation failure**,
not a protocol or transport failure. E3B hardware validation subsequently passed and is frozen.

## Test topology

The sender has a direct active route to Node 2. No route discovery is required
for this test.

## Deliberate ACK-loss test

The receiver deliberately drops the first ACK. This forces the sender's real
reliability layer to reach its timeout and retransmission path.

Expected sequence:

```text
Attempt 1
    Node 1 DATA -> Node 2
    Node 2 validates DATA
    Node 2 intentionally drops ACK

Timeout

Attempt 2
    Node 1 reliability retransmits the same DATA transaction
    routing data path performs route lookup again
    Node 2 receives the retransmission
    Node 2 sends ACK

ACK
    Node 1 ESP-NOW RX
        -> dispatcher
        -> reliability ACK service
        -> transaction DELIVERED
```

This test deliberately keeps the ACK-loss behavior inside the test
application. It does not add test-specific loss behavior to the ENP
transport or reliability implementation.

The test verifies retransmission over the real transport, but it does not
replace the existing DATA duplicate-suppression validation. Duplicate
suppression remains a separate established capability.

## Concurrency boundary in the test

The ESP-NOW transport already uses a static RX queue and static worker task.
The hardware E3 test therefore keeps reliability state manipulation in the
application task:

```text
ESP-NOW transport callback
    |
    +-- copy received ACK/DATA to static storage
    |
    +-- return

Application task
    |
    +-- dispatcher ACK processing
    +-- enp_reliability_tick()
    +-- test-specific ACK transmission
```

This avoids introducing concurrent access to the current reliability
transaction table from the transport worker task during this validation.
No production reliability synchronization API is introduced by this test.

## Final E3B hardware validation

E3B was validated on two ESP32 nodes using ESP-IDF 6.0.2. The sender submitted
reliable DATA through the routing data path, the receiver deliberately dropped
the first ACK, the sender retransmitted the same DATA transaction, and the
receiver returned the ACK on the retry. The sender dispatcher/reliability path
completed the transaction as `DELIVERED`.

The receiver also validated the ENP DATA sub-header, application sequence and
application payload. E3B is therefore frozen.
