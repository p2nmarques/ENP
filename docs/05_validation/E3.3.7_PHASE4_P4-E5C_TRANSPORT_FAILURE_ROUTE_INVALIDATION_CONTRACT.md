# E3.3.7 Phase 4 / P4-E5C — Transport Failure → Route Invalidation Contract

**Status:** HARDWARE VALIDATED / FROZEN  
**Date:** 2026-08-18  
**Target:** ESP-IDF 6.0.2  
**Depends on:** P4-E5A VALIDATED / FROZEN; P4-E5B HARDWARE VALIDATED / FROZEN

---

## 1. Purpose

P4-E5C defines the smallest routing-integration boundary that consumes a
frozen ENP transport send-result failure and changes the state of the affected
logical route.

The architectural rule is:

> **Transport reports what happened; routing decides what it means.**

P4-E5C therefore connects the already validated transport failure observation
to the existing route-table ownership without moving routing responsibility
into the transport layer.

P4-E5C is a route-state integration milestone. It is not a route-repair or
RERR-propagation milestone.

---

## 2. Existing validated/frozen inputs

P4-E5C consumes two existing boundaries without redefining them.

### 2.1 P4-E5A

P4-E5A established the ENP-level send-result callback:

```c
typedef void (*enp_transport_send_result_callback_t)(
    const enp_transport_address_t *destination,
    esp_err_t result,
    void *context);
```

P4-E5A is **VALIDATED / FROZEN** at controlled-test level.

### 2.2 P4-E5B

P4-E5B demonstrated on real ESP32 hardware that a real ESP-NOW transmission
failure reaches this interface as a non-`ESP_OK` result, with the transport
destination preserved and the observation delivered through the
`enp_espnow` task context.

P4-E5B is **HARDWARE VALIDATED / FROZEN**.

P4-E5C must consume this interface exactly as frozen.

---

## 3. Existing route-table ownership

The existing `enp_route_table_t` remains the sole owner of route state.

Its route entry already contains:

```c
typedef struct {
    enp_route_destination_t destination;
    enp_route_destination_t next_hop;

    enp_route_metric_t metric;

    uint32_t route_sequence;
    uint32_t expires_at_ms;

    enp_route_state_t state;
} enp_route_entry_t;
```

The existing route states are:

```text
ENP_ROUTE_STATE_INVALID
ENP_ROUTE_STATE_ACTIVE
ENP_ROUTE_STATE_STALE
```

The existing API also already provides:

```c
bool enp_route_table_invalidate(
    enp_route_table_t *table,
    enp_route_destination_t destination);
```

P4-E5C must reuse this route-table ownership and state transition rather than
introducing another route-state store.

---

## 4. Required P4-E5C behavior

When the transport reports an asynchronous failure:

```text
transport destination
        +
non-ESP_OK result
        ↓
P4-E5C routing integration
        ↓
identify affected logical next hop
        ↓
find active routes using that next hop
        ↓
mark affected routes STALE
```

The route invalidation operation is deliberately represented by the existing
`enp_route_table_invalidate()` API, whose current implementation transitions
an active route to `ENP_ROUTE_STATE_STALE`.

Therefore, in the current implementation vocabulary:

```text
transport failure
      ↓
ACTIVE route
      ↓
STALE route
```

P4-E5C must **not** directly remove the route or introduce a new route state.

---

## 5. Transport address → logical next-hop association

The transport callback reports a transport address, for ESP-NOW normally a
MAC address. Routing uses logical ENP addresses.

P4-E5C must bridge those representations through the existing routing-data-path
integration boundary.

The existing interface is:

```c
typedef bool (*enp_routing_resolve_transport_fn)(
    void *context,
    enp_route_destination_t next_hop,
    enp_transport_address_t *transport_address);
```

P4-E5C shall use the existing resolver in the reverse integration operation:

```text
installed route
    ↓
route.next_hop
    ↓
resolve_transport(route.next_hop)
    ↓
transport address
    ↓
compare with failed transport destination
```

The routing layer therefore remains the owner of the logical next-hop
association, while the transport layer remains unaware of ENP route entries.

### 5.1 Why reverse lookup is not added to the transport API

P4-E5C must **not** add a transport API such as:

```text
transport_mac_to_node()
transport_find_route()
transport_get_next_hop()
```

Those would leak routing semantics into the transport abstraction.

The existing route table and routing integration remain authoritative.

### 5.2 Multiple routes using the same next hop

If several active routes resolve to the same failed transport address, the
failure applies to all of those routes because they share the same failed
next hop.

Example:

```text
Route A → next hop B → MAC-B
Route C → next hop B → MAC-B
Route D → next hop E → MAC-E

MAC-B fails

Route A → STALE
Route C → STALE
Route D → remains ACTIVE
```

P4-E5C must not stop after invalidating only the first matching route.

---

## 6. Failure result semantics

P4-E5C consumes the ENP transport result after the transport adapter has
already translated the native ESP-NOW result.

The routing integration therefore uses the following rule:

```text
result == ESP_OK
    → no route invalidation

result != ESP_OK
    → candidate route failure event
```

P4-E5C must not interpret ESP-NOW-specific status values directly.

The transport abstraction remains responsible for translating transport-native
status into the ENP-level `esp_err_t` result.

### 6.1 Immediate send failure

The synchronous return value of `enp_transport_send()` is not the P4-E5C
asynchronous failure event.

P4-E5C is specifically concerned with the already validated asynchronous
send-result path.

If a future integration needs to handle immediate submission failure as a
route failure, that must be explicitly specified rather than silently
combining the two semantics.

---

## 7. Route-state transition

P4-E5C uses the existing route invalidation operation.

For an affected active route:

```text
ACTIVE
  ↓
transport failure for its next hop
  ↓
STALE
```

A stale route is retained information and must not be selected as an active
forwarding route by the existing route lookup API.

The current route-table implementation already enforces this by returning
only active entries from `enp_route_table_lookup()` and
`enp_route_table_lookup_const()`.

### 7.1 Already stale routes

An already stale route requires no additional state transition.

P4-E5C must not convert it to another state or remove it merely because the
same next-hop failure is observed again.

### 7.2 Invalid routes

An invalid route is not an active route and must not be selected as a P4-E5C
failure target.

P4-E5C must not resurrect or otherwise modify an invalid route.

---

## 8. Ownership model

P4-E5C establishes the following ownership boundary:

```text
Transport
    owns:
        - transport transmission
        - transport-specific result
        - ENP result translation
        - transport destination

P4-E5C routing integration
    owns:
        - association of transport destination with logical next hops
        - identification of affected active routes
        - invoking route invalidation

Route table
    owns:
        - route entries
        - route state
        - ACTIVE → STALE transition

RERR processor
    owns:
        - received RERR validation
        - RERR applicability
        - RERR-driven route invalidation

Route discovery / repair
    owns:
        - establishing or repairing a route

Reliability
    owns:
        - transaction state
        - retry state
        - delivery result
```

No component may silently acquire another component's ownership.

---

## 9. RERR boundary

P4-E5C does **not** generate, transmit, receive, or process RERR.

A transport failure may eventually result in RERR behavior, but that is a
separate routing-resilience integration boundary.

The existing `enp_rerr_processor_t` remains responsible for processing an
already received RERR and deciding whether an installed route should be
invalidated according to the existing RERR sequence rules.

Therefore:

```text
P4-E5C
transport failure
      ↓
local next-hop route invalidation

Later RERR integration
local route failure
      ↓
RERR generation/propagation policy
```

The two mechanisms must not be conflated.

---

## 10. Route discovery / repair boundary

P4-E5C does not initiate route discovery or local repair.

After P4-E5C marks a route stale, subsequent routing-resilience work may use
that state to trigger:

```text
STALE
  ↓
local repair / route discovery
  ↓
new ACTIVE route
```

Those operations are outside this contract.

P4-E5C therefore has no responsibility for:

- RREQ generation;
- RREQ forwarding;
- RREP processing;
- local repair;
- alternate next-hop selection;
- route restoration;
- reliability retransmission after route failure.

---

## 11. Reliability boundary

P4-E5C does not modify the reliability transaction manager.

In particular, it must not:

- mark a transaction `FAILED` solely because a route became stale;
- reset retry counters;
- initiate a retransmission;
- complete an ACK transaction;
- alter packet transaction identity.

Reliability may consume a future route-repair service, but that belongs to a
later explicitly approved integration boundary.

---

## 12. Processing-context requirement

P4-E5B established that the real ESP-NOW TX result reaches ENP task context
through the `enp_espnow` worker.

P4-E5C route-table processing must therefore occur outside the ESP-NOW/Wi-Fi
callback context.

The required production boundary is:

```text
ESP-NOW callback
       ↓
bounded transport event handoff
       ↓
enp_espnow task
       ↓
ENP send-result callback / routing integration
       ↓
route-table invalidation
```

P4-E5C must not introduce blocking work into the native ESP-NOW callback.

The existing static-task/static-queue architecture remains the preferred
execution model.

---

## 13. Idempotency and duplicate failure observations

Repeated failure observations for the same transport destination are expected
to be possible.

P4-E5C must be idempotent with respect to route state:

```text
ACTIVE + failure → STALE
STALE  + failure → STALE / no-op
INVALID + failure → no-op
```

A repeated failure must not:

- remove the route;
- create another route entry;
- change the route sequence merely because the failure repeated;
- trigger RERR;
- trigger route discovery;
- modify reliability state.

---

## 14. Route-sequence handling

A transport failure does not itself provide a new destination sequence number.

P4-E5C therefore must not invent or modify `route_sequence` merely because a
next-hop failure occurred.

The existing stored route sequence remains unchanged by the local
`ACTIVE → STALE` transition unless a later route protocol operation explicitly
updates it.

---

## 15. Required implementation interface

P4-E5C should expose a routing-integration operation conceptually equivalent
to:

```c
void handle_transport_send_result(
    routing_context_t *context,
    const enp_transport_address_t *destination,
    esp_err_t result);
```

The exact public symbol name and containing type are an implementation detail
and may follow existing repository naming conventions.

The operation must have access to:

```text
route table
transport resolver
transport destination
send result
```

It must not require a second route table or transport-specific routing API.

### 15.1 Recommended implementation algorithm

```text
if result == ESP_OK:
    return

for every route entry:
    if route.state != ACTIVE:
        continue

    resolve route.next_hop → transport address

    if resolved address != failed destination:
        continue

    invalidate route.destination
```

The implementation must ensure that invalidating one route does not prevent
inspection of the remaining route entries.

If the existing route-table API does not safely support iteration through its
public interface, the implementation must add the smallest routing-owned
inspection operation required. It must not expose route-table internals to the
transport layer.

---

## 16. Failure matching rules

A failure matches a route only when all of the following are true:

1. the route is currently `ACTIVE`;
2. the route has a logical `next_hop`;
3. the existing resolver successfully maps that next hop to a transport
   address;
4. the resolved transport address equals the failure destination;
5. the transport result is non-`ESP_OK`.

If the resolver cannot resolve a route's next hop, that route must not be
invalidated merely because another route failed.

This prevents a failed transport address from being treated as a wildcard
failure for unrelated routes.

---

## 17. Acceptance criteria

P4-E5C is accepted only when all of the following are demonstrated.

### E5C-1 — successful transmission does not invalidate a route

Given an active route whose next hop resolves to destination MAC X:

```text
ESP_OK + MAC X
    ↓
route remains ACTIVE
```

### E5C-2 — failed transmission invalidates the matching route

Given:

```text
Route D → next hop B → MAC-B
```

and:

```text
MAC-B + ESP_FAIL
```

then:

```text
Route D → STALE
```

### E5C-3 — matching is based on the existing next-hop association

The failed transport address must be matched against the transport address
resolved from the route's logical `next_hop`.

No transport-to-routing reverse API may be added.

### E5C-4 — all affected routes are invalidated

If:

```text
Route A → B → MAC-B
Route C → B → MAC-B
Route D → E → MAC-E
```

then failure of `MAC-B` must produce:

```text
A → STALE
C → STALE
D → ACTIVE
```

### E5C-5 — unrelated routes remain active

A failure for MAC-B must not invalidate a route whose next hop resolves to
MAC-E.

### E5C-6 — duplicate failure is idempotent

Repeated failure observations must not create additional state changes or
route entries.

### E5C-7 — route sequence is preserved

The local failure transition must not invent or modify the stored route
sequence.

### E5C-8 — no RERR

The P4-E5C test must demonstrate that route invalidation occurs without
invoking RERR generation or processing.

### E5C-9 — no route discovery/repair

The P4-E5C test must demonstrate that route invalidation does not start RREQ,
RREP, local repair, or rediscovery.

### E5C-10 — reliability isolation

The P4-E5C test must demonstrate that route invalidation does not directly
modify reliability transaction state.

### E5C-11 — task-context safety

The route-table mutation must occur in ENP task context, not in the native
ESP-NOW callback context.

### E5C-12 — no transport API leakage

No routing-specific API may be added to `enp_transport_t` or the ESP-NOW
adapter solely to implement E5C.

---

## 18. Controlled self-test boundary

The first P4-E5C test must use a controlled transport/event source so that
route-state behavior can be validated independently from real radio behavior.

The controlled test should establish at minimum:

```text
Route A → B → transport MAC-B       ACTIVE
Route C → B → transport MAC-B       ACTIVE
Route D → E → transport MAC-E       ACTIVE

failure(MAC-B, ESP_FAIL)

Expected:
A → STALE
C → STALE
D → ACTIVE
```

It must then repeat the same failure and demonstrate idempotency.

It must also submit a successful result for MAC-E and demonstrate that no
route is invalidated by `ESP_OK`.

The controlled test must verify that the route sequence values remain
unchanged and that no RERR/route-discovery/reliability action is triggered.

---

## 19. Hardware-validation boundary

P4-E5C should not be marked hardware validated merely because the controlled
route-state self-test passes.

Hardware validation requires a separate real-ESP32 test demonstrating:

```text
real ESP-NOW TX failure
        ↓
P4-E5B frozen result observation
        ↓
P4-E5C routing integration
        ↓
matching route becomes STALE
```

The real hardware test must also demonstrate that an unrelated route remains
usable and that route invalidation occurs in task context.

---

## 20. Explicit non-goals

P4-E5C does not implement:

- RERR generation;
- RERR forwarding;
- RERR reception/processing changes;
- RREQ;
- RREP;
- route discovery;
- local route repair;
- alternate-path selection;
- reliability recovery;
- multi-path routing;
- changes to the ENP packet wire format;
- changes to the frozen transport send-result interface.

---

## 21. Dependency chain

The Phase 4 failure-handling sequence is:

```text
P4-E5A

        │
        ▼
P4-E5B

        │
        ▼
```

RERR generation/propagation remains a separate routing-resilience decision
unless explicitly incorporated into a later approved contract.

---

## 22. Freeze rule

P4-E5C was marked **FROZEN** after:

1. this contract has been approved;
2. the implementation preserves the P4-E5A/P4-E5B frozen interfaces;
3. the controlled acceptance criteria pass;
4. documentation records the exact implementation boundary;
5. no routing/reliability ownership has leaked into the transport layer.

Hardware validation, if performed, is recorded separately from the controlled
contract acceptance.

## 23. Contract decision

The P4-E5C contract establishes:

> **A real transport failure is converted by the routing integration into a
> local `ACTIVE → STALE` transition for every active route that uses the failed
> logical next hop. The route table remains the sole owner of route state.**

P4-E5C consumes the frozen P4-E5B transport result and does not redefine the
transport interface.

**P4-E5C contract status: HARDWARE VALIDATED / FROZEN.**


## 23. Controlled validation outcome

The approved P4-E5C contract has been implemented and exercised by the
controlled self-test:

```text
E3.3.7 Phase 4 / P4-E5C self-test PASS
```

The controlled result demonstrated:

- correct send-result callback binding;
- failure matching through the existing logical-next-hop resolver;
- invalidation of all ACTIVE routes sharing the failed next hop;
- preservation of unrelated ACTIVE routes;
- route-sequence preservation;
- idempotent repeated failure handling;
- no route-discovery, RERR, or reliability side effects.

P4-E5C is therefore **HARDWARE VALIDATED / FROZEN**.

Real ESP-NOW hardware validation remains a separate subsequent milestone.
