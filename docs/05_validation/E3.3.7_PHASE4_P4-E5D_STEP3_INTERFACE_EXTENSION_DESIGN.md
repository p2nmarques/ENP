# E3.3.7 PHASE 4 / P4-E5D

# STEP 3 --- ROUTING-CONTROL / E5D INTERFACE-EXTENSION DESIGN

**Status:** PROPOSED --- READY FOR REVIEW\
**Baseline:** `ENP-0.2-r5(20260821-175726)`\
**Target:** ESP-IDF 6.0.2\
**Scope:** E5D → R4 route rediscovery integration\
**Primary focus:** RREP → R4-A completion bridge

------------------------------------------------------------------------

## 1. Purpose

This document defines the exact interface-extension design for P4-E5D
Step 3.

The purpose is to connect the already validated E5D route-repair
coordinator to the existing R4 discovery implementation without changing
the RREQ/RREP wire format or the ownership of the existing R4-A, R4-B,
R4-C and route-table components.

The central integration boundary is:

``` text
E5D repair coordinator
        |
        v
routing-control context
        |
        v
R4 discovery
        |
        v
R4-C discovery_complete()
        |
        v
R4-A enp_route_discovery_on_rrep()
```

------------------------------------------------------------------------

# 2. Design status

This is an **interface-extension design**, not an implementation freeze.

The design shall be reviewed and approved before implementation begins.

It supersedes the earlier conceptual Step-3 interface proposal where
that proposal conflicts with the actual audited source tree.

------------------------------------------------------------------------

# 3. Architectural position

The new routing-control integration layer sits between E5D and the
existing R4 primitives:

``` text
                         E5C
                          |
                          | route failure
                          v
                  E5D repair coordinator
                          |
                          | consume callback
                          v
              +---------------------------+
              | E5D / Routing-Control     |
              | orchestration context     |
              +-------------+-------------+
                            |
              +-------------+-------------+
              |             |             |
              v             v             v
             R4-A          R4-B          R4-C
          discovery        RREQ          RREP
              |             |             |
              +-------------+-------------+
                            |
                            v
                       Route table
```

The routing-control layer owns orchestration only.

------------------------------------------------------------------------

# 4. Existing R4 interfaces remain authoritative

The design uses the existing R4 primitives:

``` c
enp_route_discovery_start(...)
enp_route_discovery_on_rrep(...)
enp_route_discovery_on_timeout(...)
```

and the existing R4-B/R4-C callback interfaces.

No new R4 API such as:

``` c
repair(destination, failed_next_hop)
```

is introduced.

------------------------------------------------------------------------

# 5. RREP-originator correlation

The audit established that the RREP wire payload does not require an
originator field for discovery correlation.

Two different concepts must remain separate:

### R4-C forwarding

R4-C uses its configured:

``` c
discovery_originator
```

to determine where a RREP must be forwarded.

### R4-A discovery correlation

R4-A correlates an RREP using:

``` text
destination
+
destination sequence
```

against its active discovery state.

Therefore no RREQ/RREP wire-format extension is required.

The local node running the active discovery is the discovery originator.

------------------------------------------------------------------------

# 6. Routing-control context

The proposed context is:

``` c
typedef struct {
    enp_route_repair_t *repair;

    enp_route_discovery_t discovery;
    enp_rrep_processor_t rrep_processor;

    enp_route_table_t *route_table;
    enp_transport_t *transport;

    enp_route_destination_t active_destination;
    enp_route_destination_t active_failed_next_hop;

    enp_route_sequence_t active_destination_sequence;
    uint32_t active_route_request_id;

    bool discovery_active;

    /* static RX queue/task resources */
} enp_routing_repair_context_t;
```

The exact field names may be refined during implementation if the
audited source requires it, but the ownership semantics are fixed by
this design.

------------------------------------------------------------------------

# 7. Context ownership

The context owns the integration lifecycle of the active repair.

It does not become the owner of R4-A discovery semantics.

Specifically:

  State / responsibility        Owner
  ----------------------------- -----------------------------
  Pending repair requests       E5D repair coordinator
  Active repair context         routing-control integration
  Discovery transaction state   R4-A
  RREQ processing               R4-B
  RREP processing               R4-C
  Route state and metadata      route table
  Physical transmission         transport
  DATA transaction identity     reliability

------------------------------------------------------------------------

# 8. R4-B callback wiring

The existing R4-B callback context is:

``` c
void *context;
```

The routing-control object is supplied as that context.

Conceptually:

``` c
enp_rreq_processor_callbacks_t callbacks = {
    .context = routing_context,
    .is_duplicate = routing_control_rreq_duplicate,
    .learn_reverse_route = routing_control_learn_reverse_route,
};
```

No R4-B callback signature changes are required.

The callbacks may use the context to access the existing route table and
bounded duplicate state.

------------------------------------------------------------------------

# 9. R4-C callback wiring

The existing R4-C callbacks similarly receive the routing-control
context.

Conceptually:

``` c
enp_rrep_processor_callbacks_t callbacks = {
    .context = routing_context,
    .update_route = routing_control_update_route,
    .lookup_next_hop = routing_control_lookup_next_hop,
    .discovery_complete = routing_control_discovery_complete,
};
```

No R4-C callback signature changes are required.

------------------------------------------------------------------------

# 10. RREP → R4-A completion bridge

The central Step-3 callback is:

``` c
static bool routing_control_discovery_complete(
    void *context,
    enp_rrep_node_t destination,
    enp_route_sequence_t destination_sequence);
```

Its semantic contract is:

> Convert an accepted R4-C discovery-completion event into completion of
> the currently active R4-A discovery transaction.

The callback shall:

1.  validate the routing-control context;
2.  verify that an active discovery exists;
3.  verify that the event corresponds to the active destination;
4.  pass the event to R4-A using `enp_route_discovery_on_rrep()`;
5.  leave R4-A responsible for the authoritative destination/sequence
    correlation.

The callback shall not directly change route state.

------------------------------------------------------------------------

# 11. Bridge operation

The essential operation is:

``` c
return enp_route_discovery_on_rrep(
    &context->discovery,
    destination,
    destination_sequence);
```

R4-A remains authoritative for:

-   destination matching;
-   destination-sequence freshness;
-   discovery state transition;
-   completion/failure state.

The routing-control layer must not duplicate those rules.

------------------------------------------------------------------------

# 12. Active discovery lifecycle

The lifecycle is:

``` text
IDLE
 |
 | E5D repair request
 v
STARTING
 |
 | enp_route_discovery_start()
 v
ACTIVE
 |
 +--------------------+
 |                    |
 | valid RREP         | timeout
 v                    v
R4-A COMPLETE       R4-A FAILED
 |                    |
 v                    v
VERIFY ROUTE       REPAIR FAILURE
 |
 v
REPAIR SUCCESS
 |
 v
IDLE
```

There shall be exactly one active R4-A discovery transaction per
routing-control context.

------------------------------------------------------------------------

# 13. Starting a discovery

When E5D consumes a repair request:

``` text
destination = D
failed_next_hop = H
```

the routing-control task shall:

1.  obtain the current destination sequence from the existing
    route-table contract;
2.  populate the active repair context;
3.  allocate a new R4 route-request ID;
4.  start R4-A;
5.  mark the discovery active only after successful start.

The context must be populated before calling
`enp_route_discovery_start()`.

------------------------------------------------------------------------

# 14. Active context

The active context represents:

``` text
destination              = D
failed_next_hop          = H
destination_sequence     = S
route_request_id         = R
discovery_active         = true
```

The R4 route-request ID is an R4 discovery transaction identity.

It is not an ENP DATA transaction identity.

------------------------------------------------------------------------

# 15. E5D integration

The existing E5D repair coordinator already provides the asynchronous
repair queue and consume callback.

Its current contract explicitly defines the consume callback as running
in the dedicated repair task context. The repair request remains in the
bounded pending set until the consume callback completes.

Therefore Step 3 shall reuse that existing boundary.

Conceptually:

``` c
enp_route_repair_init(
    &repair,
    routing_control_consume_repair,
    &routing_context);
```

The design does **not** introduce a second E5D repair command queue.

------------------------------------------------------------------------

# 16. Queue/task architecture

Only the incoming routing RX path requires a separate queue.

The architecture is:

``` text
                         ESP-NOW
                            |
              +-------------+-------------+
              |                           |
              v                           v
          TX result                       RX
              |                           |
              v                           v
             E5C                    RX callback
              |                           |
              v                           v
       E5D repair queue              RX queue
              |                           |
              v                           |
       E5D repair task                    |
              |                           |
              +-------------+-------------+
                            |
                            v
                    routing-control
                     processing task
                            |
                            v
                         R4-A/B/C
```

The exact task consolidation may be refined during implementation if the
existing E5D task can safely perform the routing-control work without
violating task-context requirements.

The key invariant is that R4 processing is not performed directly from
the ESP-NOW RX callback.

------------------------------------------------------------------------

# 17. Static resource policy

The routing-control RX queue shall use:

``` c
StaticQueue_t
```

with statically allocated storage.

The routing-control processing task shall use:

``` c
StaticTask_t
StackType_t[]
```

No dynamic allocation is permitted.

The existing E5D repair queue/task remains static as already
implemented.

------------------------------------------------------------------------

# 18. RX event boundary

Incoming routing packets are represented by a bounded event containing:

``` text
packet type
transport source
packet length
packet bytes
```

The ESP-NOW callback only copies the required packet data into the
bounded RX event and publishes it to the routing-control queue.

R4-B/R4-C processing occurs in routing-control task context.

------------------------------------------------------------------------

# 19. RREQ transmission

When R4-A requires an RREQ transmission, the routing-control layer shall
use the existing ENP packet construction and transport boundary.

The existing E3.2.2 production-like path demonstrates:

``` text
enp_packet_init()
        ↓
populate ENP header
        ↓
copy RREQ payload
        ↓
enp_packet_seal()
        ↓
enp_packet_data_const()
enp_packet_length()
        ↓
enp_transport_send()
```

No routing-specific transport API shall be introduced.

------------------------------------------------------------------------

# 20. RREP transmission

RREP forwarding follows the same existing boundary:

``` text
R4-C
  ↓
routing-control
  ↓
ENP packet construction
  ↓
enp_packet_seal()
  ↓
enp_transport_send()
```

The RREP wire payload remains unchanged.

------------------------------------------------------------------------

# 21. Failed-next-hop exclusion

The active repair context contains:

``` text
failed_next_hop = H
```

R4-C's route-update callback receives the candidate immediate
sender/next-hop.

The routing-control route-update callback shall enforce:

``` text
candidate_next_hop == H
        ↓
      reject
```

and:

``` text
candidate_next_hop != H
        ↓
      normal route update
```

This exclusion is local repair policy.

It is not encoded in the RREQ or RREP.

------------------------------------------------------------------------

# 22. Route-update ownership

R4-C remains responsible for determining when a valid RREP route-update
event occurs.

The routing-control callback is responsible for applying the E5D
failed-next-hop constraint and then invoking the existing route-table
integration.

The route table remains the authority for route state and metadata.

------------------------------------------------------------------------

# 23. Successful repair

R4-A reaching `COMPLETE` is necessary but not, by itself, sufficient for
E5D repair success.

After R4-A completion, routing-control shall verify:

``` text
route exists for destination
AND
route state == ACTIVE
AND
route next-hop != failed_next_hop
```

Only then is the repair considered successful.

------------------------------------------------------------------------

# 24. Repair failure

A repair fails when R4-A enters its failure state or when completion
does not result in an acceptable repaired route.

On failure:

``` text
destination remains STALE
```

unless another existing route-table rule independently changes it.

E5D records repair failure.

No new route state is introduced.

------------------------------------------------------------------------

# 25. Multiple repair requests

E5D may retain multiple pending repair destinations.

Example:

``` text
D10 → H2
D11 → H2
D12 → H3
```

They are processed serially:

``` text
D10
 ↓
R4 discovery
 ↓
complete/fail
 ↓
D11
 ↓
R4 discovery
 ↓
complete/fail
 ↓
D12
```

There is one active R4-A discovery.

------------------------------------------------------------------------

# 26. Duplicate suppression

Duplicate suppression remains primarily an E5D responsibility.

The existing E5D implementation reserves a destination in its bounded
pending set before publishing the queue item, preventing a task race
from creating duplicate logical repair entries. fileciteturn50file1

Routing-control additionally verifies that it has no conflicting active
discovery.

R4-A itself rejects a second start while its discovery is active.

These safeguards are complementary.

------------------------------------------------------------------------

# 27. Repeated failures

A repeated failure while a destination is already pending is suppressed
by E5D.

After a repair operation completes or fails and the pending entry is
released, a later failure can generate a new repair transaction.

There is no permanent suppression.

------------------------------------------------------------------------

# 28. Reliability boundary

Step 3 does not modify reliability.

R4 route-request identity:

``` text
route_request_id
```

is separate from ENP DATA transaction identity.

A repaired route does not create a new DATA transaction identity.

Reliability retransmission semantics remain unchanged.

------------------------------------------------------------------------

# 29. Active-discovery completion ordering

The following ordering is mandatory:

``` text
R4-C discovery_complete()
        ↓
routing_control_discovery_complete()
        ↓
enp_route_discovery_on_rrep()
        ↓
R4-A COMPLETE
        ↓
route verification
        ↓
E5D completion
        ↓
active context cleared
        ↓
next pending repair
```

The active context must not be cleared before R4-A has accepted the
completion event.

------------------------------------------------------------------------

# 30. Timeout ownership

R4-A remains the owner of discovery timeout semantics.

The resolved:

``` text
ENP_DISCOVERY_TIMEOUT_MS
```

configuration remains authoritative.

E5D shall not create a second independent discovery timeout.

------------------------------------------------------------------------

# 31. Task-context invariant

The following must never occur:

``` text
ESP-NOW callback
      ↓
R4-B/R4-C
```

or:

``` text
ESP-NOW callback
      ↓
enp_route_discovery_on_rrep()
```

Instead:

``` text
ESP-NOW callback
      ↓
RX queue
      ↓
routing-control task
      ↓
R4-B/R4-C
      ↓
R4-A completion bridge
```

------------------------------------------------------------------------

# 32. Resource limits

The design retains the existing E5D bound:

``` text
ENP_ROUTE_REPAIR_MAX_PENDING = 8
```

and requires:

``` text
one active R4-A discovery
one static routing RX queue
one static routing-control task
```

No dynamic allocation is introduced.

------------------------------------------------------------------------

# 33. Implementation audit gates

Before implementation is frozen:

### S3-I01 --- Context construction

Verify the exact structure against the current R4/E5D types.

### S3-I02 --- R4-B wiring

Compile and verify both R4-B callbacks receive the routing-control
context.

### S3-I03 --- R4-C wiring

Compile and verify all R4-C callbacks receive the routing-control
context.

### S3-I04 --- Completion bridge

Prove `discovery_complete()` reaches `enp_route_discovery_on_rrep()`.

### S3-I05 --- RREQ packet path

Verify exact E3.2.2 packet construction and `enp_transport_send()`
usage.

### S3-I06 --- RREP packet path

Verify exact RREP forwarding path.

### S3-I07 --- Failed-hop exclusion

Prove the candidate next-hop is rejected only for the active repair
originator.

### S3-I08 --- Route verification

Prove successful repair requires an `ACTIVE` route using an allowed
next-hop.

### S3-I09 --- Task context

Prove R4 processing does not execute from ESP-NOW callback context.

### S3-I10 --- Regression

Run the relevant E3.2 and E5A/E5B/E5C controlled tests unchanged.

------------------------------------------------------------------------

# 34. Controlled validation

The first Step-3 controlled validation shall prove:

1.  E5D repair request starts exactly one R4 discovery.
2.  R4-A becomes active.
3.  RREQ is constructed using the existing ENP packet path.
4.  Controlled RREP reaches R4-C.
5.  R4-C calls the completion callback.
6.  The callback invokes `enp_route_discovery_on_rrep()`.
7.  R4-A reaches `COMPLETE`.
8.  An acceptable route becomes `ACTIVE`.
9.  A candidate using the failed next-hop is rejected.
10. A valid alternative next-hop is accepted.
11. An old/insufficient-sequence RREP does not complete the discovery.
12. Discovery failure leaves the route `STALE`.
13. Multiple destinations are serviced serially.
14. Unrelated routes remain unchanged.
15. R4 processing occurs in routing-control task context.

------------------------------------------------------------------------

# 35. Hardware validation

Hardware validation remains a separate evidence level.

The controlled test must pass before hardware validation.

Hardware validation will later demonstrate:

``` text
real next-hop failure
        ↓
E5C
        ↓
E5D
        ↓
real R4 discovery
        ↓
real RREQ/RREP exchange
        ↓
failed-hop exclusion
        ↓
alternate route
        ↓
ACTIVE repaired route
```

Topology and hardware-count decisions belong in the dedicated
hardware-validation record.

------------------------------------------------------------------------

# 36. Freeze criteria

Step 3 may be frozen only when:

-   the interface compiles against the baseline;
-   all ten implementation audit gates pass;
-   controlled validation passes;
-   E3.2 regression passes;
-   E5A/E5B/E5C remain unchanged and passing;
-   no RREQ/RREP wire-format change is introduced;
-   no R4-A/B/C public semantic change is introduced;
-   resource bounds are documented;
-   task-context behaviour is verified;
-   documentation is synchronized.

Hardware validation is required before declaring P4-E5D overall
`HARDWARE VALIDATED`.

------------------------------------------------------------------------

# 37. Final interface decision

The proposed Step-3 extension is:

``` text
NEW ORCHESTRATION BOUNDARY

E5D repair coordinator
        ↓
routing-control context
        ↓
existing R4-A/B/C
        ↓
existing route table
        ↓
existing transport
```

The critical bridge is:

``` c
routing_control_discovery_complete(
    void *context,
    enp_rrep_node_t destination,
    enp_route_sequence_t destination_sequence)
```

which forwards the completion event to:

``` c
enp_route_discovery_on_rrep(...)
```

The following remain unchanged:

``` text
R4-A public API
R4-B callback signatures
R4-C callback signatures
RREQ wire format
RREP wire format
route-state contract
transport API
reliability transaction identity
E5A
E5B
E5C
```
