# E3.3.7 Phase 4 / P4-E5E
# Reliability + Route Repair Integration — Step-0 Interface / Architecture Design Audit

**Project:** ENP v0.2-r5  
**Target:** ESP-IDF 6.0.2  
**Baseline:** P4-E5D Step-3 — **HARDWARE VALIDATED / FROZEN**  
**Status:** **DESIGN / AUDIT — IMPLEMENTATION NOT STARTED**  
**Date:** 2026-08-23

---

## 1. Purpose

P4-E5E is the post-freeze phase following the successful P4-E5D Step-3
three-node hardware validation.

Its purpose is to connect:

```text
reliable DATA transaction
        |
        v
existing routing DATA path
        |
        v
E5C transport-failure / E5D route-repair path
        |
        v
repaired route
        |
        v
same reliability transaction retransmission
```

without modifying the frozen P4-E5D Step-3 implementation.

The central requirement is:

> A transport failure may trigger route repair, but the reliability transaction
> must remain the owner of DATA transaction identity, ACK correlation, timeout
> and retry accounting.

P4-E5E is therefore an **integration phase**, not a new routing protocol and not
a Step-3 adapter revision.

---

# 2. Frozen baseline

The following are explicitly frozen and must be treated as regression
baselines:

```text
P4-E5A  next-hop failure observation
P4-E5B  real ESP-NOW TX-result observation
P4-E5C  route invalidation
P4-E5D Step-3
        E5D repair coordinator
        R4 orchestration adapter
        RREQ/RREP integration
        failed-next-hop exclusion
        repair queue/task
```

The P4-E5D Step-3 source must not be modified as part of E5E.

In particular, E5E must not:

- add functionality to `enp_route_repair_adapter.*`;
- change RREQ/RREP wire structures;
- change R4-A/B/C public semantics;
- change route-table ownership;
- add another discovery state machine;
- change E5C failure semantics;
- add ESP-NOW-specific logic to reliability.

# 3. Current source-tree facts

The existing reliability layer already owns:

- fixed-size transaction storage;
- the reliable DATA packet copy;
- transaction handle;
- DATA/application sequence identity;
- ACK correlation;
- ACK timeout;
- retry count;
- retransmission;
- final `DELIVERED`, `FAILED` and `CANCELLED` states.

The existing public integration points are:

```c
enp_reliability_set_submit_callback()
enp_reliability_set_result_callback()
enp_reliability_send()
enp_reliability_process_ack()
enp_reliability_tick()
enp_reliability_get_state()
enp_reliability_get_retry_count()
enp_reliability_cancel()
```

The reliability submit callback is:

```c
typedef esp_err_t (*enp_reliability_submit_fn)(
    const enp_packet_t *packet,
    void *user_context);
```

The routing DATA path already provides:

```c
esp_err_t enp_routing_data_path_submit(
    enp_routing_data_path_t *path,
    const enp_packet_t *packet);
```

and performs current ACTIVE-route lookup on every submission.

Therefore the existing DATA submission chain is already:

```text
Reliability
    |
    | submit callback
    v
Routing DATA path
    |
    | current route lookup
    v
Transport
```

# 4. The integration problem exposed by E5D

The existing E3 reliability implementation treats a non-`ESP_OK` result from
the submit callback as a transaction failure.

For example:

```text
reliability tick
      |
      v
routing submit
      |
      +-- route ACTIVE ----> transport send
      |
      +-- route STALE -----> ESP_ERR_NOT_FOUND
                              |
                              v
                         transaction FAILED
```

That behaviour is correct for the original reliability contract, but it is not
sufficient for route repair.

During E5D repair there is a legitimate transient condition:

```text
ACTIVE
  |
  | transport failure
  v
STALE
  |
  | E5D/R4 repair
  v
ACTIVE via alternative next-hop
```

A reliability retransmission that occurs while the route is `STALE` must not
destroy the reliability transaction before E5D has had an opportunity to
restore the route.

This is the central E5E design problem.

---

# 5. Design objective

The intended E5E behaviour is:

```text
Attempt N
   |
   v
real transport failure
   |
   +--------------------+
   |                    |
   v                    v
E5C/E5D                 Reliability
route repair            transaction remains owned
   |                    |
   v                    |
route ACTIVE            |
   |                    |
   +----------+---------+
              |
              v
        retry same DATA
              |
              v
          ACK / retry
              |
              v
          DELIVERED
```

The transaction identity must remain unchanged across the repair.

# 6. Ownership model

| Responsibility | Owner |
|---|---|
| DATA transaction identity | Reliability |
| Reliable packet copy | Reliability |
| ACK correlation | Reliability |
| Retry count | Reliability |
| ACK timeout | Reliability |
| Route lookup | Routing DATA path |
| Current next-hop selection | Routing |
| Transport send | Transport |
| Transport failure observation | E5B |
| Route invalidation | E5C |
| Route repair request | E5D |
| RREQ/RREP processing | Existing R4 |
| Repaired route installation | Existing route-table/R4 integration |
| Reliability/repair coordination | **New E5E integration boundary** |

The new E5E boundary must coordinate these components without taking ownership
from them.

# 7. Candidate interface strategies

Three strategies were considered.

## A — Teach reliability about `ESP_ERR_NOT_FOUND`

Example:

```text
routing submit
    |
    +-- ESP_ERR_NOT_FOUND
            |
            v
reliability keeps transaction pending
```

### Rejected

This makes the generic reliability layer understand a routing-specific error.

It couples:

```text
Reliability -> Routing semantics
```

which violates the existing E3 architecture.

---

## B — Cancel and recreate the reliability transaction after repair

Example:

```text
failure
  |
  v
cancel transaction
  |
  v
repair
  |
  v
new enp_reliability_send()
```

### Rejected

This changes transaction identity and loses the original reliability
transaction handle/state.

It also makes ACK correlation and application-level semantics unnecessarily
complex.

---

## C — Add a generic reliability "defer/retry-now" control boundary

### Preferred direction

The reliability layer remains the owner of the transaction, but exposes a
small generic control operation allowing an external integration owner to
request:

```text
keep transaction alive
and/or
retry the same transaction now
```

The routing/E5D side never manipulates reliability transaction storage
directly.

This preserves:

```text
Reliability = transaction
Routing     = path
E5D         = repair
E5E         = coordination
```

---

# 8. Proposed E5E interface extension

The exact public API is **not frozen yet**.

The implementation audit must first determine whether the smallest sufficient
API can be expressed as one of:

```c
bool enp_reliability_retry_now(
    enp_reliability_handle_t handle,
    uint32_t now_ms);
```

or:

```c
bool enp_reliability_defer(
    enp_reliability_handle_t handle,
    uint32_t now_ms);
```

or a combined operation such as:

```c
bool enp_reliability_request_retry(
    enp_reliability_handle_t handle,
    uint32_t now_ms);
```

The final API must be selected only after auditing:

- transaction lifetime;
- handle validity;
- timeout semantics;
- retry accounting;
- submit failure semantics;
- callback/task context;
- duplicate completion;
- cancellation;
- interaction with `enp_maintenance`.

No implementation is authorized by this design document alone.

---

# 9. Preferred semantic model

The preferred semantic model is:

### During route repair

The reliability transaction remains:

```text
WAITING_FOR_ACK
```

and remains the sole owner of:

```text
packet
handle
retry_count
deadline
```

The E5D repair process does not modify those fields.

### After successful repair

The E5E integration requests a normal reliability retransmission.

That retransmission goes through the existing submit callback:

```text
Reliability
   |
   v
enp_routing_data_path_submit()
   |
   v
new ACTIVE route
   |
   v
transport
```

The packet is the same reliability-owned packet copy.

### If repair fails

The transaction is not declared delivered.

E5E must return control to the normal reliability failure policy rather than
inventing a second retry algorithm.

---

# 10. How E5D completion reaches E5E

The frozen Step-3 adapter already knows when a repair completes successfully.

E5E must consume a **notification**, not inspect E5D internal state.

The preferred conceptual boundary is:

```c
typedef void (*enp_route_repair_result_fn)(
    enp_route_destination_t destination,
    bool success,
    void *context);
```

The exact callback signature is **not frozen**.

The implementation audit must first establish the smallest completion/failure
notification boundary that can be added without changing the frozen Step-3
adapter semantics.

If the existing E5D API already exposes a suitable completion observation
point, E5E should reuse it rather than add another callback.

---

# 11. Correlation problem

The central E5E correlation question is:

> Which reliability transaction should be retried when a route repair completes?

The route-repair event contains:

```text
destination
```

while reliability owns:

```text
handle
destination
DATA sequence
application sequence
```

The preferred correlation key is the reliable DATA destination, with an
integration-owned bounded map:

```text
route destination
        |
        v
active reliability handle(s)
```

However, the implementation audit must determine whether multiple active
reliable transactions to the same destination are possible.

If they are possible, destination-only correlation is insufficient.

The audit must therefore establish one of:

1. one active reliable transaction per destination;
2. bounded destination → transaction-list correlation;
3. an explicit transaction-to-repair association created when the first
   transport failure triggers E5C/E5D.

The third option is the most general, but must not duplicate reliability
transaction ownership.

---

# 12. Important asynchronous boundary

E5C currently receives transport failure information in the transport
send-result callback context.

E5D already moves repair work through its bounded static queue/task.

E5E must preserve that boundary:

```text
ESP-NOW task / transport callback
        |
        v
E5C
        |
        v
E5D repair request
        |
        v
E5D repair task
        |
        v
R4 discovery
        |
        v
E5E repair-result notification
        |
        v
Reliability control operation
```

No blocking operation is permitted in:

```text
ESP-NOW callback
E5C callback
```

The existing E5D task/queue remains frozen and is not extended with new
responsibilities unless a separately approved interface requires it.

---

# 13. Repair-failure semantics

E5E must explicitly distinguish:

```text
repair SUCCESS
repair FAILURE
repair still ACTIVE
```

### Repair SUCCESS

The route is verified ACTIVE and does not use the failed next-hop.

E5E may request a reliability retry.

### Repair FAILURE

The route remains unavailable/STALE according to the frozen E5D behaviour.

E5E must not fabricate a route or mark the DATA delivered.

The reliability transaction eventually reaches its normal FAILED state according
to its defined policy.

### Repair ACTIVE

No reliability transaction completion or delivery result is generated.

---

# 14. No reliability timer reset by E5D

E5D must not directly manipulate the reliability deadline.

The final E5E API must define explicitly whether:

```text
repair active
```

causes:

```text
deadline preserved
```

or:

```text
deadline deferred by an explicit reliability API
```

The decision must be made at the E5E audit stage.

It must not be implemented implicitly inside E5D.

---

# 15. Static resource policy

The existing project policy remains mandatory.

E5E must use:

```text
static transaction correlation state
static queues if required
static tasks only if required
bounded tables
no heap allocation
```

No new unbounded association table may be introduced.

The maximum correlation capacity must be derived from:

```text
ENP_RELIABILITY_MAX_TRANSACTIONS
```

rather than invented independently.

---

# 16. Proposed E5E controlled test architecture

The first implementation test must be hardware-independent.

It should contain:

```text
controlled transport
controlled route table
frozen E5C
frozen E5D Step-3
real reliability implementation
E5E integration boundary
```

The test must reproduce:

```text
1. reliable DATA transaction created
2. initial route is A -> B
3. initial submission succeeds
4. transport reports failure to B
5. E5C marks route STALE
6. E5D starts repair
7. repair creates route A -> C
8. E5D reports repair success
9. E5E identifies the correct reliability transaction
10. same transaction is retransmitted through current route A -> C
11. ACK is delivered
12. transaction becomes DELIVERED
```

---

# 17. Mandatory controlled negative tests

The E5E controlled test must also prove:

### Negative 1 — repair failure

```text
failure
  -> repair fails
  -> no fabricated route
  -> transaction does not become DELIVERED
```

### Negative 2 — wrong destination

A repair completion for another destination must not retry the transaction.

### Negative 3 — stale/old completion

A completion event for an old repair operation must not retry a newer
transaction incorrectly.

### Negative 4 — duplicate completion

The same repair-success event twice must not cause two reliability
retransmissions.

### Negative 5 — already completed transaction

A repair-success event arriving after ACK completion must be harmless.

### Negative 6 — retry exhaustion

Normal reliability retry accounting must remain bounded and deterministic.

### Negative 7 — unrelated route

Repair of another destination must not alter the transaction.

# 19. Hardware phase — explicitly deferred

No hardware implementation is authorized until the controlled E5E test passes.

The later hardware test must use:

```text
A / Gateway
B / failed next-hop
C / repaired alternative
```

and demonstrate:

```text
real reliable DATA
    ↓
real TX failure
    ↓
E5C invalidation
    ↓
E5D real repair
    ↓
same reliability transaction retransmission
    ↓
real ACK
    ↓
DELIVERED
```

The hardware phase must additionally verify that the retransmission uses the
repaired route rather than the failed next-hop.

P4-E5E does not implement:

- new routing states;
- multi-path routing;

- new transport APIs;

- application-level retry policy;
- ACK protocol changes;
- fragmentation;

# 23. Decision

**P4-E5E is approved as the next architectural work item, but implementation is
NOT YET AUTHORIZED.**

The next action is the **E5E implementation audit**, beginning with:

1. exact reliability transaction lifetime during an active repair;
2. exact timeout/retry behaviour;
3. minimal generic reliability control API;
4. repair-result notification boundary;
5. transaction/repair correlation.

Only after those questions are resolved should the controlled E5E test be
implemented.

The P4-E5D Step-3 source remains frozen throughout this work.
