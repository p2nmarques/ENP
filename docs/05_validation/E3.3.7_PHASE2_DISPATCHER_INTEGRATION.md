# E3.3.7 — Phase 2 Dispatcher Integration

**Target:** ESP-IDF 6.0.2  
**Status:** Corrected after first real-ESP self-test

## Result of first hardware run

The first Phase 2 hardware run passed all checks except the final retry-transaction completion check.

The failure was in the **test stimulus**, not in the reliability ACK correlation path.

The first transaction used:

- DATA sequence `TEST_DATA_SEQUENCE`
- application sequence `TEST_APP_SEQUENCE`
- ACK sequence `TEST_ACK_SEQUENCE`

The duplicate ACK was deliberately dispatched twice. The ENP dispatcher correctly recorded the first ACK in its duplicate cache and suppressed the second identical ACK.

The test then reused the **same DATA/ACK packet identity** for a second reliability transaction. Consequently, the dispatcher correctly classified the ACK as an already-seen duplicate and did not invoke the reliability ACK service for the second transaction.

This is consistent with the existing dispatcher contract: duplicate suppression occurs before service dispatch.

## Correction

The second reliability transaction now has a distinct transaction identity:

```text
DATA sequence       = TEST_DATA_SEQUENCE + 1
application sequence = TEST_APP_SEQUENCE + 1
ACK sequence        = TEST_ACK_SEQUENCE + 1
```

The retry itself remains identical to its own initial DATA submission.

This preserves the intended test semantics:

```text
Transaction 1
    DATA #1
       |
       +--> ACK #1
       +--> duplicate ACK #1 suppressed

Transaction 2
    DATA #2
       |
       +--> timeout
       +--> identical DATA #2 retransmission
       +--> ACK #2
       +--> reliability transaction DELIVERED
```

## Architectural conclusion

No change is made to the dispatcher duplicate cache.

No change is made to the reliability ACK correlation algorithm.

No protocol change is introduced.

The correction only ensures that the test represents two distinct ENP transactions while still testing duplicate ACK suppression correctly.
