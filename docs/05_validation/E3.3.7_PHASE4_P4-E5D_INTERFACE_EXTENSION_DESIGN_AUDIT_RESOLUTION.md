# E3.3.7 Phase 4 — P4-E5D Interface Extension Design / Audit Resolution

**Status:** PROPOSED — DESIGN FOR APPROVAL  
**Contract:** P4-E5D Route Repair / Rediscovery Integration — FROZEN  
**Baseline:** `ENP-0.2-r5(20260818-183327)`  
**Target:** ESP-IDF 6.0.2

---

## 1. Purpose

This document resolves the implementation gaps identified by the P4-E5D
implementation audit against the actual R4 source tree.

It does **not** implement E5D.

Its purpose is to define the smallest architecture-compatible interface
extension required to integrate:

```text
P4-E5C route invalidation
        |
        v
P4-E5D repair coordination
        |
        v
existing R4 route discovery
        |
        v
existing route-table integration
        |
        v
normal routing DATA path
```

The design preserves the frozen E5D contract and the already validated E5A,
E5B and E5C boundaries.

No existing implementation is to be modified until this design is approved.

---

# 2. Audit findings being resolved

The source audit established the following facts.

| Audit item | Actual baseline | Resolution |
|---|---|---|
| Route states | `INVALID`, `ACTIVE`, `STALE`; `INVALID` is used for unused table slots | Preserve exactly; E5D never uses `INVALID` as an operational state |
| R4 discovery | `enp_route_discovery_t` supports one active discovery transaction | Reuse it; add E5D coordination around it |
| R4 start API | `enp_route_discovery_start(...)` has no failed-next-hop parameter | Keep R4 API unchanged |
| Failed-next-hop exclusion | No existing R4 exclusion API | Enforce exclusion at RREP-derived route installation for the repair originator |
| RREP integration | Callback-based `update_route()` and `discovery_complete()` | Reuse callbacks through an E5D-owned integration context |
| Route freshness | `enp_route_table_update()` replaces an entry but does not compare sequence freshness | Add freshness decision in the RREP route-update integration callback, not in R4 |
| Duplicate discovery | R4 rejects a second `REQUESTING` transaction | E5D provides bounded duplicate repair suppression |
| RERR | R4-D validates and invalidates routes; no production repair coordinator exists | E5D does not create a new RERR subsystem |
| Routing task | No production repair task/queue exists | Add one bounded static E5D repair task/queue |
| Reliability | Reliability owns transaction/timer/retry state; initial submit failure currently fails transaction | Do not change reliability semantics in E5D; trigger repair from E5C failure before retransmission |
| Transport | ENP transport already exposes asynchronous TX-result callback | Reuse E5C boundary; no new transport API |
| Route discovery timing | `enp_route_discovery.h` defines 2000 ms; `enp_defaults.h` defines 6000 ms | Resolve configuration ownership before implementation |

---

# 3. Design principles

The implementation shall follow these rules:

1. Do not redesign R4.
2. Do not modify the ENP wire format.
3. Do not add `INVALID` or `REPAIRING` as operational route states.
4. Do not modify the frozen E5A/E5B/E5C interfaces.
5. Do not add ESP-NOW-specific routing code.
6. Do not modify reliability transaction identity.
7. Do not reset the reliability retransmission timer because of repair.
8. Do not make R4 depend on FreeRTOS.
9. Keep all new E5D state statically allocated and bounded.
10. Keep route-table ownership with `enp_route_table`.
11. Keep RREQ/RREP protocol processing with R4.
12. Keep DATA submission with `enp_routing_data_path`.
13. Use the smallest integration layer capable of coordinating these existing
    components.

---

# 4. Proposed E5D integration component

Introduce one new routing integration component:

```text
main/core/routing/enp_route_repair.h
main/core/routing/enp_route_repair.c
```

The component is a **coordinator**, not a second routing protocol.

Its responsibilities are:

- accept a repair request;
- suppress duplicate requests for the same destination;
- retain the failed next-hop constraint;
- start the existing R4 discovery transaction;
- provide the R4 integration callbacks;
- reject a repaired route that selects the known failed next-hop;
- recognize discovery completion;
- coordinate bounded repair failure;
- expose repair progress to the production routing context.

It shall not:

- build RREQ packets itself;
- process RREQ packets itself;
- process RREP packets itself;
- install routes directly outside the existing route-table callback boundary;
- send DATA;
- call ESP-NOW APIs;
- own reliability transactions.

---

# 5. Proposed E5D state model

The persistent route-table state remains:

```text
ACTIVE
STALE
```

E5D operation state is separate:

```text
IDLE
REQUESTED
DISCOVERING
COMPLETED
FAILED
```

These are **repair-operation states**, not route-table states.

The route table therefore remains:

```text
ACTIVE
   |
   | E5C transport failure
   v
STALE
   |
   | successful E5D/R4 repair
   v
ACTIVE
```

No `INVALID` route transition is introduced by E5D.

---

# 6. Repair request boundary

The conceptual request remains:

```text
repair(destination, failed_next_hop)
```

The proposed C-level interface is:

```c
bool enp_route_repair_request(
    enp_route_repair_t *repair,
    enp_route_destination_t destination,
    enp_route_destination_t failed_next_hop,
    uint32_t now_ms);
```

This API is intentionally owned by E5D rather than R4.

The failed next-hop is a routing identity:

```c
enp_route_destination_t
```

not an ESP-NOW MAC address.

The transport address has already been translated into the logical next-hop
identity by the existing E5C/routing integration boundary.

---

# 7. Why the repair request is triggered by E5C

The existing reliability implementation treats a non-`ESP_OK` initial or
retransmission submit result as transaction failure.

Therefore E5D must not wait until the next reliability retransmission and then
change the reliability semantics.

The preferred sequence is:

```text
DATA transmission
      |
      v
real ESP-NOW TX failure
      |
      v
E5B TX-result observation
      |
      v
E5C route invalidation
      |
      v
E5D repair request
      |
      v
R4 discovery
      |
      v
route restored
      |
      v
normal reliability retransmission
```

This preserves the existing reliability layer as the owner of:

- transaction identity;
- retry count;
- ACK timeout;
- retransmission;
- final result.

No new reliability API is required for the basic E5D repair path.

---

# 8. E5C → E5D integration extension

The existing E5C callback currently invalidates all active routes whose logical
next-hop resolves to the failed transport address.

E5D should receive the same logical failure information after invalidation.

The smallest extension is a routing-path repair callback:

```c
typedef void (*enp_routing_route_failure_fn)(
    void *context,
    enp_route_destination_t destination,
    enp_route_destination_t failed_next_hop);
```

and an optional registration member in:

```c
enp_routing_data_path_t
```

The callback is invoked once for each affected route after that route has been
transitioned to `STALE`.

The callback is a notification boundary only.

It does not perform repair inline.

---

# 9. Callback execution rule

The existing E5B/E5C transport callback must remain lightweight.

Therefore:

```text
transport callback
       |
       v
E5C invalidation
       |
       v
bounded repair request event
       |
       v
E5D repair task
       |
       v
R4 discovery
```

No RREQ/RREP processing or blocking discovery work is permitted inside the
transport callback.

---

# 10. Bounded repair coordination

R4 currently permits only one active discovery transaction.

E5D therefore acts as the bounded coordinator above R4.

Proposed capacity:

```c
#define ENP_ROUTE_REPAIR_MAX_PENDING 8U
```

Rationale:

- the existing reliability layer permits `ENP_RELIABILITY_MAX_TRANSACTIONS == 8`;
- this gives E5D a deterministic upper bound matching the maximum number of
  simultaneously outstanding reliable DATA transactions;
- R4 remains single-discovery;
- pending repairs are processed sequentially.

The implementation must not dynamically grow this queue.

Duplicate requests for the same destination while a repair is already pending
or active shall collapse into the existing repair operation.

---

# 11. Failed-next-hop exclusion

The audit confirmed that R4 has no failed-next-hop exclusion parameter.

The wire format shall **not** be changed to add one.

Instead, E5D shall carry the exclusion as local repair context:

```text
repair destination
failed next-hop
```

When the originator receives an RREP, the existing R4-C processor provides:

```text
previous_hop
```

which is the immediate next-hop toward the RREP destination.

The E5D route-update integration callback shall reject:

```text
previous_hop == failed_next_hop
```

for the active repair destination.

This gives:

```text
RREP
  |
  v
R4-C
  |
  v
E5D route-update adapter
  |
  +--> failed next-hop? ---- yes --> reject candidate
  |
  +--> acceptable ---------> existing route-table update
```

No R4 wire-format change is required.

---

# 12. Important limitation of the exclusion mechanism

The exclusion is local to the node performing repair.

It does not modify the RREQ wire payload and does not instruct remote nodes
to avoid the failed next-hop.

This is intentional.

The requirement being enforced is:

> the repaired route installed at the repairing node must not select the known
> failed next-hop.

If the current R4 behaviour proves unable to produce an alternative route
under real multi-hop hardware validation, that is a validation result and must
trigger a separate R4 architecture review rather than an undocumented E5D
wire-format extension.

---

# 13. R4 API remains unchanged

The following existing R4 API remains authoritative:

```c
bool enp_route_discovery_start(
    enp_route_discovery_t *discovery,
    enp_discovery_destination_t destination,
    uint32_t route_request_id,
    uint32_t destination_sequence,
    uint8_t ttl,
    uint32_t now_ms);
```

E5D maps:

```text
enp_route_destination_t
```

to:

```text
enp_discovery_destination_t
```

and supplies:

- a locally allocated non-zero route request ID;
- the current route sequence;
- a bounded TTL;
- the current ENP time.

E5D does not add a failed-next-hop parameter to this function.

---

# 14. RREP completion integration

The existing R4-C callback:

```c
enp_rrep_discovery_complete_fn
```

is the correct completion boundary.

E5D shall provide the callback context.

On completion:

```text
RREP accepted
    |
    v
route update accepted
    |
    v
discovery_complete()
    |
    v
E5D marks repair COMPLETED
```

The normal route-table representation is used.

No E5D-specific route entry is created.

---

# 15. Route freshness resolution

The audit confirmed that:

```c
enp_route_table_update()
```

does not itself perform sequence-number freshness comparison.

Therefore E5D shall not silently assume that `update()` is a freshness policy.

The RREP integration adapter shall:

1. obtain the current route entry;
2. compare the candidate RREP destination sequence with the installed route
   sequence using the existing routing serial-number semantics;
3. accept the candidate only when permitted by the existing routing protocol;
4. preserve the existing route metadata policy;
5. call `enp_route_table_update()` only after the routing decision is made.

This is an integration correction, not a second sequence-number algorithm.

The comparison logic must be factored into one reusable routing helper if the
same decision is needed elsewhere; it must not be duplicated between E5D and
R4.

---

# 16. Repair completion versus route installation

These remain separate events:

```text
RREP route candidate accepted
        |
        v
route-table update
        |
        v
usable ACTIVE route
        |
        v
E5D repair completion
```

E5D shall only report repair success after a usable ACTIVE route exists.

---

# 17. Repair failure

R4's existing timeout/retry state remains authoritative.

When R4 reaches:

```text
ENP_DISCOVERY_STATE_FAILED
```

E5D marks the corresponding repair operation failed.

E5D shall not:

- add a new route state;
- start an unbounded retry loop;
- modify R4 retry constants;
- generate a second discovery protocol.

RERR remains governed by the existing R4-D boundary.

---

# 18. RERR interaction

E5D does not create or modify the RERR packet format.

The relationship is:

```text
repair fails
    |
    v
existing routing failure policy
    |
    v
existing RERR behaviour where applicable
```

If an existing production RERR propagation path is not available, E5D shall not
invent one as part of this interface extension.

---

# 19. Reliability integration decision

No E5D-specific reliability transaction API is required for the first
implementation.

The intended behaviour is:

```text
T0  DATA sent using route A
T1  TX failure observed
T1  route A -> STALE
T1  E5D repair starts
T2  route repaired
T3  reliability retransmission uses the same stored DATA packet
T4  same ENP DATA transaction identity is preserved
```

The reliability retransmission timer remains owned by reliability.

E5D must never reset it.

If repair is slower than the existing reliability timeout, the resulting
reliability failure is an existing reliability outcome and must not be hidden
by E5D.

A later phase may explicitly redesign this interaction if required, but E5D
must not silently change reliability timing semantics.

---

# 20. Transaction identity

The reliability transaction retains:

```text
ENP DATA packet sequence
application sequence
source
destination
retry count
transaction handle
```

The repair operation has its own local:

```text
route_request_id
```

These identifiers are independent.

```text
ENP DATA transaction identity
        !=
RREQ route-discovery identity
        !=
E5D repair-operation identity
```

No identifier is reused across these layers.

---

# 21. Repair task and static queue

The proposed E5D coordinator owns:

```text
StaticQueue_t
static queue storage
StaticTask_t
static task stack
```

The queue carries a bounded repair event containing:

```text
destination
failed_next_hop
```

The task performs:

```text
request dequeue
    |
    v
R4 start
    |
    v
RREQ/RREP integration
    |
    v
completion/failure
```

R4 itself remains FreeRTOS-independent.

---

# 22. Maintenance integration

The existing maintenance task already invokes:

```c
enp_reliability_tick(now_ms);
```

and performs neighbor/service maintenance.

E5D shall not create a second periodic timer mechanism merely to drive R4.

Instead, the E5D repair task shall use the existing ENP time source and invoke
R4 timeout processing for its active discovery.

This keeps discovery timing local to the repair coordinator while retaining
R4's state machine as the authority.

---

# 23. Discovery timing must be resolved before implementation

The baseline currently contains:

```text
enp_route_discovery.h
    ENP_DISCOVERY_TIMEOUT_MS = 2000 ms

enp_defaults.h
    ENP_DISCOVERY_TIMEOUT_MS = 6000 ms
```

and:

```text
ENP_MAX_RETRIES = 3
```

The source tree therefore has a configuration ownership inconsistency.

Before implementation:

1. select the authoritative configuration location;
2. remove the duplicate fallback definition;
3. ensure R4 tests use the authoritative value;
4. document the resulting value;
5. do not change the value merely to make E5D tests pass.

This is an **R4 configuration cleanup gate**, not an E5D behavioural change.

---

# 24. Route repair trigger policy

E5D shall repair a route when:

```text
route is STALE
AND
a routing operation has established that the destination needs a usable route
```

For the E5C transport-failure path, the failed transmission itself establishes
that the route was required, so E5D may immediately queue repair.

This avoids waiting for reliability to rediscover the problem.

For unrelated stale routes created only by route expiration, E5D does not
proactively repair every stale entry.

---

# 25. Multiple destinations sharing one failed next-hop

E5C may stale several routes:

```text
D10 -> N2
D11 -> N2
D12 -> N3
```

A failure of N2 creates:

```text
D10 -> STALE
D11 -> STALE
D12 -> ACTIVE
```

E5D creates at most:

```text
repair(D10, N2)
repair(D11, N2)
```

and never:

```text
repair(D12, N2)
```

Repairs are destination-specific.

The bounded pending queue prevents uncontrolled parallel discovery.

---

# 26. Duplicate repair suppression

The uniqueness key is:

```text
destination
```

A second request for a destination already:

```text
PENDING
or
DISCOVERING
```

does not create another R4 transaction.

If the failed-next-hop differs while the same destination is already being
repaired, the implementation shall retain the most recent failure constraint
only if it can prove that doing so cannot weaken the active repair. Otherwise the
request remains coalesced and the existing failure context is retained.

This policy must be covered by controlled validation.

---

# 27. Route-table ownership

E5D shall never manipulate:

```text
table->entries[]
table->count
```

directly.

All route state changes must use the existing route-table API or the
existing R4 callback integration boundary.

The route table remains authoritative for persistent route state.

---

# 28. No changes to validated boundaries

The following remain unchanged:

```text
P4-E5A
    next-hop failure observation boundary

P4-E5B
    real ESP-NOW TX-result observation

P4-E5C
    transport failure -> route STALE
```

E5D only consumes the routing-level consequence of E5C.

---

# 29. Proposed interface summary

### New component

```text
enp_route_repair.h/.c
```

### New E5D API

```c
bool enp_route_repair_init(
    enp_route_repair_t *repair,
    enp_route_table_t *routes,
    enp_route_discovery_t *discovery,
    uint16_t local_network_id,
    uint16_t local_node_id);

bool enp_route_repair_request(
    enp_route_repair_t *repair,
    enp_route_destination_t destination,
    enp_route_destination_t failed_next_hop,
    uint32_t now_ms);

void enp_route_repair_tick(
    enp_route_repair_t *repair,
    uint32_t now_ms);

bool enp_route_repair_is_pending(
    const enp_route_repair_t *repair,
    enp_route_destination_t destination);
```

The exact callback types and R4 integration adapter signatures shall be
finalized during implementation after confirming all production call sites.

### Routing-path extension

```c
typedef void (*enp_routing_route_failure_fn)(
    void *context,
    enp_route_destination_t destination,
    enp_route_destination_t failed_next_hop);
```

and registration during `enp_routing_data_path_init()` or through a dedicated
setter, with the latter preferred if preserving existing call sites is the
smaller change.

No existing public E5A/E5B/E5C API is changed.

# 30. Implementation sequence

Implementation shall proceed in this order:

1. Resolve discovery timing/configuration ownership.
2. Add `enp_route_repair.h/.c`.
3. Add the bounded static repair queue/task.
4. Add the E5C route-failure notification boundary.
5. Connect E5D to the existing R4 discovery state machine.
6. Add the RREP route-update integration adapter.
7. Add failed-next-hop exclusion.
8. Add route freshness decision at the existing routing integration boundary.
9. Add R4 completion/failure propagation.
10. Add controlled self-test.
11. Full-clean build.
12. Controlled validation.
13. Hardware validation.
14. Documentation synchronization.
15. Freeze only after the required evidence passes.

---

# 31. Controlled validation requirements

Before hardware validation, the controlled test must demonstrate at minimum:

- E5C failure produces one repair request per affected destination;
- duplicate repair requests are suppressed;
- multiple affected destinations are handled independently;
- unrelated active routes remain unchanged;
- failed-next-hop candidate is rejected;
- acceptable RREP route candidate is accepted;
- successful repair produces a normal ACTIVE route;
- route sequence semantics are preserved;
- R4 timeout/retry bounds are respected;
- repair failure produces existing routing failure semantics;
- no `INVALID` operational route state is introduced;
- no `REPAIRING` route-table state is introduced;
- no ESP-NOW API is referenced by E5D;
- no reliability transaction identity is modified;
- no reliability retransmission timer is reset;
- E5D uses bounded/static resources.

# 34. Architecture decision

The recommended architecture is:

```text
                    ┌──────────────────────┐
                    │ Reliability          │
                    │ transaction/retry    │
                    └──────────┬───────────┘
                               │ DATA
                               v
                    ┌──────────────────────┐
                    │ Routing Data Path    │
                    │ route selection      │
                    └──────────┬───────────┘
                               │
                    transport TX result
                               │
                               v
                    ┌──────────────────────┐
                    │ E5C                  │
                    │ route -> STALE       │
                    └──────────┬───────────┘
                               │ repair event
                               v
                    ┌──────────────────────┐
                    │ E5D Repair           │
                    │ coordinator          │
                    │ static queue/task    │
                    └──────────┬───────────┘
                               │
                               v
                    ┌──────────────────────┐
                    │ R4 Discovery         │
                    │ R4-A / R4-B / R4-C   │
                    └──────────┬───────────┘
                               │
                               v
                    ┌──────────────────────┐
                    │ Route-table          │
                    │ ACTIVE / STALE       │
                    └──────────────────────┘
```

This adds one integration coordinator without creating a second routing
protocol, route table, transport path, or reliability mechanism.

---

# 35. Design decision

**P4-E5D Interface Extension Design: PROPOSED FOR APPROVAL**

The design is intentionally smaller than a redesign of R4.

The only new architectural responsibility is:

> **E5D coordinates repair; R4 performs discovery; the existing route-table
> integration installs the resulting route; reliability remains unchanged.**

No implementation should begin until this design is approved.
