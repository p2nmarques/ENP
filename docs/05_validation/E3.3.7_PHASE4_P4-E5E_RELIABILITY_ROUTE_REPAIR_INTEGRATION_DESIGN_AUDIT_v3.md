## 1. Purpose

P4-E5E is the post-freeze phase following the successful P4-E5D Step-3
three-node hardware validation.

Its purpose is to connect:

```text
reliable DATA transaction
        |
        v
existing routing DATA path
        |
        v
E5C transport-failure / E5D route-repair path
        |
        v
repaired route
        |
        v
same reliability transaction retransmission
```

without modifying the frozen P4-E5D Step-3 implementation.

The central requirement is:

> A transport failure may trigger route repair, but the reliability transaction
> must remain the owner of DATA transaction identity, ACK correlation, timeout
> and retry accounting.

P4-E5E is therefore an **integration phase**, not a new routing protocol and not
a Step-3 adapter revision.

- change R4-A/B/C public semantics;

- add another discovery state machine;

# 2. Current source-tree facts

The existing reliability layer already owns:

- fixed-size transaction storage;
- the reliable DATA packet copy;
- transaction handle;
- DATA/application sequence identity;
- ACK correlation;
- ACK timeout;
- retry count;
- retransmission;
- final `DELIVERED`, `FAILED` and `CANCELLED` states.

The existing public integration points are:

```c
enp_reliability_set_submit_callback()
enp_reliability_set_result_callback()
enp_reliability_send()
enp_reliability_process_ack()
enp_reliability_tick()
enp_reliability_get_state()
enp_reliability_get_retry_count()
enp_reliability_cancel()
```

The reliability submit callback is:

```c
typedef esp_err_t (*enp_reliability_submit_fn)(
    const enp_packet_t *packet,
    void *user_context);
```

The routing DATA path already provides:

```c
esp_err_t enp_routing_data_path_submit(
    enp_routing_data_path_t *path,
    const enp_packet_t *packet);
```

and performs current ACTIVE-route lookup on every submission.

Therefore the existing DATA submission chain is already:

```text
Reliability
    |
    | submit callback
    v
Routing DATA path
    |
    | current route lookup
    v
Transport
```

# 3. The integration problem exposed by E5D

The existing E3 reliability implementation treats a non-`ESP_OK` result from
the submit callback as a transaction failure.

For example:

```text
reliability tick
      |
      v
routing submit
      |
      +-- route ACTIVE ----> transport send
      |
      +-- route STALE -----> ESP_ERR_NOT_FOUND
                              |
                              v
                         transaction FAILED
```

That behaviour is correct for the original reliability contract, but it is not
sufficient for route repair.

During E5D repair there is a legitimate transient condition:

```text
ACTIVE
  |
  | transport failure
  v
STALE
  |
  | E5D/R4 repair
  v
ACTIVE via alternative next-hop
```

A reliability retransmission that occurs while the route is `STALE` must not
destroy the reliability transaction before E5D has had an opportunity to
restore the route.

This is the central E5E design problem.

---

# 4. Design objective

The intended E5E behaviour is:

```text
Attempt N
   |
   v
real transport failure
   |
   +--------------------+
   |                    |
   v                    v
E5C/E5D                 Reliability
route repair            transaction remains owned
   |                    |
   v                    |
route ACTIVE            |
   |                    |
   +----------+---------+
              |
              v
        retry same DATA
              |
              v
          ACK / retry
              |
              v
          DELIVERED
```

The transaction identity must remain unchanged across the repair.

| Responsibility | Owner |

| DATA transaction identity | Reliability |

| ACK correlation | Reliability |
| Retry count | Reliability |

The new E5E boundary must coordinate these components without taking ownership

# 6. Candidate interface strategies

Three strategies were considered.

## A — Teach reliability about `ESP_ERR_NOT_FOUND`

Example:

```text
routing submit
    |
    +-- ESP_ERR_NOT_FOUND
            |
            v
reliability keeps transaction pending
```

### Rejected

This makes the generic reliability layer understand a routing-specific error.

It couples:

```text
Reliability -> Routing semantics
```

which violates the existing E3 architecture.

---

## B — Cancel and recreate the reliability transaction after repair

Example:

```text
failure
  |
  v
cancel transaction
  |
  v
repair
  |
  v
new enp_reliability_send()
```

### Rejected

This changes transaction identity and loses the original reliability
transaction handle/state.

It also makes ACK correlation and application-level semantics unnecessarily
complex.

---

## C — Add a generic reliability "defer/retry-now" control boundary

### Preferred direction

The reliability layer remains the owner of the transaction, but exposes a
small generic control operation allowing an external integration owner to
request:

```text
keep transaction alive
and/or
retry the same transaction now
```

The routing/E5D side never manipulates reliability transaction storage
directly.

This preserves:

```text
Reliability = transaction
Routing     = path
E5D         = repair
E5E         = coordination
```

---

# 7. Resolved E5E interface direction

The E5E interface is **not** a generic `retry_now()` command.

The resolved semantic model is:

```text
transport failure
      |
      v
transaction associated with repair
      |
      v
REPAIR_PENDING
      |
      | repair SUCCESS
      v
resume same reliability transaction
      |
      v
normal reliability retransmission
```

The reliability layer remains the owner of:

- transaction identity;
- packet storage;
- retry accounting;
- ACK correlation;
- retry eligibility;
- final transaction result.

E5E may request a state transition from `REPAIR_PENDING` back to the normal
retransmission path, but E5E must not manipulate reliability transaction
storage or retry counters directly.

The exact C API name/signature remains an implementation-audit item. The
semantic contract is frozen first:

```text
enter repair pending
resume after verified repair
```

A `retry_now()` API is explicitly rejected as the architectural abstraction
because it would expose retry-policy semantics outside Reliability.

---

# 8. Resolved reliability state model

The reliability transaction shall explicitly represent the route-repair hold:

```text
CREATED
   |
   v
WAITING_FOR_ACK
   |
   | correlated transport failure / repair accepted
   v
REPAIR_PENDING
   |
   +-----------------------+
   |                       |
 repair SUCCESS         repair FAILURE
   |                       |
   v                       v
WAITING_FOR_ACK          FAILED
   |
   | ACK
   v
DELIVERED
```

`REPAIR_PENDING` is a **Reliability state**, not a routing state.

E5D does not create, own, or modify this state.

While `REPAIR_PENDING`:

- the reliability packet remains unchanged;
- the reliability handle remains unchanged;
- the retry count remains owned by Reliability;
- the transaction cannot be completed as DELIVERED;
- normal ACK timeout expiry must not independently destroy the transaction;
- Reliability must not submit duplicate DATA merely because its ordinary timer
  fires while repair is active.

The precise timer representation is an implementation detail, but the semantic
rule is frozen:

> **An active, correlated repair temporarily suspends normal ACK-timeout
> failure progression without resetting or consuming the reliability retry
> budget.**

When repair succeeds, Reliability resumes through its normal retransmission
path. The retry budget is consumed only by an actual retransmission attempt.

---

# 9. Resolved repair-operation identity

A repair completion must identify the **repair operation**, not merely the
destination.

The conceptual repair record is:

```text
repair_id
destination
failed_next_hop
status
```

The exact structure and width of `repair_id` remain implementation-audit
details.

The semantic requirements are frozen:

1. every repair operation has a bounded identity;
2. a completion must carry that identity;
3. duplicate completion for the same identity is idempotent;
4. completion for an old identity cannot complete a newer repair;
5. E5E must never infer repair identity from destination alone.

E5E consumes a completion notification. It does not inspect E5D internals and
does not change the frozen Step-3 state machine.

The preferred conceptual notification is therefore:

```text
repair completion
    |
    +-- repair_id
    +-- destination
    +-- status
    |
    v
E5E
```

The exact callback signature remains open until the implementation audit has
confirmed the existing E5D observation point and context/ownership constraints.

If an existing E5D completion observation already carries an adequate operation
identity, it must be reused rather than introducing a second identity.

---

# 10. Resolved failure-to-transaction correlation

Destination-only correlation is **rejected**.

The architecture shall associate the reliability transaction with the repair
operation at the moment the transport failure is correlated with the
transaction.

Conceptually:

```text
Reliability transaction T17
        |
        | failed route attempt
        v
E5E correlation record
        |
        +-- reliability handle = T17
        +-- destination = C
        +-- failed next-hop = B
        +-- repair_id = R42
        |
        v
E5D repair(R42)
        |
        v
repair complete(R42)
        |
        v
E5E
        |
        v
Reliability T17 -> resume
```

This creates an explicit:

```text
transaction <-> repair operation
```

association.

The correlation record is **integration state**, not a second copy of the
Reliability transaction.

E5E must not own:

- the DATA packet;
- ACK state;
- retry count;
- transaction lifetime.

The existing packet/transaction identity should be reused where the source
implementation proves it is sufficient. A new packet identity or wire-format
field is not permitted merely to solve correlation.

If the existing packet identity cannot safely provide the required correlation,
the bounded internal `repair_id` association is the fallback.

---

# 12. Multiple transactions to the same destination

The architecture explicitly supports:

```text
T1 -> C
T2 -> C
T3 -> D
```

simultaneously.

Destination is therefore an attribute, not a unique key.

The minimum E5E correlation unit is:

```text
repair_id <-> exactly one reliability transaction
```

not:

```text
destination -> one transaction
```

Multiple transactions to the same destination may exist.

A repair completion for `C` is therefore insufficient by itself to select a
transaction.

Example:

```text
T1 -> C, repair R41
T2 -> C, repair R42

R41 SUCCESS
```

Expected:

```text
T1 resumes
T2 remains unchanged
```

Then:

```text
R42 SUCCESS
```

Expected:

```text
T2 resumes
```

This rule prevents accidental cross-completion.

If the implementation discovers that a single route repair legitimately serves
multiple reliability transactions, E5E may associate multiple transaction
records with the same `repair_id`. That association must still be explicit and
bounded; destination-only matching remains prohibited.

---

# 12. Important asynchronous boundary

E5C currently receives transport failure information in the transport
send-result callback context.

E5D already moves repair work through its bounded static queue/task.

E5E must preserve that boundary:

```text
ESP-NOW task / transport callback
        |
        v
E5C
        |
        v
E5D repair request
        |
        v
E5D repair task
        |
        v
R4 discovery
        |
        v
E5E repair-result notification
        |
        v
Reliability control operation
```

No blocking operation is permitted in:

```text
ESP-NOW callback
E5C callback
```

The existing E5D task/queue remains frozen and is not extended with new
responsibilities unless a separately approved interface requires it.

---

# 13. Repair-failure semantics

E5E must explicitly distinguish:

```text
repair SUCCESS
repair FAILURE
repair still ACTIVE
```

### Repair SUCCESS

The route is verified ACTIVE and does not use the failed next-hop.

E5E may request a reliability retry.

### Repair FAILURE

The route remains unavailable/STALE according to the frozen E5D behaviour.

E5E must not fabricate a route or mark the DATA delivered.

The reliability transaction eventually reaches its normal FAILED state according
to its defined policy.

### Repair ACTIVE

No reliability transaction completion or delivery result is generated.

---

# 14. Resolved timer semantics

E5D never manipulates a Reliability deadline.

The resolved semantic rule is:

```text
normal ACK timer
       |
transport failure correlated to repair
       |
       v
REPAIR_PENDING
       |
       | timer progression suspended
       |
repair SUCCESS
       |
       v
WAITING_FOR_ACK
       |
normal reliability retransmission
```

Entering `REPAIR_PENDING` does **not**:

- reset the retry counter;
- increment the retry counter;
- consume a retry;
- manufacture a new DATA transaction;
- extend the retry budget.

Repair time is therefore not counted as an ACK-timeout failure interval.

The retransmission after repair is a normal Reliability retransmission and is
subject to the existing retry policy.

If repair fails, the transaction returns to normal Reliability failure
processing; E5E does not invent an alternative retry policy.

# 17. Mandatory controlled negative tests

The E5E controlled test must also prove:

### Negative 1 — repair failure

```text
failure
  -> repair fails
  -> no fabricated route
  -> transaction does not become DELIVERED
```

### Negative 2 — wrong destination

A repair completion for another destination must not retry the transaction.

### Negative 3 — stale/old completion

A completion event for an old repair operation must not retry a newer
transaction incorrectly.

### Negative 4 — duplicate completion

The same repair-success event twice must not cause two reliability
retransmissions.

### Negative 5 — already completed transaction

A repair-success event arriving after ACK completion must be harmless.

### Negative 6 — retry exhaustion

Normal reliability retry accounting must remain bounded and deterministic.

### Negative 7 — unrelated route

Repair of another destination must not alter the transaction.

# 24. Resolved asynchronous TX-failure → Reliability correlation gate

The architecture requires an explicit proof of how an asynchronous transport
TX failure is associated with the Reliability transaction that originated the
failed DATA transmission.

The required path is:

```text
Reliability transaction T17
        |
        | DATA submit
        v
Routing DATA path
        |
        v
Transport / ESP-NOW
        |
        | asynchronous TX result
        v
E5C / failure observation
        |
        v
E5E correlation
        |
        v
repair operation R42
```

The correlation mechanism must preserve the association:

```text
T17 <-> R42
```

without:

- modifying the frozen P4-E5D Step-3 adapter;
- adding a Reliability field to ENP/R4 wire formats;
- making ESP-NOW transport own Reliability state;
- making E5C own Reliability transactions;
- duplicating the Reliability packet/transaction as a second owner.

The implementation audit must inspect the actual source path from the Reliability
submit callback through routing and transport TX-result observation and prove
which existing identity can safely survive the asynchronous boundary.

The preferred order is:

1. reuse an existing transaction/packet identity if it is demonstrably sufficient;
2. otherwise use the smallest bounded internal E5E correlation record;
3. only introduce a new internal correlation identity if the existing identity
   cannot safely satisfy the required lifetime and uniqueness constraints.

A new wire-format field is not permitted merely to solve this correlation
problem.

### E5E-I17 — mandatory implementation gate

The source-tree audit must answer:

> Given an asynchronous TX failure, exactly how does E5E identify the originating
> Reliability transaction?

No Reliability/E5E source implementation is authorized until this question is
answered against the real source tree.

# 25. Resolved repair-operation lifecycle and ownership

The repair operation is an E5E integration concept associated with the frozen E5D
repair service.

The lifecycle is:

```text
NONE
  |
  | E5E registers/associates repair
  v
REQUESTED
  |
  v
ACTIVE
  |
  +-------------------+
  |                   |
 SUCCESS            FAILURE
  |                   |
  v                   v
COMPLETED            FAILED
```

An obsolete or duplicate completion is not a new lifecycle transition:

```text
old/duplicate completion
          |
          v
        IGNORE
```

### Ownership

```text
E5E owns:
    repair_id
    transaction <-> repair association
    bounded correlation state
    repair lifetime/association state

E5D owns:
    repair execution
    R4 discovery
    RREQ/RREP processing
    route installation
    repair queue/task

Reliability owns:
    transaction
    packet
    ACK state
    retry count
    Reliability state
    final transaction result
```

E5D does not create or own the Reliability transaction association.

E5D does not need to know that a repair is being performed for a reliable DATA
transaction.

`repair_id` is an internal E5E control-plane identifier. It MUST NOT appear in
ENP DATA or R4 routing wire formats.

A normal repair may be associated with one Reliability transaction, but the
architecture does not require one-to-one cardinality. If one route repair
legitimately serves multiple transactions, E5E may maintain a bounded:

```text
repair_id -> {transaction handles}
```

association.

Destination-only correlation remains prohibited.

# 26. Resolved repair timeout and lifetime semantics

`REPAIR_PENDING` cannot be an unbounded wait.

A repair association therefore has a bounded lifetime:

```text
repair accepted
      |
      v
REPAIR_PENDING
      |
      +---- repair SUCCESS ----> resume
      |
      +---- repair FAILURE ----> normal failure policy
      |
      +---- repair TIMEOUT ----> normal failure policy
```

The repair lifetime is an E5E coordination bound. It is not an additional
Reliability retry budget.

During the repair lifetime:

- the Reliability transaction remains alive;
- the DATA packet remains unchanged;
- the retry count is unchanged;
- no retry is consumed merely because repair is active;
- normal ACK-timeout failure progression is suspended for the correlated
  transaction;
- no duplicate DATA is generated by the ordinary ACK timer.

When the repair lifetime expires:

```text
REPAIR_PENDING
      |
      v
repair timeout
      |
      v
normal Reliability failure processing
```

E5E does not invent a new retry algorithm at repair timeout.

The exact timeout representation and numerical value remain implementation-audit
items and must be derived from the existing project's timing/resource model.

### E5E-I18 — repair lifetime gate

The implementation audit must define:

1. where the repair deadline is stored;
2. which task/context evaluates it;
3. how it interacts with the existing Reliability tick;
4. how expiry returns control to normal Reliability failure processing;
5. how stale completion after expiry is rejected.

# 27. Resolved race-condition and invariant model

The following invariants are architectural requirements.

### Invariant 1 — transaction identity

A route repair never creates a replacement Reliability transaction.

```text
T17 before repair == T17 after repair
```

### Invariant 2 — repair identity

Every repair operation has its own bounded identity.

```text
R42 != R43
```

A second repair after a new transport failure is a new operation.

### Invariant 3 — stale completion

A completion for an old repair cannot complete a newer repair association.

```text
R42 complete
R43 active

late R42 complete -> IGNORE
```

### Invariant 4 — duplicate completion

The same completion delivered twice cannot cause two retransmissions.

```text
R42 SUCCESS
R42 SUCCESS again

=> one resume
```

### Invariant 5 — terminal transaction

A terminal Reliability transaction cannot be resurrected.

```text
T17 -> DELIVERED
late R42 SUCCESS -> IGNORE
```

### Invariant 6 — second failure

If the retransmission after repair fails again, it creates a new repair
operation rather than reusing the previous one.

```text
T17
 |
R42
 |
repair success
 |
retransmit
 |
transport failure
 |
R43
```

### Invariant 7 — same-destination isolation

Two transactions targeting the same destination cannot be selected by
destination alone.

```text
T1 -> C / R41
T2 -> C / R42

R41 SUCCESS -> T1 only
R42 SUCCESS -> T2 only
```

### Invariant 8 — unrelated destination isolation

A repair for another destination cannot alter the transaction.

### Invariant 9 — retry accounting

Repair time does not consume or reset the Reliability retry budget.

Only an actual Reliability retransmission consumes a retry.

### Invariant 10 — E5D isolation

E5D never reads or writes Reliability transaction state.

### Invariant 11 — no wire-format coupling

`repair_id` and E5E correlation state remain internal.

No RREQ/RREP/ENP wire-format modification is permitted.

### Invariant 12 — bounded resources

All correlation and repair-association state remains statically bounded.

No unbounded transaction-to-repair map is permitted.

### Architecture freeze boundary

The following semantic decisions are now authoritative E5E Step-1 architecture
decisions:

```text
1. explicit asynchronous failure → transaction correlation
2. explicit repair operation identity
3. E5E owns the transaction ↔ repair association
4. Reliability REPAIR_PENDING state
5. repair suspends ACK-timeout failure progression
6. retry budget is preserved during repair
7. repair has a bounded lifetime
8. resume uses the normal Reliability retransmission path
9. destination-only correlation is prohibited
10. multiple same-destination transactions are supported
11. stale/duplicate completion is harmless
12. a second failure creates a new repair operation
13. terminal transactions cannot be resurrected
14. E5D does not own or manipulate Reliability state
15. E5E correlation state is internal and bounded
16. no ENP/R4 wire-format changes
```

The exact C API and structures remain open until the source-tree implementation
audit confirms that they can be introduced without violating the frozen
P4-E5D Step-3 boundaries.

No implementation begins until the remaining OPEN gates are resolved.

- changes to P4-E5D Step-3;
- RREQ/RREP/RERR wire-format changes;
- new routing states;
- multi-path routing;
- route metrics beyond the existing contract;
- new transport APIs;
- ESP-NOW-specific reliability code;

# 27. Decision

**P4-E5E Step-1 architecture remains resolved for failure correlation, repair
identity, reliability state, resume semantics and multiple transactions.**

This revision does not redesign those decisions. It makes the architecture
authoritative by additionally resolving:

- the asynchronous TX-failure correlation as a mandatory implementation gate;
- repair-operation lifecycle and ownership;
- bounded repair lifetime/timeout semantics;
- explicit race-condition and invariant rules.

The authoritative model is:

```text
transport failure
      |
      v
exact asynchronous transaction correlation
      |
      v
repair operation Rxx
      |
      v
Reliability = REPAIR_PENDING
      |
      +---- SUCCESS ----> verified route -> Reliability resume
      |
      +---- FAILURE ----> normal Reliability failure policy
      |
      +---- TIMEOUT ----> normal Reliability failure policy
      |
      v
normal retransmission
      |
      +---- ACK -------> DELIVERED
      |
      +---- failure ---> new repair operation Ryy
```

The remaining work is an **implementation audit**, not another architecture
redesign.

The next audit actions are:

1. inspect the actual Reliability transaction/state machine;
2. trace the real asynchronous TX-result path from transport back to E5C/E5E;
3. prove the existing packet/transaction identity is sufficient or define the
   smallest bounded internal correlation record;
4. inspect the frozen E5D completion path and exact callback/context boundary;
5. derive the exact repair lifetime and static correlation capacity;
6. define the exact C structures and APIs;
7. implement the controlled E5E acceptance matrix;
8. run the complete regression suite before any hardware work.

The P4-E5D Step-3 source remains frozen throughout this work.
