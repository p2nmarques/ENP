# E3.3.7 Phase 4 / P4-E5D Step 3 — Hardware Validation Plan

**Status:** **EXECUTED — PASS / HARDWARE VALIDATED / FROZEN**
**Validation date:** 2026-08-23
**Validation revision:** V3.4
**Target:** ESP-IDF 6.0.2
**Frozen implementation:** P4-E5D Step 3

## 1. Purpose

Validate the already frozen Step-3 orchestration adapter on real ESP32 hardware without modifying the adapter.

## 2. First hardware gate

This first hardware gate uses a direct alternative path:

```text
             C / destination (node 3)
            / \
           /   \
 A / node 1     B / failed next-hop (node 2)
```

The initial route is deliberately:

```text
A -> B -> C
```

After B is powered off, the repair candidate is:

```text
A -> C
```

This is intentionally a direct-alternative hardware gate. It validates the complete real failure-to-repair chain without adding a new multi-hop relay requirement to the frozen Step-3 adapter.

## 3. Real path under test

```text
real DATA A -> B
        |
        | ESP-NOW TX failure
        v
       E5C
        |
        | route -> STALE
        v
       E5D
        |
        v
 Step-3 adapter
        |
        v
      R4-A
        |
        | real RREQ
        v
       C
        |
        | real RREP
        v
       A
        |
        v
 route C -> ACTIVE via C
```

## 4. Preparation

1. Flash node 1 with `CONFIG_ENP_E3_NODE_ID=1`.
2. Flash node 2 with `CONFIG_ENP_E3_NODE_ID=2`.
3. Flash node 3 with `CONFIG_ENP_E3_NODE_ID=3`.
4. Place A, B and C so that A can communicate with both B and C.
5. Keep B powered for neighbor discovery and initial route setup.
6. Ensure all three nodes use the same Wi-Fi channel.

## 5. Execution

### A — establish initial route

Wait for A to report:

```text
PASS: real neighbors B and C discovered
PASS: initial route C installed via real failed-next-hop B
PASS: initial route C is ACTIVE
PASS: initial route C uses next-hop B
PASS: initial route C sequence is 7
```

### B — remove failed next-hop

Power off node 2.

Do not restart A or C.

### A — trigger real failure

Type:

```text
e5d fail
```

The test submits a real DATA packet to C using the existing route through B.

## 6. Acceptance criteria

The A log must show:

- real DATA transmission submitted;
- E5C failure transitioned route C toward repair; the transient `STALE` state may be too short to be sampled, so V3.4 accepts direct observation of the transition or rapid completed repair;
- E5D repair became active;
- real RREQ was transmitted to C;
- C received the RREQ;
- C generated a real RREP;
- A received the RREP;
- repaired route became `ACTIVE`;
- repaired next-hop is C (node 3);
- destination sequence remains `7`.

Final result must be:

```text
E3.3.7 Phase 4 / P4-E5D Step-3 hardware validation PASS
```

## 7. Actual V3.4 hardware result

The three-node hardware run passed the complete failure-to-repair path.

Gateway evidence included:

```text
PASS: real E5C failure transitioned route C before rapid E5D repair completion
PASS: real E5C failure created/consumed an active E5D repair
PASS: real R4 rediscovery repaired route C via next-hop C
PASS: repaired route C is ACTIVE
PASS: repaired route C uses alternative next-hop C
PASS: repaired route C preserves sequence 7
E3.3.7 Phase 4 / P4-E5D Step-3 hardware validation PASS
```

Gateway RREP diagnostics also recorded:

```text
RREP classified #1
RREP RX entering adapter
RREP RX: from=3 destination=3 result=1
V3.3 DIAG RX summary: frames=19 verify-fail=0 route=1 rreq=0 rrep=1 unknown-route=0
```

Node C independently received the RREQ as the destination and transmitted the
RREP toward Gateway A. This confirms the real RREQ → RREP exchange rather than
a local-only repair simulation.

The V3.4 assertion correction was validation-only: it does not change the
Step-3 adapter or routing protocol.

## 8. Evidence boundary

This test does not claim:

- reliability recovery;
- application retransmission;
- multi-hop RREQ forwarding through a relay;
- multi-hop RREP forwarding through a relay;
- RERR validation.

Those are separate validation activities.

## 9. Frozen-code rule

If this test fails, do not immediately modify the Step-3 adapter.

First classify the failure as one of:

1. hardware/topology/setup issue;
2. test integration issue;
3. existing E3.2/R4 regression;
4. frozen Step-3 implementation defect;
5. contract/interface defect.

Only category 4 or 5 can justify reopening the Step-3 freeze.
