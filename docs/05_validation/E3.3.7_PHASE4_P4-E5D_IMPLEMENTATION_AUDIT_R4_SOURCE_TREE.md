# P4-E5D Implementation Audit — Actual R4 Source Tree

**Contract:** E3.3.7 Phase 4 / P4-E5D Route Repair / Rediscovery Integration Contract v3  
**Contract status:** FROZEN — APPROVED CONTRACT  
**Source baseline:** `ENP-0.2-r5(20260818-183327).zip`  
**Target:** ESP-IDF 6.0.2  
**Audit date:** 2026-08-18

## 1. Audit purpose

This audit checks the frozen P4-E5D contract against the actual R4 routing source
tree before implementation.

The audit deliberately does **not** implement E5D or change any source file.

The contract requires ten implementation audit gates before coding begins. The
results below are based on the actual R4 source files in:

```text
main/core/routing/
    enp_route_table.*
    enp_route_discovery.*
    enp_rreq_processor.*
    enp_rrep_processor.*
    enp_rerr_processor.*
    enp_routing_data_path.*

main/core/reliability/
    enp_reliability.*
    enp_reliability_service.*

main/core/enp_maintenance.c
main/core/enp_context.h
main/config/enp_defaults.h
```

## 2. Executive result

**E5D implementation should NOT start yet.**

The audit confirms that the frozen contract is architecturally consistent with
the existing R4 separation, but several required integration capabilities do
not currently exist in the production source tree.

The most important findings are:

1. **Failed-next-hop exclusion is not represented by the existing R4 APIs.**
2. **There is no production E5D → R4 repair API.**
3. **R4 discovery is a single-transaction state machine, not a production
   destination-aware repair coordinator.**
4. **Route installation/freshness ownership is callback-based and not currently
   wired into a production runtime.**
5. **Reliability currently fails immediately when routing cannot submit the
   packet; there is no repair pause/resume integration.**
6. **There is no production routing/repair task or queue.**
7. **R4 timeout constants are inconsistent with the repository's routing defaults
   and documentation and must be resolved before E5D implementation.**

These are architecture/interface gaps, not reasons to change the frozen E5D
contract prematurely.

## 4. E5D-A01 — Route-state audit

### Actual implementation

`enp_route_state_t` defines:

```c
ENP_ROUTE_STATE_INVALID = 0
ENP_ROUTE_STATE_ACTIVE  = 1
ENP_ROUTE_STATE_STALE   = 2
```

However, `INVALID` is used for unused route-table slots:

- initialization marks unused entries `INVALID`;
- removal clears the final slot and marks it `INVALID`;
- `entry_is_valid()` accepts only `ACTIVE` and `STALE`;
- route lookup returns a route only when its state is `ACTIVE`;
- invalidation changes an installed route to `STALE`.

### Finding

The source tree **does contain an `INVALID` enum value**, but it is not an
installed-route state representing repair failure.

Therefore the frozen E5D contract is correct to prohibit E5D from using
`INVALID` as a persistent repair state.

### Gate result

**RESOLVED.**

No contract change is required.

---

## 5. E5D-A02 — R4 API audit

### Actual API

The discovery start interface is:

```text
enp_route_discovery_start(
    discovery,
    destination,
    route_request_id,
    destination_sequence,
    ttl,
    now_ms
)
```

The discovery object stores:

```text
state
destination
route_request_id
destination_sequence
ttl
retry_count
started_at_ms
deadline_ms
```

There is no:

```text
failed_next_hop
repair_reason
repair_context
```

and no API equivalent to:

```text
repair(destination, failed_next_hop)
```

### Finding

The frozen contract correctly treated that notation as conceptual.

The actual source confirms that a repair integration interface does not yet
exist.

### Gate result

**BLOCKED.**

Before implementation we need an explicit interface decision.

---

## 6. E5D-A03 — Failed-next-hop exclusion audit

### Actual implementation

The RREQ processor receives:

```text
originator
immediate_sender
RREQ
```

and its reverse-route callback receives:

```text
originator
next_hop
hop_count
destination_sequence
lifetime
```

The RREP processor receives:

```text
previous_hop
RREP
```

and its route-update callback receives:

```text
destination
next_hop
destination_sequence
hop_count
lifetime
metric
```

None of these interfaces carries a repair exclusion such as:

```text
failed_next_hop = X
```

There is also no R4 discovery field for a forbidden next-hop.

### Gate result

**BLOCKED.**

This is the first major interface extension that E5D must resolve.

Importantly, this does **not** mean adding an arbitrary field immediately.

We must first decide whether failed-next-hop exclusion belongs:

1. in the local repair/discovery context;
2. in the RREQ generation/processing policy;
3. in route selection;
4. or in another existing routing boundary.

## 7. E5D-A04 — Duplicate-discovery audit

### Actual behaviour

`enp_route_discovery_start()` rejects a second start whenever the current
discovery object is already in `REQUESTING`.

Therefore one discovery object can represent only one outstanding discovery
transaction.

The RREQ processor does not own a duplicate cache. It invokes:

```text
is_duplicate(context, originator, request_id)
```

through a callback.

### Finding

There is useful bounded suppression, but it is not yet the E5D contract's
destination-aware repair coordinator.

In particular:

```text
destination A repair active
destination B repair requested
```

cannot both be represented by one discovery object.

The source tree does not contain a production per-destination repair registry.

### Gate result

**PARTIAL.**

E5D must reuse existing suppression where possible, but an integration decision
is required for repair coordination.

---

## 8. E5D-A05 — Route-installation audit

### Actual implementation

R4-A explicitly does not modify the route table.

R4-C updates a route only through:

```text
update_route(context, ...)
```

The actual route-table operation is therefore callback-owned.

The repository's routing integration tests provide callback implementations that
install/update routes, but the production `main/core` runtime does not currently
wire R4 discovery, RREQ processing and RREP processing into a production route
repair orchestration.

### Gate result

**GAP.**

Before E5D implementation we must identify the authoritative production
route-installation integration point.

---

## 9. E5D-A06 — Repair-failure audit

### Actual implementation

R4-A.1 has:

```text
IDLE
REQUESTING
COMPLETE
FAILED
```

and bounded retry behaviour.

After `ENP_MAX_RETRIES`, the discovery enters:

```text
FAILED
```

However, the module has no failure callback or event interface to notify:

```text
E5D
Reliability
Route table
```

of that failure.

### Gate result

**PARTIAL/GAP.**

The state-machine failure semantics exist, but production failure propagation
does not.

---

## 10. E5D-A07 — Sequence / metadata audit

### Actual implementation

R4-A.1 compares an incoming RREP destination sequence against the requested
destination sequence before completing discovery.

R4-C forwards the RREP destination sequence to its `update_route()` callback.

However:

- `enp_route_table_update()` does not compare route sequence freshness;
- the route table accepts a valid update and replaces the existing entry;
- R4-C itself does not decide whether the new route is fresher or better.

Therefore route metadata selection is delegated to the callback integration.

### Gate result

**GAP.**

The authoritative production owner of:

```text
fresher route
better route
sequence comparison
metric comparison
```

must be identified before E5D can safely install repaired routes.

This is especially important because E5D must preserve existing route sequence
semantics.

## 11. E5D-A08 — Reliability integration audit

The current reliability architecture is highly relevant.

Reliability owns:

```text
transaction table
DATA sequence
application sequence
retry count
ACK correlation
ACK timeout
retransmission
```

and retains a static copy of the original packet.

The submit callback is the routing integration boundary.

However, the current routing path returns:

```text
ESP_ERR_NOT_FOUND
```

when no `ACTIVE` route exists.

The current reliability implementation treats a non-`ESP_OK` result from the
initial submit as immediate transaction failure.

During retry:

```text
ACK timeout = 1000 ms
```

the reliability layer invokes the same submit callback again.

There is currently no:

```text
repair requested
repair pending
repair completed
resume transaction
```

interface.

### Important timing consequence

R4 discovery currently has its own timeout/retry state, while reliability has a
1-second ACK timeout.

Therefore E5D cannot simply block reliability until discovery finishes without
an explicit integration design.

### Gate result

**BLOCKED.**

This is a major E5D integration boundary.

The solution must preserve reliability ownership as required by the frozen
contract; it must not simply reset or extend reliability timers as an
implementation shortcut.

---

## 12. E5D-A09 — Context / concurrency audit

### Actual implementation

The route table has no mutex.

R4-A.1 deliberately has no FreeRTOS dependency and no queue/task.

The current production maintenance task is static and performs:

```text
reliability tick
neighbor expiry
periodic service discovery
```

There is no production routing/repair task or bounded repair queue in
`main/core`.

The current E5C routing-data-path callback can mutate route state directly from
the transport send-result callback path.

E5D, however, must not perform lengthy RREQ/RREP discovery work in that
transport callback context.

### Gate result

**GAP.**

The implementation must establish where repair requests execute.

The preferred design remains:

```text
transport/routing event
        |
        v
bounded event/queue
        |
        v
routing/repair execution context
        |
        v
R4 discovery
```

but the actual queue/task ownership must be determined from the production
context architecture.

---

## 13. E5D-A10 — Resource audit

Confirmed bounded resources include:

```text
ENP_MAX_ROUTES = 64
```

and the R4-A.1 discovery object is a fixed-size structure.

R4-A.1 also has a bounded retry count.

However, RREQ duplicate and reverse-route storage is callback-owned. There is no
production bounded implementation of that state in `main/core`.

Therefore the final E5D repair capacity cannot yet be derived.

### Gate result

**PARTIAL.**

Any E5D repair state must be explicitly bounded after the integration design is
chosen.

## 14. Additional source-tree finding — configuration inconsistency

The audit found an important pre-E5D inconsistency.

`enp_route_discovery.h` defines defaults of:

```text
ENP_MAX_RETRIES              = 3
ENP_DISCOVERY_TIMEOUT_MS     = 2000 ms
ENP_DISCOVERY_DEFAULT_TTL    = 8
```

while `main/config/enp_defaults.h` contains:

```text
ENP_MAX_RETRIES              = 3
ENP_DISCOVERY_INTERVAL_MS    = 2000 ms
ENP_DISCOVERY_TIMEOUT_MS     = 6000 ms
```

The routing protocol document describes:

```text
RREQ response timeout = 1000 ms
Maximum RREQ retries  = 3
```

The current source therefore has multiple discovery timing definitions.

### Consequence

E5D must not independently choose repair timing until this is resolved.

This should be treated as an **R4 configuration audit issue** before E5D coding.

## 15. Additional source-tree finding — R4 production orchestration boundary

The source tree contains:

```text
enp_route_discovery.*
enp_rreq_processor.*
enp_rrep_processor.*
enp_rerr_processor.*
```

and they are compiled by the main component.

However, these modules are deliberately separated by callback interfaces and
the production `enp_context_t` does not currently contain an R4 discovery state,
route-table ownership object, repair coordinator, or RREQ/RREP processor
instances.

The existing integration examples in `main/tests/2-E/E1` and later E3 tests
construct these objects and supply test-local callbacks.

Therefore:

> **R4 exists as validated routing infrastructure, but the source tree does
> not yet expose a single production runtime R4 orchestration interface that
> E5D can call.**

This is the central finding of the audit.

## 16. What the audit proves

The audit confirms that the frozen E5D contract is compatible with the existing
architecture in these respects:

### Confirmed

- `ACTIVE -> STALE` is the actual route invalidation transition.
- `INVALID` is an unused-slot sentinel rather than the normal installed-route
  failure state.
- R4 discovery is deliberately separated from transport and route-table
  storage.
- RREQ duplicate checking is callback-based.
- RREP route updates are callback-based.
- R4 has bounded discovery state and bounded retries.
- Reliability owns transaction identity and retransmission state.
- Routing data-path submission is the existing DATA routing boundary.
- E5D should not create a second RREQ/RREP state machine.
- E5D should not directly depend on ESP-NOW.

These observations support the ownership model in the frozen contract.

## 17. What is NOT yet implemented / available

The following capabilities required by E5D are not currently present as
production interfaces:

```text
repair request API
failed-next-hop exclusion
production repair coordinator
production per-destination repair state
production R4 orchestration API
repair failure propagation
repair completion propagation
route freshness/better-route integration
reliability repair pause/resume integration
production routing repair task/queue
bounded repair-state capacity
```

These must be designed before implementation.

---

## 18. Recommended next step

Do **not** start E5D implementation yet.

The next step should be a focused **P4-E5D Interface Extension Design / Audit
Resolution** addressing only these source-tree gaps:

```text
1. E5D repair-request boundary
2. failed-next-hop exclusion boundary
3. R4 orchestration boundary
4. duplicate-repair coordination
5. route-installation/freshness ownership
6. repair completion/failure signalling
7. reliability interaction
8. routing/repair execution context
9. bounded repair-state capacity
10. discovery timing/configuration ownership
```

The goal should be to produce the minimum interface extension required to connect
E5D to the existing R4 infrastructure.

We should **not** redesign R4.

## 19. Audit decision

### Current decision

**P4-E5D IMPLEMENTATION: NOT CLEARED**

Reason:

> The existing R4 components provide the core route-discovery primitives, but
> the production integration boundary required by E5D does not yet exist.

This is exactly the situation for which the frozen contract's Section 29 audit
gate was intended.

### Contract status

The P4-E5D contract remains:

**FROZEN — APPROVED CONTRACT**

No contract change is recommended as a result of this audit.

### Implementation status

**BLOCKED PENDING INTERFACE-EXTENSION DESIGN / AUDIT RESOLUTION**

The next design step should therefore be narrowly scoped to resolving the
identified R4 integration gaps without changing the frozen E5D architectural
contract.
