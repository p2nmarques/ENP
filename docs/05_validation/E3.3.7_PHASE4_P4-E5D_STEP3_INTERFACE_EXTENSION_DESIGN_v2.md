# E3.3.7 PHASE 4 / P4-E5D

# STEP 3 --- R4 ROUTE REDISCOVERY INTERFACE EXTENSION DESIGN v2

**Status:** **FROZEN — APPROVED INTERFACE SEMANTICS**\
**Baseline:** `ENP-0.2-r5(20260821-191821)`\
**Target:** ESP-IDF 6.0.2\
**Scope:** E5D → R4 route rediscovery integration\
**Revision:** v2 --- conservative interface boundary

------------------------------------------------------------------------

## 1. Purpose

This document defines the Step-3 interface-extension design for
connecting the already validated E5D route-repair coordinator to the
existing R4 route-discovery implementation.

The design deliberately freezes **interface semantics and ownership**,
while leaving implementation-specific details that are not yet required
by the audited R4 source tree open.

The objective is to:

-   connect E5D repair requests to existing R4 discovery;
-   preserve R4-A, R4-B, R4-C and route-table ownership;
-   preserve the RREQ/RREP wire format;
-   preserve transport independence;
-   preserve bounded/static resource policy;
-   enforce failed-next-hop exclusion at the correct routing integration
    boundary;
-   bridge successful RREP processing back into the active R4-A
    discovery transaction.

------------------------------------------------------------------------

# 2. Contract status

**Status: PROPOSED --- READY FOR REVIEW**

This document is not yet frozen.

Approval shall freeze the **interface semantics, ownership boundaries
and behavioural rules** defined here.

Implementation-specific choices shall remain subject to the
implementation audit unless explicitly stated as contract requirements.

------------------------------------------------------------------------

# 3. Architectural position

The Step-3 integration boundary is:

``` text
E5C
 |
 | route failure
 v
E5D repair coordinator
 |
 | repair request
 v
E5D / routing-control adapter
 |
 +-------------------+
 |                   |
 v                   v
R4-A                R4-B / R4-C
discovery           routing processing
 |                   |
 +---------+---------+
           |
           v
      route table
           |
           v
     repaired route
```

The adapter is an **orchestration boundary**.

It does not become the owner of R4 discovery, RREQ/RREP processing,
route state or transport.

------------------------------------------------------------------------

# 4. Existing R4 interfaces remain authoritative

The existing R4-A primitives remain the authoritative discovery
interface:

``` c
enp_route_discovery_start(...)
enp_route_discovery_on_rrep(...)
enp_route_discovery_on_timeout(...)
enp_route_discovery_is_active(...)
enp_route_discovery_state(...)
```

The existing R4-B and R4-C callback interfaces remain authoritative for
RREQ/RREP processing.

No new public R4 API of the form:

``` c
repair(destination, failed_next_hop)
```

shall be introduced.

No RREQ or RREP wire-format extension is required.

------------------------------------------------------------------------

# 5. Ownership model

  -----------------------------------------------------------------------
  Responsibility                      Owner
  ----------------------------------- -----------------------------------
  Detect transport failure            E5B / transport

  Mark affected route `STALE`         E5C

  Generate repair request             E5C → E5D

  Suppress duplicate repair requests  E5D

  Queue/execute repair work           E5D

  Maintain active repair integration  E5D / routing-control adapter
  state                               

  Own discovery state machine         R4-A

  Process RREQ                        R4-B

  Process RREP                        R4-C

  Own route state and metadata        route table

  Physical transmission               transport integration

  DATA transaction identity           reliability layer
  -----------------------------------------------------------------------

The adapter coordinates these components; it does not absorb their
ownership.

------------------------------------------------------------------------

# 6. Repair request semantics

The existing E5D repair request remains conceptually:

``` text
destination
failed_next_hop
```

The `failed_next_hop` is **local repair context**.

It is not:

-   an RREQ field;
-   an RREP field;
-   a new R4-A parameter;
-   a new protocol identity.

The repair context must remain available for the duration of the active
repair transaction.

------------------------------------------------------------------------

# 7. Adapter context --- semantic contract only

The adapter shall maintain sufficient state to represent:

``` text
active repair destination
failed next-hop
active R4 discovery state/reference
R4 discovery transaction identity
repair lifecycle state
```

The exact C structure, field names and ownership of embedded R4 objects
are **not frozen by this document**.

In particular, this document does not require a new public structure
such as:

``` c
typedef struct {
    ...
} enp_routing_repair_context_t;
```

unless the implementation audit demonstrates that such a structure is
necessary.

The adapter context may be implemented using an existing production
routing-control object if that provides the required ownership boundary.

------------------------------------------------------------------------

# 8. RREP-originator correlation

No RREP originator field shall be added.

The R4-C forwarding decision continues to use the existing
discovery-originator context.

R4-A remains responsible for correlating a received RREP against its
active discovery using the existing destination and destination-sequence
semantics.

Therefore:

``` text
R4-C
 |
 | discovery_complete(destination, sequence)
 v
routing-control adapter
 |
 v
enp_route_discovery_on_rrep(...)
 |
 v
R4-A
```

The adapter shall not duplicate R4-A's authoritative correlation rules.

------------------------------------------------------------------------

# 9. R4-B integration

The existing R4-B callback interfaces shall be used unchanged.

The routing-control integration may supply the adapter/routing-control
context through the existing callback `void *context` mechanism.

The exact callback assignments shall be verified against the actual R4
source during implementation.

No R4-B public callback signature change is permitted without a
separately approved interface extension.

------------------------------------------------------------------------

# 10. R4-C integration

The existing R4-C callback interfaces shall be used unchanged.

The routing-control integration may supply the adapter/routing-control
context through the existing callback `void *context` mechanism.

The R4-C `discovery_complete` event is the completion boundary between
R4-C and the active R4-A discovery transaction.

No R4-C public callback signature change is permitted without a
separately approved interface extension.

------------------------------------------------------------------------

# 11. RREP → R4-A completion bridge

The semantic completion bridge is:

``` text
R4-C discovery_complete
        |
        v
routing-control adapter
        |
        v
enp_route_discovery_on_rrep()
```

The adapter shall:

1.  validate that an active repair/discovery exists;
2.  associate the completion event with the active repair destination;
3.  forward the destination and destination sequence to R4-A;
4.  allow R4-A to remain authoritative for discovery correlation and
    state transition.

The adapter shall not directly force R4-A into `COMPLETE`.

------------------------------------------------------------------------

# 12. Active discovery lifecycle

The lifecycle is:

``` text
IDLE
 |
 | E5D repair request
 v
START
 |
 | enp_route_discovery_start()
 v
ACTIVE
 |
 +-----------------------+
 |                       |
 | accepted RREP         | timeout/failure
 v                       v
R4-A completion        R4-A failure
 |                       |
 v                       v
route verification     repair failure
 |
 v
repair success
 |
 v
IDLE
```

There shall be **one active R4-A discovery transaction for the repair
execution context**.

Multiple E5D repair requests may remain pending.

They shall not create parallel R4-A transactions unless a separately
approved architecture changes this rule.

------------------------------------------------------------------------

# 13. Discovery start

When an E5D repair request is executed, the integration shall:

1.  confirm that the repair request is still valid;
2.  confirm that no conflicting active repair exists;
3.  obtain the current destination sequence according to the existing
    route-table contract;
4.  create/select the R4 discovery transaction identity required by
    `enp_route_discovery_start()`;
5.  preserve the failed-next-hop repair context;
6.  start the existing R4-A discovery.

R4-A remains responsible for its existing discovery timeout/retry
semantics.

E5D shall not introduce a second discovery timeout.

------------------------------------------------------------------------

# 14. Failed-next-hop exclusion

The existing R4-A start interface does not contain a forbidden-next-hop
parameter.

Therefore the failed-next-hop constraint shall be enforced where the
candidate route next-hop is actually available.

Required policy:

``` text
candidate next-hop == failed_next_hop
        |
        v
      REJECT
```

and:

``` text
candidate next-hop != failed_next_hop
        |
        v
      ACCEPT / normal route processing
```

This is an adapter-level repair policy.

It shall not be encoded in RREQ/RREP payloads.

The exact implementation point must be identified during the
implementation audit.

------------------------------------------------------------------------

# 15. Route-update ownership

R4-C remains responsible for identifying a valid RREP route-update
event.

The routing-control integration is responsible for applying the E5D
failed-next-hop repair constraint at the appropriate candidate-route
boundary.

The route table remains authoritative for:

-   route state;
-   route metadata;
-   destination sequence;
-   installed next-hop.

The adapter shall not duplicate route-table state ownership.

------------------------------------------------------------------------

# 16. Successful repair

R4-A completion is necessary but not by itself sufficient for E5D repair
success.

Successful repair requires:

``` text
R4 discovery completed
AND
route exists for destination
AND
route state == ACTIVE
AND
route next-hop != failed_next_hop
```

Only then shall the repair be reported as successful.

------------------------------------------------------------------------

# 17. Repair failure

If R4 discovery fails:

``` text
repair = FAILED
```

The existing route shall remain governed by the existing route-table
contract.

For the E5D repair scenario, the expected state remains:

``` text
STALE
```

unless another existing route-table rule independently changes it.

No new route state is introduced by Step 3.

------------------------------------------------------------------------

# 18. Multiple destinations

E5D may contain:

``` text
D1 → H1
D2 → H1
D3 → H2
```

as independent pending repairs.

They shall be processed serially:

``` text
D1 → R4 discovery → complete/fail
D2 → R4 discovery → complete/fail
D3 → R4 discovery → complete/fail
```

A successful repair of one destination shall not implicitly repair
another destination.

------------------------------------------------------------------------

# 19. Duplicate suppression

E5D remains responsible for duplicate repair suppression.

R4-A remains responsible for rejecting an invalid/concurrent discovery
start according to its existing state machine.

The two mechanisms are complementary.

Step 3 shall not replace the existing E5D duplicate-suppression
mechanism with a second global repair registry.

------------------------------------------------------------------------

# 20. Repeated failures

If a destination is already pending/active:

``` text
new failure
    ↓
E5D duplicate suppression
```

If its previous repair has completed or failed and its pending state has
been released:

``` text
later failure
    ↓
new E5D repair transaction
```

There shall be no permanent suppression of a destination.

------------------------------------------------------------------------

# 21. Reliability boundary

Step 3 does not modify reliability semantics.

The R4 discovery transaction identity is separate from:

``` text
ENP DATA transaction identity
```

A repaired route does not create a new DATA transaction identity.

Retransmission after route repair remains a reliability-layer concern.

------------------------------------------------------------------------

# 22. Callback/task boundary

The following is prohibited:

``` text
ESP-NOW callback
      |
      v
R4-B/R4-C processing
```

and:

``` text
ESP-NOW callback
      |
      v
enp_route_discovery_on_rrep()
```

R4 processing must occur in an appropriate non-transport-callback
execution context.

The precise existing task/queue used to provide that context is **not
frozen here**.

The implementation audit shall determine whether the existing production
routing RX/E5D task boundary is sufficient.

A new routing-control queue/task shall **not** be introduced merely
because this document defines an orchestration adapter.

------------------------------------------------------------------------

# 23. Queue and task policy

The following are frozen requirements:

-   bounded resources;
-   no dynamic allocation;
-   no R4 processing directly from ESP-NOW callbacks;
-   one active R4 discovery transaction for the repair execution
    context.

The following are deliberately **not frozen**:

-   creation of a new routing-control queue;
-   creation of a new routing-control task;
-   exact queue depth;
-   exact task stack size;
-   exact event structure.

Those decisions belong to implementation audit and resource analysis.

------------------------------------------------------------------------

# 24. Transport boundary

R4 remains transport-independent.

RREQ/RREP transmission shall use the existing production ENP
packet-construction and transport-submission path.

Conceptually:

``` text
R4 routing decision
      |
      v
existing ENP packet construction
      |
      v
enp_packet_seal()
      |
      v
existing transport submission
```

No routing-specific transport API shall be introduced.

------------------------------------------------------------------------

# 25. Wire-format boundary

Step 3 shall not modify:

``` text
RREQ wire format
RREP wire format
ENP DATA wire format
```

No failed-next-hop field is added to RREQ or RREP.

No new RREP originator field is required.

------------------------------------------------------------------------

# 26. Implementation audit gates

Before implementation freeze:

### S3-I01 --- Exact R4-A start integration

Identify the production owner of the `enp_route_discovery_t` instance.

### S3-I02 --- Exact RREQ integration

Identify the existing production path from R4 discovery state to ENP
RREQ transmission.

### S3-I03 --- Exact RREP integration

Identify the existing R4-C completion callback and prove its path to
R4-A.

### S3-I04 --- Failed-next-hop exclusion

Identify the exact candidate-route boundary where next-hop identity is
available.

### S3-I05 --- Route-table integration

Identify the existing route-table update and lookup callbacks used by
R4.

### S3-I06 --- Timeout ownership

Verify that `ENP_DISCOVERY_TIMEOUT_MS` remains the sole R4 discovery
timeout configuration.

### S3-I07 --- Active discovery ownership

Identify the exact single active-discovery lifecycle.

### S3-I08 --- Task context

Prove that R4 processing does not execute in ESP-NOW callback context.

### S3-I09 --- Resource bound

Document exact queue/task/resource requirements after examining the
existing production path.

### S3-I10 --- Regression

Run E3.2 and relevant E5A/E5B/E5C controlled tests without changing
their contracts.

All ten gates must pass before implementation is frozen.

------------------------------------------------------------------------

# 27. Controlled validation

Step-3 controlled validation shall prove:

1.  E5D repair request starts one R4 discovery.
2.  A duplicate request does not create a second discovery.
3.  R4-A becomes active.
4.  RREQ uses the existing packet/transport path.
5.  RREP reaches R4-C.
6.  R4-C completion reaches R4-A.
7.  R4-A completes only for an acceptable RREP.
8.  A route using the failed next-hop is rejected.
9.  An allowed alternative next-hop can be accepted.
10. Successful repair produces an `ACTIVE` route.
11. Failed discovery does not manufacture a route.
12. Multiple pending destinations are processed serially.
13. Unrelated routes remain unchanged.
14. R4 processing occurs outside the ESP-NOW callback context.

------------------------------------------------------------------------

# 28. Hardware validation boundary

Hardware validation remains a separate evidence level.

The controlled Step-3 test must pass first.

Hardware validation shall later demonstrate:

``` text
real next-hop failure
        ↓
E5C
        ↓
E5D
        ↓
real R4 discovery
        ↓
real RREQ/RREP exchange
        ↓
failed-next-hop exclusion
        ↓
alternate route
        ↓
ACTIVE repaired route
```

Topology and node-count decisions belong in the hardware-validation
document.

------------------------------------------------------------------------

# 29. Freeze criteria

Step 3 may be frozen when:

-   the ten implementation audit gates pass;
-   exact R4 integration points are documented;
-   failed-next-hop exclusion is implemented without wire-format
    changes;
-   controlled validation passes;
-   E3.2 regression remains valid;
-   E5A/E5B/E5C remain unchanged and passing;
-   no R4-A/B/C ownership is transferred;
-   no route-table ownership is transferred;
-   resource bounds are documented;
-   task-context behaviour is verified;
-   documentation is synchronized.

Hardware validation is required before declaring P4-E5D overall
`HARDWARE VALIDATED`.

# 31. Decision

**P4-E5D Step 3 Interface Extension Design v2: PROPOSED --- READY FOR
REVIEW**

The recommended interface direction is:

``` text
E5D
 ↓
thin routing-control/orchestration adapter
 ↓
existing R4-A/B/C
 ↓
existing route table
 ↓
existing transport integration
```

The design deliberately does **not** freeze:

-   an exact new adapter C structure;
-   a new routing-control queue;
-   a new routing-control task;
-   a new R4 public repair API;
-   any RREQ/RREP wire-format change.

The design **does** freeze the semantic boundaries:

-   E5D owns repair coordination;
-   R4-A owns discovery state;
-   R4-B owns RREQ processing;
-   R4-C owns RREP processing;
-   the route table owns route state/metadata;
-   the adapter owns repair-specific orchestration;
-   failed-next-hop exclusion is applied at the route-candidate
    integration boundary;
-   RREP completion is bridged back to R4-A through the existing
    discovery interface;
-   R4 processing does not execute directly from ESP-NOW callback
    context.

**This v2 is the recommended freeze candidate, subject to final
review.**
